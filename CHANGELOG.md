# Changelog

All notable changes to SuperBot are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The version is `server/Cargo.toml`'s; tagging `v<version>` publishes the images ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)) and a GitHub release with that version's section below as its notes ([ADR 0111](docs/adr/0111-changelog-and-github-releases.md)).

Add each user-facing change to the newest section in the PR that makes it. Once that version is tagged, start a `## [Unreleased]` section above it, and rename it to the next version, with `server/Cargo.toml` bumped to match, before tagging that one. CI checks the format, that the newest version is `server/Cargo.toml`'s, and that every tag has a dated section (`deploy/release-notes.sh`).

## [0.1.0] - Unreleased

The first release: everything merged to `main` up to the M4 public-launch work ([roadmap](docs/ROADMAP.md)).

### Added

- `botd`, a harness-agnostic Bot server in Rust, with adapters for Claude Code, Codex, Pi and Hermes Agent ([ADR 0011](docs/adr/0011-hermes-agent-backend.md)); Hermes Agent is the default harness on managed tiers ([ADR 0079](docs/adr/0079-hermes-default-for-managed-tiers.md)).
- A computer per Bot: a screen with a browser and desktop apps, shown live ([ADR 0003](docs/adr/0003-computer.md)).
- Bot-to-Bot messaging (`botctl ask`), routines, per-Bot model and reasoning effort, and suggested prompts.
- An Expo client for web, iOS and Android as the single interface, with a minimal admin-only console ([ADR 0027](docs/adr/0027-expo-primary-hermes-default.md), [ADR 0032](docs/adr/0032-console-admin-only.md)), push notifications ([ADR 0080](docs/adr/0080-client-push-notifications.md)) and an optional biometric app lock ([ADR 0078](docs/adr/0078-client-biometric-app-lock.md)).
- Installs: a VPS installer and Docker Compose ([ADR 0006](docs/adr/0006-docker-compose.md)), published multi-arch images on GHCR with computer use ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)), an onboarding wizard ([ADR 0034](docs/adr/0034-onboarding-wizard.md)) and a backup and restore tool with a CI drill ([ADR 0030](docs/adr/0030-backup-restore-drill.md)).
- Multi-user: users, server-side sessions and RBAC ([ADR 0012](docs/adr/0012-users-sessions-rbac.md)); sign-in with Microsoft Entra ID, Google, generic OIDC, GitHub, Apple and SAML through a broker; SCIM 2.0 provisioning, with SCIM groups as teams ([ADR 0095](docs/adr/0095-scim-groups-as-teams.md)); shared and private Bots.
- Approvals and a harness permission policy, with an editor, notifications and end-to-end hook tests against the real harness CLIs ([ADR 0007](docs/adr/0007-approvals.md)).
- Per-user isolation: a Unix account per user on one server ([ADR 0037](docs/adr/0037-per-user-unix-accounts.md)), teammates' own accounts and logins, and a token per run ([ADR 0083](docs/adr/0083-per-run-tokens.md)).
- A managed control plane: one machine per user on Linode or as an Incus container ([ADR 0025](docs/adr/0025-control-plane-linode.md), [ADR 0065](docs/adr/0065-incus-container-machines.md)), enrolled over mutual TLS ([ADR 0031](docs/adr/0031-machine-enrollment-mtls.md)), with harness CLIs, logins, screens, off-host backups, restores onto another host and placement by host load.
- Teams with a machine per teammate ([ADR 0087](docs/adr/0087-team-accounts-and-machines.md)).
- UK/EU data regions: a server admin sets a region, such as London (`gb-lon`) or Frankfurt (`de-fra-2`), for a user or a team; their machines are made only there (a Linode in that region, or an Incus host tagged with it) and their off-host backups go to that region's store, with requests, restores and region changes that would put data elsewhere refused and audited; `botctl regions`, `botctl user region`, `botctl team region`, and the console and app show it ([ADR 0117](docs/adr/0117-uk-eu-data-regions.md)).
- Contractual data residency: a server admin pins a user or a team to a data region under an agreement reference (`botctl user|team residency`, the console, or the admin API). The pin is refused while the region has no host or backup store, or any of their data is elsewhere. While it holds, their region can't change, a pinned team takes no member with data elsewhere and can't be deleted, backups go only to a store in the region even with `MACHINE_BACKUP_RESIDENCY=warn`, and restores, moves and lost-host recoveries outside it are refused; every pin, unpin (with a reason) and refusal is audited, and pins that can't be kept are warned about at startup and in `GET /api/regions` ([ADR 0129](docs/adr/0129-contractual-data-residency.md)). The DPA template gains a data residency annex that says plainly what a pin doesn't cover (botd's own data and model calls, with the regions model providers offer), and the security pack a DPIA template for customers.
- In-region model routes for residency pins ([ADR 0139](docs/adr/0139-in-region-model-routes.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a tiers file endpoint may list the data `regions` it processes in. While a user or team is pinned, their Bots' runs (and runs they ask for, through any number of Bots asking Bots) take only a route whose endpoint is marked as in their region and keep only in-region fallbacks. Hermes Agent's side tasks stay on the run's endpoint, and built-in providers' keys are left out. With no such route, including on open tiers and for Claude Code or Codex, the run is refused and audited as `bot.run_refused` (`residency_pinned`); so is a queued run whose people were pinned while it waited. Pinned plans without a route there are warned about at startup and in `GET /api/regions`.
- Residency reports ([ADR 0155](docs/adr/0155-residency-reports.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `botctl user|team residency <key> report` (or `GET /api/users/{key}/residency/report`, `/api/teams/{id}/residency/report`) makes a report on one pin for the customer, as Markdown or JSON: where each covered person's machine, host and backups are and whether all of it is in the region, warnings, the pin's changes, what it refused and how many runs it held to in-region routes in a period (the last 90 days by default), and what it doesn't cover. It is sealed with a SHA-256 digest the customer can check with `jq` and `sha256sum`, and each report is audited as `residency.report_generated`. The DPA's residency annex lists it as evidence.
- Residency in the app ([ADR 0168](docs/adr/0168-residency-in-the-app.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): people whose data is pinned see the pin in Settings: the region, the agreement (their own pin's, or their team's for its owners and admins), whether their computer and its backups are in the region, and whether their plan has an AI model there. They download the residency report on their own pin, and a team's owners and admins the one on the team's pin, as Markdown (`GET /api/me/residency`, `GET /api/me/residency/report`). Reports are audited as admins' are, marked `selfService`, and limited to 5 per person every 10 minutes.
- Refusing startup when a residency pin can't be kept, and keeping leavers' pins ([ADR 0171](docs/adr/0171-residency-startup-and-leavers.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): with `RESIDENCY_STARTUP=refuse` (default `warn`), botd won't start while a pin's region has lost its hosts or backup store, or some of its data is outside it; it logs which pins and why and audits `residency.startup_refused`, and `GET /api/regions` shows the setting. Someone who leaves a pinned team, is removed from it, or is removed by SCIM now keeps the team's pin as their own (same region and reference, `keptFrom` the team), so their remaining machine and backups stay held; it is audited as `user.residency_pin_kept`, shown in reports, and an admin ends it with a reason. An erased person keeps none. In the app and their own report, a kept pin shows the team it came from, not the team's agreement reference. The DPA's residency annex says so.
- botd's own data region for residency ([ADR 0184](docs/adr/0184-botds-own-data-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `SERVER_DATA_REGION` states where botd's database, files and on-host backups are, and `SERVER_BACKUP_S3_DATA_REGION` where server backups' own store is. Residency reports gain a "botd's own data" section and list it as not covered only when it isn't in the pin's region; the app's residency card and `GET /api/regions` show it. With `RESIDENCY_SERVER_DATA=require` (default `report`), every pin is held to botd's own region: botd won't start without it or with server backups copied elsewhere, pins to another region are refused (`server_data_outside`), and older pins elsewhere are warned about or refuse startup under `RESIDENCY_STARTUP=refuse`.
- In-region Claude Code and Codex routes ([ADR 0192](docs/adr/0192-in-region-claude-code-and-codex-routes.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a Claude Code route may name an `anthropic-messages` endpoint from the tiers file, and a Codex route an `openai-responses` one (a new protocol, the Responses API), so a pinned person's Claude Code and Codex Bots take the plan's in-region route instead of being refused. The endpoint's URL and key reach the harness per run, never in its command line or its shell, and outrank the Bot's own settings; held runs also turn off Claude Code's nonessential traffic and WebFetch domain check and Codex's analytics. Such a route needs no harness login. Claude Code and Codex routes take no fallback, and the same model may sit on two providers.
- A leaver's kept residency pin ends by itself once their data is gone ([ADR 0205](docs/adr/0205-ending-a-kept-pin-once-the-data-is-gone.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): once someone who left a pinned team has no machine left that isn't destroyed and no machine backup not yet deleted, the next reconcile pass ends the pin they kept from the team, audited as `user.residency_pin_ended` (reason `data_gone`) and listed in residency reports, without the team's reference in their own. Their data region stays as it was. The app tells them a kept pin ends this way. `RESIDENCY_KEPT_PINS=keep` (default `end`) keeps each one until an admin unpins it, and warns about those that hold nothing; `GET /api/regions` shows the setting.
- `MACHINE_OWN_KERNEL_TIERS`: the tiers whose machines must have a kernel of their own, or `all`; botd won't start with Incus containers for them, and refuses runs on a machine of those tiers that isn't one of its VMs (such as a container left from before a move to Linode), and the substrate view and `botctl machine substrate` show each tier's kernel. A machine's first `machine.enrolled` audit event records its provider, tier and seconds since it was requested. Both come with a proposed evaluation of the managed substrate: Linode VMs, Incus containers, an orchestrator, or a mix by tier, awaiting the owner's decision ([ADR 0120](docs/adr/0120-managed-substrate.md), [#43](https://github.com/CG-Labs/superbot/issues/43)).
- Air-gapped installs: `deploy/offline-bundle.sh` packs the release binaries, the web client, the landing page, the installer's templates, the Compose files and, optionally, the images (each signature-checked before it is saved, with its SBOM) into one bundle with a `SHA256SUMS`; `install.sh --offline <bundle>` installs or upgrades from it with no network (no apt, git, curl, cargo, npm or Let's Encrypt), after checking its SHA-256 or cosign signature and every file in it, refuses an older bundle than the one installed, and serves `--domain` with the operator's certificate (`--tls-cert`, `--tls-key`, also usable online). `offline-bundle.sh load` loads a bundle's images for Compose. A CI job installs and upgrades from real bundles as root with networking off. The license already verifies offline, now guarded by a test ([ADR 0128](docs/adr/0128-air-gapped-self-host.md), [guide](docs/ops/air-gapped.md), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Offline bundles for every release, and registry mirrors: once the docker workflow has published and signed a `v*` tag's images, the `offline` workflow builds x86_64 and aarch64 bundles from that tag's commit on `main`, signs them and attaches them to the release, with no manual run. Bundled images are now OCI archives copied from the registry with skopeo, keeping the digest whose signature was checked (`docker load` still reads them), and `offline-bundle.sh push <bundle> --registry <host/path>` copies them to an internal registry, checks the digest there, and prints Compose's `SUPERBOT_IMAGE` and `SUPERBOT_CADDY_IMAGE` pinned by digest. Making a bundle with images now needs skopeo and jq; image references need a tag ([ADR 0140](docs/adr/0140-release-bundles-and-registry-mirrors.md), [guide](docs/ops/air-gapped.md#registry-mirrors), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Signatures and multi-arch images in registry mirrors: a bundle now carries each signed image's cosign signatures and attestations (on the multi-arch index, its image for the arch and that image's attestation manifest, and the build provenance), and `offline-bundle.sh push <x86_64 bundle> <aarch64 bundle> --registry <host/path>` puts up the release's signed multi-arch index unchanged with both arches' images and every signature, so `cosign verify` and `cosign verify-attestation` work against the mirror, offline with a copied trusted root. Registries with or without the OCI referrers API work. The copying is done by `superbot-oci`, a small Rust tool in the bundle's `bin/` that reads skopeo's and Docker's logins, CAs and `registries.conf`, so `push` no longer needs skopeo. `build --image-key` checks images signed with your own cosign key. Bundles with images now need `superbot-oci` (`cargo build --release --bin superbot-oci`). A CI job signs a two-arch image, bundles it for both arches, pushes both bundles to a registry with networking off and verifies it there with cosign ([ADR 0147](docs/adr/0147-signatures-and-multi-arch-indexes-in-mirrors.md), [guide](docs/ops/air-gapped.md#checking-signatures-in-the-mirror), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Every release's offline bundles checked end to end: `deploy/offline-release-check.sh` checks a release's attached bundles as a customer uses them. Connected, it checks each bundle's signature and SHA-256, that it was built from the tag's commit with binaries for its arch that run on Ubuntu 22.04, and that its images are what ghcr.io's tags name now, signed. With no network and Sigstore's trusted root, it checks that the bundles verify, push to a mirror as the signed multi-arch index, and pass `cosign verify` and `verify-attestation` there. The `offline-release-check` workflow runs it, then installs botd from the x86_64 bundle and loads its images with no network. It runs once a release's bundles are attached, weekly on the latest release, and by hand. Operators can run it themselves before carrying a release in ([ADR 0172](docs/adr/0172-release-bundles-checked-end-to-end.md), [guide](docs/ops/air-gapped.md#checking-a-release-end-to-end), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Harness installs on users' machines from mirrors inside an air-gapped network: `MACHINE_NODE_MIRROR`, `MACHINE_NPM_REGISTRY` and `MACHINE_MIRROR_CA_FILE` point machines at the operator's Node.js and npm mirrors (Artifactory, Nexus, Verdaccio, or plain files laid out as nodejs.org/dist) and the internal CA they're signed by, instead of nodejs.org and npm's registry. The pins don't change: Node.js and each harness are still checked against their pinned SHA-256 and SHA-512, so a mirror can serve them but not change them. `botctl machine mirror` (`GET /api/machines/harness-mirror`, admins) fetches every file the harness plan names from where machines would and checks each pin, before any machine needs it. Agents older than this aren't sent a plan with a registry or CA (`botctl machine upgrade` them first, from botd, with no internet); servers without mirrors send the same plan as before. On Incus, `INCUS_EGRESS_ALLOW` opens exact private `address:port` pairs (TCP only) for mirrors containers' firewall would otherwise drop, and `botctl machine mirror` names any mirror address the machines' firewall (Incus, or Linode's outbound rules) still drops. Hermes Agent's installer still needs GitHub and PyPI. CI installs a package and its dependency with the real npm from a stand-in registry with a CA of its own, as root with networking off, and a real Incus container reaches an allowed port ([ADR 0186](docs/adr/0186-harness-installs-from-internal-mirrors.md), [guide](docs/ops/air-gapped.md#harness-clis-on-users-machines), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Hermes Agent on an air-gapped server ([ADR 0200](docs/adr/0200-hermes-agent-bundle-for-air-gapped-installs.md), [#59](https://github.com/CG-Labs/superbot/issues/59)): `deploy/offline-bundle.sh hermes` packs Hermes Agent at its pinned commit, as its installer leaves it in `/opt/hermes`, into a Hermes bundle; every release attaches a signed one per arch. `install.sh --offline --with-hermes --hermes-bundle <file> [--hermes-bundle-sha256 <hex>]` checks it (SHA-256 or signature, its files, the pinned commit, this arch, only links that stay inside) and swaps it into `/opt/hermes` with no network, putting the previous one back if it doesn't run. An `--upgrade` without `--with-hermes` keeps Hermes, and now says when the release pins another commit. Fixed: with per-user accounts, the online `--with-hermes` install left some of Hermes's files readable by root only, so Bots' accounts couldn't run it.
- Plans: tiers with model routing behind them ([ADR 0033](docs/adr/0033-tiers-model-routing.md)) and fallback across providers ([ADR 0077](docs/adr/0077-two-providers-through-tier-routing.md)); Stripe billing with checkout, the customer portal, token metering, storage limits, resizing on a plan change, billing emails and team plans ([ADR 0093](docs/adr/0093-team-billing.md)); a self-host license key ([ADR 0038](docs/adr/0038-self-host-license-key.md)) and no free tier ([ADR 0068](docs/adr/0068-no-free-tier.md)).
- Operations: Prometheus metrics and structured logs ([ADR 0089](docs/adr/0089-metrics-and-structured-logs.md)), host capacity metrics and a dashboard ([ADR 0106](docs/adr/0106-host-capacity-metrics.md)), a requests-and-runs dashboard, error alert rules and opt-in error reporting to a Sentry-compatible tracker, scrubbed of prompts, chats and secrets ([ADR 0113](docs/adr/0113-service-dashboards-and-error-reporting.md)), recovery objectives and backup alerts for Linode machines ([ADR 0110](docs/adr/0110-linode-machine-recovery-objectives.md)), and a status page with an uptime SLO ([ADR 0090](docs/adr/0090-status-page-and-uptime-slo.md)).
- Compliance: audit events with CSV export, chat history retention with legal holds ([ADR 0098](docs/adr/0098-chat-retention.md)), retention for harness session files and teammates' archived work, on the server and on machines ([ADR 0112](docs/adr/0112-harness-session-and-teammate-files-retention.md)), an access-review report ([ADR 0099](docs/adr/0099-access-review-report.md)), erasing a user's data ([ADR 0102](docs/adr/0102-erasing-a-users-data.md)), deleting a destroyed machine's backups ([ADR 0108](docs/adr/0108-deleting-a-destroyed-machines-backups.md)), and server backups copied off the host to S3-compatible storage, encrypted, with retention, an RPO, alerts and `botctl backups` ([ADR 0109](docs/adr/0109-server-backups-off-the-host.md)).
- Backups encrypted by default: new installs (installer and Compose) make an age key and encrypt server archives and their off-host copies to it, upgrades opt in with `--backup-age-generate`, and plain backups are a startup warning, a setup checklist item, a metric with an alert and an audit event; `SUPERBOT_BACKUP_ENCRYPTION=required` refuses them and `off` keeps them plain by choice ([ADR 0114](docs/adr/0114-backups-encrypted-by-default.md)).
- Opt-in OpenTelemetry traces over OTLP/HTTP (`TRACES_OTLP_ENDPOINT`, off by default): a span per request and per Bot run, with each harness attempt, tool call, approval check and machine call as a child and a Bot's own calls during a run joined to it; trace ids in structured logs and audit events; never a message, prompt, path or secret in a span. Requests and runs also counted by tier in `/metrics`, with no per-user labels ([ADR 0118](docs/adr/0118-harness-run-traces-and-per-tier-metrics.md), [guide](docs/ops/tracing.md)).
- Custom roles: an admin builds a role on member or read-only from six fixed permissions (`users.manage`, `bots.manage`, `audit.view`, `billing.manage`, `signups.approve`, `machines.manage`) and gives it across the server or within a team, through `/api/roles`; the built-in roles are presets of the same permissions and behave as before, unknown permissions grant nothing, holders can never change admins or make them, and every change is audited ([ADR 0123](docs/adr/0123-custom-roles.md), [#53](https://github.com/CG-Labs/superbot/issues/53)).
- Custom roles in the apps: a **Roles** screen in the app and a **Roles** tab in the admin console to build, change and delete roles from the fixed permissions, see what each adds up to, and give them across the server or within a team; a custom role picker and each person's effective permissions in Users (admin user views now carry `permissions`), a custom role column on team members in the console, and `botctl roles` and `botctl role show | add | edit | rm | assign | unassign` ([ADR 0132](docs/adr/0132-custom-roles-in-the-apps.md), [#53](https://github.com/CG-Labs/superbot/issues/53)).
- Service accounts ([ADR 0143](docs/adr/0143-service-accounts.md)): non-human callers for scripts and integrations, through `/api/service-accounts` and `botctl service-account`. Each holds member, read-only (the default) or a custom role, across the server or within a team, and can never be an admin (the database refuses it too). It acts only through `sbsa_` API tokens: shown once and kept as hashes, scoped to permissions it holds, expiring in 1 to 365 days (default 90), rotatable with an optional overlap, and revocable. Every request is capped by what its owner holds now, so a demoted or disabled owner takes it down too; delegates with `users.manage` manage only their own. Service accounts can't sign in or use a person's routes, take no seats, and the audit log names them as the actor (`authMethod: service_token`, with the token's id).
- Service accounts in the apps ([ADR 0152](docs/adr/0152-service-accounts-in-the-apps.md)): a **Service accounts** screen in the app and tab in the admin console, for admins only. Make one (name, role, team, and a first token), see what it can use today and when each token was last used and from where, issue tokens with scopes and an expiry, rotate them with an optional overlap, revoke them, change the role, team or owner, and disable, enable or delete it. A new token's secret is shown once, with Copy, and never again.
- Service accounts in access reviews ([ADR 0165](docs/adr/0165-service-accounts-in-access-reviews.md), [#53](https://github.com/CG-Labs/superbot/issues/53)): the access-review report (`GET /api/access-review`, its CSV, and **Access review** in the app) now lists every service account beside the people. Each shows its owner and whether they still lend it access, its roles, what its tokens can use today, the Bots it reaches, and each live token's scopes, expiry and last use (never the token or the address it was used from). It's flagged when it's disabled, its owner is inactive, or a token has everything it holds or hasn't been used for 90 days. The sign-off digest covers them, so a new token, a wider role or an owner leaving makes a loaded report stale (409). Using a token doesn't. Servers with no service accounts keep their digests. The CSV gets a row per service account and `kind`, `owner`, `effective_permissions`, `service_tokens` and `service_flags` columns before `report_digest`. The monthly evidence bundle's `access-review.json` lists them by id and counts `service_account.*` and `service_token.*` events; its manifest `format` is now 2.
- Service accounts granted Bots ([ADR 0170](docs/adr/0170-service-accounts-granted-bots.md), [#53](https://github.com/CG-Labs/superbot/issues/53)): a Bot's owner or an admin can grant a service account `viewer` or `operator` on the Bot, by its id, with the same routes and `botctl bot grant <bot> <sa> <level>`, so a person's script can use their private Bot without sharing it. A service account now reaches no Bot, and does no more with one, than its owner can on each request, in lists, live streams, runs it asks for and the access review; a grant beyond that is refused (409, `bot.access_refused` with `service_account_owner`). One case reaches less than before: a team's service account whose owner isn't on the team no longer reaches the team's shared Bots. Grants go when it's deleted, moves team, or the Bot's owner leaves its team; changing its owner or team stops runs it asked for on Bots it can no longer use. It never manages or owns a Bot (giving it one is 409) and is never asked to decide approvals. Its views get `refusals`, how often it was refused in the last 30 days by reason, counted from the audit log, and `GET /api/service-accounts/{id}` lists the Bots it reaches. A refused service token's `auth.login_failed` now names its account (target, `serviceAccount`, the token's id as `via`) and is throttled per account.
- A delegate's own service accounts in the app ([ADR 0182](docs/adr/0182-delegates-own-service-accounts.md), [#53](https://github.com/CG-Labs/superbot/issues/53)): anyone whose role holds `users.manage` now gets **Your service accounts** in the app's sidebar. There they make, change, disable and delete the service accounts they own, and issue, rotate and revoke their tokens, without seeing anyone else's or changing an owner. `GET /api/service-accounts` adds `view` (`all` or `own`) and `choices`: the roles allowed across the server, the teams the caller may use with the roles allowed in each, and those roles' names and permissions, all worked out by the same check `POST` makes. The app's forms offer only those, for admins too. A delegate can put a service account only in the team they're on (403, `access.denied` with `limit: "service_account_team"`). A team's service account now counts as one of the team only while its owner is an admin or on that team, so its token no longer reads a team its owner can't (`GET /api/team` is 404 then). Its views get `ownerOnTeam`, and the app flags an account whose owner is off its team.
- Service accounts off their owner's team, in access reviews ([ADR 0188](docs/adr/0188-service-accounts-off-their-team-in-access-reviews.md), [#53](https://github.com/CG-Labs/superbot/issues/53)): each service account in the access review (`GET /api/access-review`) now has `ownerOnTeam`, as on the Service accounts screen. One in a team whose owner is active but neither an admin nor on that team acts in no team (ADR 0182), and is now flagged `owner_off_team`: "Owner off its team" in the app, with "acts in no team" beside its team, and in the CSV's `service_flags` and the evidence bundle's `access-review.json`, which also gets `ownerOnTeam`. The report's digest covers it while it lasts, so an owner leaving the team makes an earlier sign-off stale (409). Reports where every owner is on their account's team keep their digests.
- Time-bound custom roles ([ADR 0197](docs/adr/0197-time-bound-custom-roles.md), [#53](https://github.com/CG-Labs/superbot/issues/53)): giving a custom role by hand, across the server or within a team, now takes an optional end and reason (`PUT /api/roles/:id/users/:user` and `.../teams/:team/users/:user` with `{expiresAt?, reason?}`; `botctl role assign <role> <user> [--team T] [--for 8h|7d] [--reason TEXT]`; an end chooser in **Roles** in the app and the console). The role stops granting anything the moment its end passes, in every session, and a sweep takes it away within a minute, audited as `role.expired`; across the server they keep its base, never admin. It now leaves out `.env` and `.env.*` (but updates `.env.example`), `data/`, `workspace/`, `backups/`, `logs/`, `secrets/`, the usual key and token files, SQLite files, every `*_DIR` and `*_FILE` the install's `.env` points inside its folder (as written, with any link on the way, and as resolved), and botd's default `BACKUP_DIR` beside a moved `DATA_DIR`; a setting pointing at the folder itself stops the installer. The upgrade runbook and `deploy/README.md` say so ([guide](deploy/README.md#from-a-local-checkout)).

### Security

- Secrets sealed under a master key and redacted from output ([ADR 0010](docs/adr/0010-secrets.md)), with safe master key rotation ([ADR 0096](docs/adr/0096-master-key-rotation.md)).
- TOTP second factor with recovery codes ([ADR 0094](docs/adr/0094-totp-second-factor.md)), JIT SSO accounts only from an allow-list ([ADR 0103](docs/adr/0103-sso-jit-needs-an-allow-list.md)), and alerts on suspicious sign-ins ([ADR 0104](docs/adr/0104-suspicious-sign-in-alerts.md)).
- Model providers only over HTTPS ([ADR 0097](docs/adr/0097-model-providers-over-https.md)) and harness sandboxes on by default.
- Supply chain: dependency vulnerability scanning ([ADR 0092](docs/adr/0092-dependency-vulnerability-scanning.md)), GitHub Actions pinned by commit ([ADR 0100](docs/adr/0100-github-actions-pinned-by-commit.md)), and image scanning, signing and provenance ([ADR 0101](docs/adr/0101-image-scanning-and-signing.md)).
- A tamper-evident audit log: every event sealed onto a SHA-256 hash chain (existing events sealed on upgrade), kept whole through erasure and retention (an erased event counts only if an intact `audit.erased` names it); `botctl audit verify` and `GET /api/audit/verify` name the first changed, removed, added or reordered event and check hashes pinned from a SIEM, and botd checks itself daily ([ADR 0122](docs/adr/0122-siem-export-and-tamper-evident-audit.md)).
- Signed and timestamped audit checkpoints: every `AUDIT_CHECKPOINT_MINUTES` (60 by default) botd records an `audit.checkpoint` signing the chain's head with an Ed25519 key derived from the master key (public key at `botctl audit key` and `GET /api/audit/checkpoints/key`), and with `AUDIT_TIMESTAMP_URL` (off by default, any RFC 3161 TSA, free ones included) has each timestamped in the background, retrying with backoff and never holding up audit writes. Both go out with the SIEM export and can be checked with OpenSSL alone. `botctl audit verify` now checks signatures and tokens, over a range (`--from`, `--to`) and against keys you pin (`--key`); `botctl audit chain` (`GET /api/audit/chain`) and a **Chain** panel in the app's audit log show the head, last checkpoint and timestamp, export lag and last check ([ADR 0149](docs/adr/0149-signed-and-timestamped-audit-checkpoints.md), [guide](docs/ops/audit-export.md#checkpoints-and-timestamps), [#56](https://github.com/CG-Labs/superbot/issues/56)).
- A write-once S3 archive of the audit log ([ADR 0154](docs/adr/0154-write-once-s3-audit-archive.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): `AUDIT_EXPORT=s3://<bucket>/<prefix>` (off by default) writes every event, in order and at least once, as JSON-lines objects in batches (`AUDIT_EXPORT_S3_BATCH_SECONDS`, 300 by default, or 10,000 events) to any S3-compatible store, each locked with S3 Object Lock by the bucket's default retention or in compliance or governance mode for `AUDIT_EXPORT_S3_RETAIN_DAYS`. botd refuses a bucket without Object Lock and reads every object's lock back, so a store that doesn't lock is a failing export (`not_write_once`) and retention keeps the events; `botctl audit siem` and the app show the last object and when its lock ends ([guide](docs/ops/audit-export.md#archive-events-to-write-once-s3)).
- Checking the audit archive ([ADR 0163](docs/adr/0163-checking-the-audit-archive.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): `botctl audit verify --archive` (`GET /api/audit/verify?archive=on`) reads every object in the write-once S3 archive, taking the version botd wrote first, and checks keys and metadata, locks, the chain across objects, signed checkpoints, and that the archive begins where botd started it and reaches the last event delivered. Then it holds every archived event's hash to this server's log, so a log rebuilt after an event was changed fails (reason `archive`). A later version that differs (`overwritten`), a gap (`link`), a changed copy of an event still in the log (`contents`), a missing start or tail (`start`, `behind`) and keys botd didn't write (`stray`) are reported; it needs `s3:ListBucketVersions` ([guide](docs/ops/audit-export.md#check-the-archive)).
- An audit archive alongside a SIEM ([ADR 0173](docs/adr/0173-an-archive-alongside-a-siem.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): `AUDIT_EXPORT` takes a SIEM and an S3 archive at once, split by a comma (`https://<siem>/<path>,s3://<bucket>/<prefix>`). Each sink has its own cursor, retries and failure events (now with `kind`), so a SIEM outage doesn't stop the archive; retention waits for both. `botctl audit siem` leads with the sink in the worst state and lists each under `sinks`, the app's audit log shows a line per sink, and the export's metrics gain a `kind` label.
- A daily check of new audit archive objects ([ADR 0183](docs/adr/0183-daily-check-of-new-archive-objects.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): with an S3 archive, botd's daily self-check also checks what was archived since its last pass, so a rebuilt log is caught without anyone running `--archive`. It reads the objects past the head the last pass reached, carrying the chain on from it, and any object the store dates after that pass, so forged copies and new versions over old objects are caught too. It also checks that the head still has the same hash in the log, which catches a log rebuilt from an event already checked. The first daily check reads the whole archive once; after that it's one listing and about one `GET` per new batch. The result is in `audit.verified` (with `after` and `skipped`) and on an `Archive check` line in the app's audit log. `AUDIT_EXPORT_S3_CHECK=off` turns it off. Upgrading: the check needs `s3:ListBucketVersions` on the bucket, which export alone didn't. Without it the daily `audit.verified` fails and names that right, so grant it or turn the check off.
- Several SIEMs, each with its own headers ([ADR 0191](docs/adr/0191-several-siems-with-their-own-headers.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): `AUDIT_EXPORT` takes up to four SIEMs beside the archive, each named (`splunk=https://...,mdr=https://...`). `AUDIT_EXPORT_HEADERS_<NAME>` (or `_FILE`) goes to that webhook only, as a server secret no Bot gets, in the env or Vault, and `AUDIT_EXPORT_START_<NAME>` sets where a new one starts. With several SIEMs, `AUDIT_EXPORT_HEADERS` stops botd, since it would go to all of them. Each SIEM keeps its own cursor (by URL, so naming a running sink resumes it), retries and failure events (with `name`). `botctl audit siem`, the startup summary and the app's audit log name each sink, and the export's metrics gain a `name` label on named sinks. A single unnamed SIEM works as before.
- Exported audit events that check themselves ([ADR 0199](docs/adr/0199-self-checking-audit-lines.md), [#56](https://github.com/CG-Labs/superbot/issues/56)): each exported line now carries `chainDigest`, and `chainSalt` unless the event was erased or redacted on the way out, so its `chainHash` can be worked out from the line alone. They start after a marker saved once (`digestsAfter` in `botctl audit siem`), so resent batches don't change. The archive check catches an archived copy that was changed (`digest`) or stripped of its digest (`unbound`), even after retention deleted the row, and counts `bound`, `boundFixed` and `unbound` lines. `botctl audit verify-lines <file|dir|->... [--key <hex>] [--digests-after <id>]` checks a SIEM export or a copy of the archive with no botd: each line, copies of an event, the chain per host, and signed checkpoints. It exits 1 on any problem.
- Deprovisioning stops a person's work at once: deactivating or deleting them over SCIM, or an admin disabling them, stops every run and queued message on their Bots and the runs on others' Bots that are for them, a run's Bot token acts for no one who is disabled, and their own machine is suspended and held off until they're enabled again (`MACHINE_ON_DISABLE=suspend`, the default, or `keep`), each audited as `user.deprovisioned` ([ADR 0124](docs/adr/0124-deprovisioning-stops-bots-and-machines.md), [#51](https://github.com/CG-Labs/superbot/issues/51)).
- Native SAML 2.0 sign-in: botd is the service provider itself, with no broker. A `saml` provider without `ISSUER` sends an AuthnRequest, publishes SP metadata, and accepts the IdP's HTTP-POST response only when the assertion is signed by a certificate from the IdP's metadata (RSA-SHA256 or stronger) and matches the audience, ACS URL, request, IdP and validity window, once; signature wrapping, DTDs, comments, encrypted assertions and IdP-initiated posts are refused, each audited with its reason. IdP metadata from a URL, a file, or `botctl sso saml <id> import`; `botctl sso saml <id>` shows what to enter at the IdP. Identities are keyed as with the bridge, so links carry over; the just-in-time allow-list and disabled users apply as for OIDC. Guides for Okta and Microsoft Entra ID ([ADR 0127](docs/adr/0127-native-saml-service-provider.md), [guide](docs/sso/saml-native.md), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML signed AuthnRequests and single logout. Each native provider has an SP signing key (made once and sealed, or your own with `SSO_<ID>_SP_CERT_FILE` and `SSO_<ID>_PRIVATE_KEY`) published in the SP metadata with the SLO URL; `SSO_<ID>_SIGN_REQUESTS=true` signs AuthnRequests over the redirect binding. When the IdP has a logout URL, signing out of SuperBot in a browser also signs you out at the IdP, and the IdP's signed LogoutRequests at `/api/auth/sso/<id>/slo` revoke the SuperBot sessions they name; unsigned, misdirected, stale and replayed logout messages are refused. Audited as `auth.slo`, `auth.slo_response`, `auth.slo_failed` and `sso.saml_sp_key_created` ([ADR 0137](docs/adr/0137-saml-signed-requests-and-single-logout.md), [guide](docs/sso/saml-native.md#single-logout), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML encrypted assertions. `SSO_<ID>_ENCRYPTED_ASSERTIONS=allow` (or `require`) takes `EncryptedAssertion`, decrypted with a separate per-provider encryption key (made once and sealed, or your own with `SSO_<ID>_SP_ENCRYPTION_CERT_FILE` and `SSO_<ID>_ENCRYPTION_PRIVATE_KEY`) that the SP metadata publishes. Only AES-GCM content with RSA-OAEP key transport is accepted; AES-CBC, Triple DES and RSA PKCS #1 v1.5 are refused before anything is decrypted, and all decryption failures look the same. The assertion inside must still be signed by the IdP and passes every wrapping and signature check a plain one does. Off by default ([ADR 0150](docs/adr/0150-saml-encrypted-assertions.md), [guide](docs/sso/saml-native.md#encrypted-assertions), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML encrypted NameIDs, ECDSA keys and signed IdP metadata. An `EncryptedID` in an assertion or an IdP LogoutRequest is decrypted with the provider's encryption key (with `ENCRYPTED_ASSERTIONS` on), with the same AES-GCM and RSA-OAEP only rules, and read only after the IdP's signature over it is checked; a subject with two identifiers is refused. IdPs may sign with ECDSA P-256 or P-384 keys (`ecdsa-sha256`, `ecdsa-sha384`, each only with its own curve; SHA-1 refused), and your own SP signing key may be ECDSA. `SSO_<ID>_METADATA_SIGNING_CERT_FILE` (with `SSO_<ID>_SIGNED_METADATA=require|allow`) checks the IdP metadata's signature on every load from a URL, file or import: unsigned (with `require`), badly signed or expired signed metadata is refused, the last good copy stays in use, and each refusal is audited as `sso.saml_metadata_refused` ([ADR 0151](docs/adr/0151-saml-encrypted-nameids-ecdsa-and-signed-metadata.md), [guide](docs/sso/saml-native.md#signed-idp-metadata), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML groups. `SSO_<ID>_GROUPS_ATTRIBUTE` reads the groups in the IdP's signed assertion (no default; exact names; an Entra ID overage or more than 500 values counts as no groups). `SSO_<ID>_REQUIRED_GROUPS` refuses anyone in none of them before just-in-time sign-up, audited as `not_in_group` or `groups_unknown`. Admins map a provider's group to a custom role across the server (`botctl sso role map <provider> <group> <role>`, `/api/sso/role-mappings`): never admin, a built-in role or a role with permissions that reach admins, and a mapped role can't gain them or be deleted. Each sign-in gives the role to people in the group and takes it back from those no longer in it, restoring their earlier built-in role; only what a mapping gave is taken away, a change by hand stands against every provider's groups, and removing the mapping or unlinking the identity takes the role away. Audited as `role.assigned`/`role.unassigned` with `via: saml` and `sso.saml_role_*` ([ADR 0160](docs/adr/0160-saml-groups-and-role-mapping.md), [guide](docs/sso/saml-native.md#groups), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML app tiles. With `SSO_<ID>_IDP_INITIATED=restart`, an unsolicited response from the IdP's portal (the Okta dashboard, Microsoft My Apps, the OneLogin portal) is checked like any other, must answer no request, has its assertion spent, and sends the browser to start an SP-initiated sign-in. It never signs anyone in itself, so a forged or stolen post can't sign a browser in as someone else. An IdP that answers that request unsolicited again is refused as `idp_initiated_loop` rather than looped. Audited as `auth.saml_idp_initiated`; off by default. The guide shows how to point Entra ID and Okta tiles at the start URL instead ([ADR 0175](docs/adr/0175-saml-idp-initiated-sign-in-restarted.md), [guide](docs/sso/saml-native.md#idp-initiated-sign-in-app-tiles), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML key rollover. botd's own SP signing and encryption keys can be replaced with no failed sign-in: `botctl sso saml <id> key next <signing|encryption>` makes a new key and publishes it in the SP metadata beside the one in use (a next encryption key decrypts at once, a next signing key never signs); `promote` puts it in use once the IdP has it, keeping a replaced encryption key decrypting, unpublished, until `retire`; `cancel` drops a next key. `botctl sso saml <id>` shows each stage and when each encryption key last decrypted a sign-in. Keys from `SSO_<ID>_SP_CERT_FILE` and `SSO_<ID>_SP_ENCRYPTION_CERT_FILE` are rolled over in `.env` instead. Admin only; audited as `sso.saml_sp_key_created` (with `stage`), `sso.saml_sp_key_promoted` and `sso.saml_sp_key_retired` ([ADR 0181](docs/adr/0181-saml-sp-key-rollover.md), [guide](docs/sso/saml-native.md#rolling-over-superbots-keys), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML can require the IdP's MFA. `SSO_<ID>_AUTHN_CONTEXT` lists how people must have signed in at the IdP (exact values, comma separated). A sign-in gets in only if the signed assertion's `AuthnContextClassRef`, or a value of the attribute `SSO_<ID>_AUTHN_METHODS_ATTRIBUTE` names (Entra ID's `authnmethodsreferences`, Okta's `session.amr`), is one of them. It's checked on every sign-in before just-in-time sign-up, and a refusal is audited as `authn_context` with what the IdP sent; people are told the sign-in didn't use the method required, such as MFA. `SSO_<ID>_REQUEST_AUTHN_CONTEXT=true` also asks the IdP for those classes in AuthnRequests (`exact`), and an IdP answering `NoAuthnContext` gets the same message. Every native SAML `auth.login` now records `authnContext`. Shown by `botctl sso saml <id>` and `GET /api/sso/:id/saml`; the guide has settings for Entra ID, ADFS, Okta and REFEDS ([ADR 0190](docs/adr/0190-saml-required-authn-context.md), [guide](docs/sso/saml-native.md#require-mfa-at-the-idp), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML warns before its certificates expire: SuperBot's signing and encryption certificates (configured, or generated with their next keys), the IdP's signing certificates and the trusted metadata signers. botd checks them at startup and every hour, reading URL metadata again when its daily refresh is due. It audits each certificate once as `sso.saml_certificate_expiring` 30 days before its end, and once as `sso.saml_certificate_expired` after it, with outcome `failure` when no other certificate replaces it. `botctl sso saml <id>` lists them as certificate warnings with what to do, and shows the days left after each end date. `GET /api/sso/:id/saml` gives `certificateWarnings` and each certificate's `expiry` and `daysLeft`. Signature checks still don't depend on certificate dates ([ADR 0198](docs/adr/0198-saml-certificate-expiry-warnings.md), [guide](docs/sso/saml-native.md#certificates-that-are-ending), [#52](https://github.com/CG-Labs/superbot/issues/52)).

- Per-user machines hardened at first boot, on by default (`MACHINE_HARDENING=off` to opt out): SSH only for root with a key and no forwarding, kernel hardening sysctls, unattended security updates that never reboot by themselves, and egress rules that keep every Bot's and teammate's OS user (even one made later) off private, shared, link-local and cloud metadata addresses and `MACHINE_EGRESS_DENY`, while root and the OS's network daemons pass. Each agent reports every step in its heartbeat; botd audits `machine.hardened`, `machine.hardening_failed` and `machine.reboot_required`, and CI checks the rules as root and on a real Incus host ([ADR 0126](docs/adr/0126-per-user-machine-hardening.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Each Bot run on a user's machine is held to its tier's run limits in a cgroup of its own, on by default (`MACHINE_RUN_LIMITS=off` to opt out): a share of the machine's CPUs and memory, a process cap and an IO weight (`runLimits` in `MACHINE_TIERS`, with safe defaults), so one runaway run can't starve the machine, the agent or other runs. A run killed for memory, refused forks or held back on CPU is audited as `machine.run_limited`. Admins can also set an outbound allow-list for every machine, or for one user's, with `botctl machine egress`, `botctl user egress` or the console: Bots then reach only the listed hosts and networks, on top of the deny rules; runs wait until a machine has it loaded, and every change and load is audited ([ADR 0135](docs/adr/0135-run-limits-and-egress-allow-lists.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Bots on users' machines run as their own unprivileged user by default (`MACHINE_BOT_USER=off` opts out, with a warning at every start), one per person, owner or teammate. Every process run as such a user can't gain privileges again (no sudo, su, setuid programs or file capabilities), keeps its files to itself (umask 077, its own `TMPDIR`), and is killed before the agent when memory runs out; the agent refuses a run user in a privileged group or with a sudo rule; new and rebuilt machines hide other users' processes from runs; and runs through `superbot-run` on one server can't gain privileges either. Upgrading switches each machine over (its agent must be botd's build), and the installer says so. A red-team suite runs as root in CI and checks that cross-person file reads, reading the agent's key and records, privilege escalation, getting past or changing the outbound allow-list, and exhausting the machine are all stopped ([ADR 0145](docs/adr/0145-locked-down-run-users-and-red-team.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- A seccomp filter on every Bot run, login and screen on users' machines, and every run through `superbot-run` on one server: keyrings, eBPF, perf events, userfaultfd, io_uring (ENOSYS, so Node falls back), file handles, the kernel log, and administrators' calls (modules, kexec, reboot, swap, the clock) are refused, and calls through another ABI (i386, x32) kill the process; user namespaces stay open for harness sandboxes. Heartbeats say whether an agent filters runs (`botUser.seccomp` in the machine view), and a new red-team scenario checks each refused call ([ADR 0156](docs/adr/0156-seccomp-filter-per-run.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).

When its hosts are full the team's next machine waits or is refused, never placed on a shared host, so a kernel escape stays within one customer. Dedicating is refused while anyone else's machine is on the host; `botctl machine host share <host> --reason <text>` ends it; both are audited. Existing firewalls get the rules on the reconciler's next pass, with no rebuild, audited as `machine.firewall_updated` with `outbound`; startup and the substrate view say which ([ADR 0179](docs/adr/0179-outbound-rules-at-the-provider.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
