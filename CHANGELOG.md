# Changelog

All notable changes to SuperBot are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The version is `server/Cargo.toml`'s; tagging `v<version>` publishes the images ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)) and a GitHub release with that version's section below as its notes ([ADR 0111](docs/adr/0111-changelog-and-github-releases.md)).

Add each user-facing change to the newest section in the PR that makes it. Once that version is tagged, start a `## [Unreleased]` section above it, and rename it to the next version, with `server/Cargo.toml` bumped to match, before tagging that one. CI checks the format, that the newest version is `server/Cargo.toml`'s, and that every tag has a dated section (`deploy/release-notes.sh`).

## [0.1.0] - Unreleased

The first release: everything merged to `main` up to the M4 public-launch work ([roadmap](docs/ROADMAP.md)).

### Added

- `botd`, a harness-agnostic Bot server in Rust, with adapters for Claude Code, Codex, Pi and Hermes Agent ([ADR 0011](docs/adr/0011-hermes-agent-backend.md)); Hermes Agent is the default harness on managed tiers ([ADR 0079](docs/adr/0079-hermes-default-for-managed-tiers.md)).
- A computer per Bot: a screen with a browser and desktop apps, shown live ([ADR 0003](docs/adr/0003-computer.md)).
- Bot-to-Bot messaging (`botctl ask`), routines, per-Bot model and reasoning effort, and suggested prompts.
- An Expo client for web, iOS and Android as the single interface, with a minimal admin-only console ([ADR 0027](docs/adr/0027-expo-primary-hermes-default.md), [ADR 0032](docs/adr/0032-console-admin-only.md)), push notifications ([ADR 0080](docs/adr/0080-client-push-notifications.md)) and an optional biometric app lock ([ADR 0078](docs/adr/0078-client-biometric-app-lock.md)).
- A design system for the app and the admin console ([ADR 0335](docs/adr/0335-design-system-for-the-app-and-the-console.md), [UI overhaul](docs/ROADMAP.md#ui-overhaul-grok-bot-aligned)): one set of design tokens (`apps/client/src/tokens.json`: a warm neutral palette with one accent, for light and dark, plus spacing, radii, type, shadows and motion) used by the app and, as CSS custom properties checked in CI (`npm run tokens:check`), by the console. The chat screen and the sidebar are restyled on it and follow the device's light or dark setting: a centred chat column, Bot replies without bubbles, a floating composer with a round send button, a fixed-width sidebar that scrolls Bots and links together, and a greeting in an empty chat. The console follows the browser's light or dark setting. Text meets WCAG AA contrast in both schemes. Other screens stay dark until their slices; nothing behaves differently.
- The app's sign-in on the design system ([ADR 0336](docs/adr/0336-sign-in-on-the-design-system.md), [UI overhaul](docs/ROADMAP.md#ui-overhaul-grok-bot-aligned)): the sign-in screen, its two-factor check and set-up, the recovery codes and the app lock sit in one centred card (edge to edge on phones) and follow the device's light or dark setting. Single sign-on buttons (Microsoft Entra, Google, GitHub, Apple, OIDC and SAML) are outlined pills, with Apple's in its own black (light) or white (dark); fields show focus with the accent; errors are soft cards read out as alerts, and a server that can't be reached is named with what to check instead of "Failed to fetch". Long provider lists scroll on small phones. Sign-in works exactly as before.
- Settings and the admin screens restyled on the design system ([ADR 0337](docs/adr/0337-a-shared-kit-for-settings-and-admin-screens.md), [UI overhaul](docs/ROADMAP.md#ui-overhaul-grok-bot-aligned)): in the app, settings, plan, secrets, team, policy, users, roles, service accounts, the audit log and access review follow the device's light or dark setting, with grouped sections of rounded cards, a consistent header with a back pill, list rows with hairline separators, pill buttons and segmented choices, and on wide windows a list pane beside a centred detail column. They share one kit (`apps/client/components/ui.tsx`). In the console, tables are rounded cards with a quiet header row, the tabs sit on one row, and fields, buttons, tags and modals take the token spacing and type. Nothing behaves differently.
- Installs: a VPS installer and Docker Compose ([ADR 0006](docs/adr/0006-docker-compose.md)), published multi-arch images on GHCR with computer use ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)), an onboarding wizard ([ADR 0034](docs/adr/0034-onboarding-wizard.md)) and a backup and restore tool with a CI drill ([ADR 0030](docs/adr/0030-backup-restore-drill.md)).
- Multi-user: users, server-side sessions and RBAC ([ADR 0012](docs/adr/0012-users-sessions-rbac.md)); sign-in with Microsoft Entra ID, Google, generic OIDC, GitHub, Apple and SAML through a broker; SCIM 2.0 provisioning, with SCIM groups as teams ([ADR 0095](docs/adr/0095-scim-groups-as-teams.md)); shared and private Bots.
- Approvals and a harness permission policy, with an editor, notifications and end-to-end hook tests against the real harness CLIs ([ADR 0007](docs/adr/0007-approvals.md)).
- Per-user isolation: a Unix account per user on one server ([ADR 0037](docs/adr/0037-per-user-unix-accounts.md)), teammates' own accounts and logins, and a token per run ([ADR 0083](docs/adr/0083-per-run-tokens.md)).
- A managed control plane: one machine per user on Linode or as an Incus container ([ADR 0025](docs/adr/0025-control-plane-linode.md), [ADR 0065](docs/adr/0065-incus-container-machines.md)), enrolled over mutual TLS ([ADR 0031](docs/adr/0031-machine-enrollment-mtls.md)), with harness CLIs, logins, screens, off-host backups, restores onto another host and placement by host load.
- Teams with a machine per teammate ([ADR 0087](docs/adr/0087-team-accounts-and-machines.md)).
- UK/EU data regions: a server admin sets a region, such as London (`gb-lon`) or Frankfurt (`de-fra-2`), for a user or a team; their machines are made only there (a Linode in that region, or an Incus host tagged with it) and their off-host backups go to that region's store, with requests, restores and region changes that would put data elsewhere refused and audited; `botctl regions`, `botctl user region`, `botctl team region`, and the console and app show it ([ADR 0117](docs/adr/0117-uk-eu-data-regions.md)).
- Contractual data residency: a server admin pins a user or a team to a data region under an agreement reference (`botctl user|team residency`, the console, or the admin API). The pin is refused while the region has no host or backup store, or any of their data is elsewhere. While it holds, their region can't change, a pinned team takes no member with data elsewhere and can't be deleted, backups go only to a store in the region even with `MACHINE_BACKUP_RESIDENCY=warn`, and restores, moves and lost-host recoveries outside it are refused; every pin, unpin (with a reason) and refusal is audited, and pins that can't be kept are warned about at startup and in `GET /api/regions` ([ADR 0129](docs/adr/0129-contractual-data-residency.md)). The DPA template gains a data residency annex that says plainly what a pin doesn't cover (botd's own data and model calls, with the regions model providers offer), and the security pack a DPIA template for customers.
- In-region model routes for residency pins ([ADR 0139](docs/adr/0139-in-region-model-routes.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a tiers file endpoint may list the data `regions` it processes in. While a user or team is pinned, their Bots' runs (and runs they ask for, through any number of Bots asking Bots) take only a route whose endpoint is marked as in their region and keep only in-region fallbacks. Hermes Agent's side tasks stay on the run's endpoint, and built-in providers' keys are left out. With no such route, including on open tiers and for Claude Code or Codex, the run is refused and audited as `bot.run_refused` (`residency_pinned`); so is a queued run whose people were pinned while it waited. Pinned plans without a route there are warned about at startup and in `GET /api/regions`.
- Residency reports ([ADR 0155](docs/adr/0155-residency-reports.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `botctl user|team residency <key> report` (or `GET /api/users/{key}/residency/report`, `/api/teams/{id}/residency/report`) makes a report on one pin for the customer, as Markdown or JSON: where each covered person's machine, host and backups are and whether all of it is in the region, warnings, the pin's changes, what it refused and how many runs it held to in-region routes in a period (the last 90 days by default), and what it doesn't cover. It is sealed with a SHA-256 digest the customer can check with `jq` and `sha256sum`, and each report is audited as `residency.report_generated`. The DPA's residency annex lists it as evidence.
- Residency in the app ([ADR 0168](docs/adr/0168-residency-in-the-app.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): people whose data is pinned see the pin in Settings: the region, the agreement (their own pin's, or their team's for its owners and admins), whether their computer and its backups are in the region, and whether their plan has an AI model there. They download the residency report on their own pin, and a team's owners and admins the one on the team's pin, as Markdown (`GET /api/me/residency`, `GET /api/me/residency/report`). Reports are audited as admins' are, marked `selfService`, and limited to 5 per person every 10 minutes.
- Refusing startup when a residency pin can't be kept, and keeping leavers' pins ([ADR 0171](docs/adr/0171-residency-startup-and-leavers.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): with `RESIDENCY_STARTUP=refuse` (default `warn`), botd won't start while a pin's region has lost its hosts or backup store, or some of its data is outside it; it logs which pins and why and audits `residency.startup_refused`, and `GET /api/regions` shows the setting. Someone who leaves a pinned team, is removed from it, or is removed by SCIM now keeps the team's pin as their own (same region and reference, `keptFrom` the team), so their remaining machine and backups stay held; it is audited as `user.residency_pin_kept`, shown in reports, and an admin ends it with a reason. An erased person keeps none. In the app and their own report, a kept pin shows the team it came from, not the team's agreement reference. The DPA's residency annex says so.
- botd's own data region for residency ([ADR 0184](docs/adr/0184-botds-own-data-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `SERVER_DATA_REGION` states where botd's database, files and on-host backups are, and `SERVER_BACKUP_S3_DATA_REGION` where server backups' own store is. Residency reports gain a "botd's own data" section and list it as not covered only when it isn't in the pin's region; the app's residency card and `GET /api/regions` show it. With `RESIDENCY_SERVER_DATA=require` (default `report`), every pin is held to botd's own region: botd won't start without it or with server backups copied elsewhere, pins to another region are refused (`server_data_outside`), and older pins elsewhere are warned about or refuse startup under `RESIDENCY_STARTUP=refuse`.
- In-region Claude Code and Codex routes ([ADR 0192](docs/adr/0192-in-region-claude-code-and-codex-routes.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a Claude Code route may name an `anthropic-messages` endpoint from the tiers file, and a Codex route an `openai-responses` one (a new protocol, the Responses API), so a pinned person's Claude Code and Codex Bots take the plan's in-region route instead of being refused. The endpoint's URL and key reach the harness per run, never in its command line or its shell, and outrank the Bot's own settings; held runs also turn off Claude Code's nonessential traffic and WebFetch domain check and Codex's analytics. Such a route needs no harness login. Claude Code and Codex routes take no fallback, and the same model may sit on two providers.
- A leaver's kept residency pin ends by itself once their data is gone ([ADR 0205](docs/adr/0205-ending-a-kept-pin-once-the-data-is-gone.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): once someone who left a pinned team has no machine left that isn't destroyed and no machine backup not yet deleted, the next reconcile pass ends the pin they kept from the team, audited as `user.residency_pin_ended` (reason `data_gone`) and listed in residency reports, without the team's reference in their own. Their data region stays as it was. The app tells them a kept pin ends this way. `RESIDENCY_KEPT_PINS=keep` (default `end`) keeps each one until an admin unpins it, and warns about those that hold nothing; `GET /api/regions` shows the setting.
- Pinned people's chats kept in a store in their region ([ADR 0215](docs/adr/0215-pinned-chats-in-a-store-in-their-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `REGION_DATA_DIRS=<region>=<folder>,...` gives offered regions a folder outside `DATA_DIR`, each holding a SQLite chat store keyed with botd's database key. A Bot's messages are kept in the store of its owner's pin region (their team's, else their own) and moved there or back right after a pin or unpin, on every reconcile pass and at startup, audited as `residency.chats_moved`. Moves commit the copy before deleting the original, so a crash never loses a message. botd won't start with a recorded store missing or swapped, or a dropped one still holding chats or gone (unless named in `REGION_DATA_FORGET`). Chats not in their pin's store make the pin `data_outside`. Each store is backed up daily into its own folder's `backups/` (`REGION_DATA_BACKUPS`, default 7), never into server backups. The residency report has a "Chats" section, listing other stores' backups that still hold moved chats, `GET /api/regions` shows each region's store, and the app tells people their chats are kept in their region.
- Pinned people's routines and approvals kept with their chats ([ADR 0228](docs/adr/0228-routines-and-approvals-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a Bot's routines and the approvals it asked for, with their sealed tool input and the decider's note, are kept in its owner's pin region's chat store and moved with its chat. Ids stay unique across places, moves zero what they delete, store approvals are sealed under the current master key at startup and during rotations, and residency reports, the app and `GET /api/regions` count routines and approvals; any left outside make the pin `data_outside` until reconcile moves them (`routinesMoved`, `approvalsMoved`).
- Clearing moved rows out of regional chat stores' backups ([ADR 0238](docs/adr/0238-clearing-moved-rows-from-store-backups.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): once a Bot's chat, routines and approvals have left a store, the hourly check rewrites that store's earlier backups without them (zeroed, vacuumed, checked, renamed into place under the same name), so they stay restore points for everyone else; each is audited as `residency.chat_store_backups_cleared`, residency reports stop listing them as earlier copies once done, and `GET /api/regions` warns when clearing keeps failing.
- Copying regional chat stores' backups off the host, inside their region ([ADR 0246](docs/adr/0246-copying-store-backups-off-the-host-in-their-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `REGION_DATA_S3_<REGION>_*` gives a region's chat store a bucket in that region, and the hourly check keeps it a mirror of the store's backups (each copy named by the file's SHA-256, optionally age-encrypted, copies of pruned or rewritten backups deleted with every old version), audited as `residency.chat_store_backups_copied`. A move out of a store counts as cleared only once its copies no longer hold the rows either; residency reports and `GET /api/regions` show the copies and warn while copying fails.
- Restoring a regional chat store ([ADR 0256](docs/adr/0256-restoring-a-regional-chat-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `botd chat-store list <region>` shows a store's backups and its bucket's copies, and `botd chat-store restore <region> <backup|newest>`, run with botd stopped, puts one back. The backup is checked to be the store (and a copy against its SHA-256), the rows of Bots kept elsewhere now are taken out, erasures made since are run on it again, and the store it replaces is kept as a backup. Without `--yes` it only says what would come back and what would go. botd audits the restore at its next start as `residency.chat_store_restored`.
- Runs on a computer in the pin's region ([ADR 0267](docs/adr/0267-runs-on-a-computer-in-the-pins-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): while anyone a run carries (the Bot's owner, the asker, or someone carried through Bots asking Bots) is pinned, it takes place only on a computer in their region: botd's own server only when `SERVER_DATA_REGION` says botd is there, and the owner's machine only when its region and its host's are. Otherwise it is refused, not counted, said in the chat and audited as `bot.run_refused` (`residency_pinned`, `runsOn`). Admins are warned at startup and in `GET /api/regions` about pinned people whose Bots run on botd's server outside their region; residency reports gain each person's `runs` and a "Bots run on" column, and `GET /api/me/residency` and Settings say where your Bots run. With pins, routing off and no matching `SERVER_DATA_REGION`, pinned people's runs are refused after upgrading.
- Bots' memory in the regional store ([ADR 0276](docs/adr/0276-bots-memory-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a pinned person's Bots' memory is kept in their region's chat store with their chats, routines and approvals, not in `DATA_DIR/bots/<id>/MEMORY.md`. A pin, startup and every reconcile pass move it from its file into the store (audited with `memories` in `residency.chats_moved`), and an unpin writes it back. It is covered by the store's encryption, backups, off-host copies, backup clearing and restore. Reports, `GET /api/regions` and the app count it, and a memory file left in `DATA_DIR` makes the pin `data_outside` until the next pass. Owners' facts (`USER.md`) stay where botd runs for now.
- Owners' facts in the regional store ([ADR 0277](docs/adr/0277-owners-facts-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a pinned person's facts (`USER.md`) are kept in their region's chat store, not in `DATA_DIR/users/<id>/USER.md`. They move with the pin like Bots' memory (audited with `facts` in `residency.chats_moved`, `factsMoved` from reconcile), as rows keyed by person through backup clearing, restore and erasure. Reports, `GET /api/regions` and the app count them, and a facts file left in `DATA_DIR` makes the pin `data_outside` until the next pass.
- Sign-ins in the regional store ([ADR 0283](docs/adr/0283-sign-ins-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a pinned person's sign-in sessions, with the IP address and browser of each device, their native SAML sign-ins and their push devices are kept in their region's chat store, not in botd's own database. They move together with the pin on each pass, audited with `sessions`, `samlSessions` and `pushDevices`, and are cleared from the store's backups once they leave. Push tokens in a store are sealed under the master key at startup. A restore takes sign-ins from the store it replaces (or drops them if it is missing), so a session revoked since never works again. Reports, `GET /api/regions` and the app count them. Nobody is signed out on upgrade.
- Own secrets in the regional store ([ADR 0293](docs/adr/0293-own-secrets-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): the API keys and tokens a pinned person saved for their own Bots are kept in their region's chat store, not in botd's own database. They move with the pin on each pass, audited with `personalKeys`, and are cleared from the store's backups once they leave. The secrets' own connection attaches the stores, so a new secret goes to the pin's store and changes and deletes reach every copy. Secrets in a store are sealed under the master key at startup. A restore takes them from the store it replaces, so a secret deleted or changed since stays so; with the store gone, the backup's are kept. Reports, `GET /api/regions` and the app count them. No Bot loses a key on upgrade.
- Second factors in the regional store ([ADR 0299](docs/adr/0299-second-factors-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a pinned person's TOTP secret and recovery codes are kept in their region's chat store, not in botd's own database. They move with the pin on each pass, audited with `secondFactors` and `recoveryCodes`, and are cleared from the store's backups once they leave. Enrolment writes to the pin's store; confirming, spending a code, new codes and turning it off reach every copy. They are sealed under the master key at startup, and a rotation that renews derived keys drops their recovery codes, as it does botd's own. A restore takes them from the store it replaces, so a factor turned off or a code spent since stays so; with the store gone, the backup's are kept, and the restore is refused while someone kept in it has none in the backup, unless `--second-factors-from-backup` is added. Reports, `GET /api/regions` and the app count them. Nobody sets theirs up again on upgrade.
- Model usage records in the regional store ([ADR 0304](docs/adr/0304-usage-records-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): a pinned person's per-run usage records (Bot, run, model, tokens, when, and whether Stripe's meter has them) are kept in their region's chat store, not in botd's own database. They move with the pin on each pass, ids and meter state intact, audited with `usageRecords`, and are cleared from the store's backups once they leave. New ones are written to the pin's store with ids no place repeats; quotas, the usage page and the meter read them across places, and marking one sent reaches every copy, so none is sent twice. A restore takes them from the store it replaces; with the store gone, the backup's are kept and those still waiting for the meter are marked failed rather than sent again, and the result says how many. Reports, `GET /api/regions` and the app count them.
- Audit details in the regional store ([ADR 0316](docs/adr/0316-audit-details-in-the-regional-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): the details of a pinned person's audit events (who, IP address, browser, session and what changed) and their salts are kept in their region's chat store, while botd's log keeps each event's sealed row with `{"inChatStore":"<region>"}` in its details. The audit page, filters, verification, the SIEM export and the archive read them back, so the log is still one chain that verifies. They move with the pin, audited with `auditEvents`, and go back into botd's log when unpinned; erasure and retention reach them where they are kept. Events whose details only a forgotten or lost store held are named as erased (`audit.erased`), so the log still verifies, and a restore says how many. Reports, `GET /api/regions` and the app count them.
- Events about a pinned person in their store ([ADR 0321](docs/adr/0321-events-about-a-pinned-person-in-their-store.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): an audit event's details are kept for the first of its people held in a region with a chat store (the user who acted, the one a Bot acted for, then the one it is about), so what an admin who isn't pinned does about a pinned person (their pin, role changes, their residency reports) is kept in that person's region. Each reconcile pass decides it again, so the details follow whichever of the event's people is held, back into botd's log when none is; a store's backups are cleared of details by whether the store still holds them, and a restore with the store gone keeps only those botd's log says it holds. The app says so (`auditAbout` in `GET /api/me/residency`).
- Audit export held to a pin's region ([ADR 0330](docs/adr/0330-audit-export-held-to-a-pins-region.md), [#58](https://github.com/CG-Labs/superbot/issues/58)): `AUDIT_EXPORT_DATA_REGION` (or a named sink's `AUDIT_EXPORT_DATA_REGION_<NAME>`) states where each SIEM or archive keeps what it gets. A sink outside a pinned person's region gets the events whose details their region's chat store keeps as sealed rows, details held back, which still give their hash, so the chain, `botctl audit verify-lines` and the archive check all hold; an archive retry holds back the same events. `botctl audit siem` shows each sink's `dataRegion` and `heldBack`, the archive check counts `heldBack`, and a pin's residency report has an "Audit export" section and names the sinks that get their events whole outside the region.
- `MACHINE_OWN_KERNEL_TIERS`: the tiers whose machines must have a kernel of their own, or `all`; botd won't start with Incus containers for them, and refuses runs on a machine of those tiers that isn't one of its VMs (such as a container left from before a move to Linode), and the substrate view and `botctl machine substrate` show each tier's kernel. A machine's first `machine.enrolled` audit event records its provider, tier and seconds since it was requested. Both come with a proposed evaluation of the managed substrate: Linode VMs, Incus containers, an orchestrator, or a mix by tier, awaiting the owner's decision ([ADR 0120](docs/adr/0120-managed-substrate.md), [#43](https://github.com/CG-Labs/superbot/issues/43)).
- Air-gapped installs: `deploy/offline-bundle.sh` packs the release binaries, the web client, the landing page, the installer's templates, the Compose files and, optionally, the images (each signature-checked before it is saved, with its SBOM) into one bundle with a `SHA256SUMS`; `install.sh --offline <bundle>` installs or upgrades from it with no network (no apt, git, curl, cargo, npm or Let's Encrypt), after checking its SHA-256 or cosign signature and every file in it, refuses an older bundle than the one installed, and serves `--domain` with the operator's certificate (`--tls-cert`, `--tls-key`, also usable online). `offline-bundle.sh load` loads a bundle's images for Compose. A CI job installs and upgrades from real bundles as root with networking off. The license already verifies offline, now guarded by a test ([ADR 0128](docs/adr/0128-air-gapped-self-host.md), [guide](docs/ops/air-gapped.md), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Offline bundles for every release, and registry mirrors: once the docker workflow has published and signed a `v*` tag's images, the `offline` workflow builds x86_64 and aarch64 bundles from that tag's commit on `main`, signs them and attaches them to the release, with no manual run. Bundled images are now OCI archives copied from the registry with skopeo, keeping the digest whose signature was checked (`docker load` still reads them), and `offline-bundle.sh push <bundle> --registry <host/path>` copies them to an internal registry, checks the digest there, and prints Compose's `SUPERBOT_IMAGE` and `SUPERBOT_CADDY_IMAGE` pinned by digest. Making a bundle with images now needs skopeo and jq; image references need a tag ([ADR 0140](docs/adr/0140-release-bundles-and-registry-mirrors.md), [guide](docs/ops/air-gapped.md#registry-mirrors), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Signatures and multi-arch images in registry mirrors: a bundle now carries each signed image's cosign signatures and attestations (on the multi-arch index, its image for the arch and that image's attestation manifest, and the build provenance), and `offline-bundle.sh push <x86_64 bundle> <aarch64 bundle> --registry <host/path>` puts up the release's signed multi-arch index unchanged with both arches' images and every signature, so `cosign verify` and `cosign verify-attestation` work against the mirror, offline with a copied trusted root. Registries with or without the OCI referrers API work. The copying is done by `superbot-oci`, a small Rust tool in the bundle's `bin/` that reads skopeo's and Docker's logins, CAs and `registries.conf`, so `push` no longer needs skopeo. `build --image-key` checks images signed with your own cosign key. Bundles with images now need `superbot-oci` (`cargo build --release --bin superbot-oci`). - Native SAML sessions end with the IdP's, and can require a recent sign-in. A session made from an assertion with `SessionNotOnOrAfter` now ends then (or at `SESSION_MAX_AGE`, if sooner), for web and app sign-ins; this is on by default, a change for IdPs that send it, and `SSO_<ID>_IDP_SESSION_LIMIT=off` restores the old behaviour. `SSO_<ID>_MAX_AUTHN_AGE` (5m to 365d) sends a sign-in older than that back to the IdP once with `ForceAuthn`, and `SSO_<ID>_FORCE_AUTHN=true` asks every time. `AuthnInstant` is read only from the signed assertion and checked, so an IdP that ignores `ForceAuthn` is refused (`stale_authn` or `idp_session_ended`; people see `sso_reauth_required`) rather than letting an old session through. Each retry is audited as `auth.saml_reauthn`, `auth.login` records `authnInstant`, `idpSessionEnds` and `forceAuthn`, and `GET /api/sso/:id/saml` and `botctl sso saml <id>` show the settings ([ADR 0225](docs/adr/0225-saml-session-lifetime-and-reauthentication.md), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML AuthnRequests over HTTP-POST. An IdP whose metadata offers only an HTTP-POST `SingleSignOnService` now works with no setting (botd used to refuse its metadata): the browser gets a page that posts the AuthnRequest to the IdP, which loads nothing, runs only its own script (allowed by hash), posts only to https and sends no Referer. `SSO_<ID>_REQUEST_BINDING=post` uses HTTP-POST even when the IdP offers HTTP-Redirect too, and `redirect` keeps the old behaviour; `auto`, the default, still prefers HTTP-Redirect. Signed AuthnRequests over HTTP-POST carry an enveloped XML signature with the same SP key. `botctl sso saml <id>` shows the binding in use ([ADR 0235](docs/adr/0235-saml-authn-requests-over-http-post.md)).
- Native SAML single logout over HTTP-POST. An IdP whose metadata lists only an HTTP-POST `SingleLogoutService` now gets single logout with no setting: signing out of SuperBot in a browser answers with a one-time link (five minutes) to a botd page that posts the signed LogoutRequest to the IdP, so clients don't change, and the IdP's own LogoutRequests, which botd used to refuse as `no_slo`, are answered with a signed LogoutResponse posted back. HTTP-Redirect is still used when the IdP lists both, unless `SSO_<ID>_REQUEST_BINDING=post`. `botctl sso saml <id>` says `Single logout: yes, over HTTP-POST`, and `auth.slo_response` now records the binding the IdP's answer came by ([ADR 0248](docs/adr/0248-saml-logout-over-http-post.md), [guide](docs/sso/saml-native.md#logout-over-http-post), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML back-channel logout when an admin or SCIM ends sessions. Revoking a session or all of someone's sessions, disabling or erasing them, or SCIM deactivating or deleting them now also ends their IdP sessions when the IdP's metadata has a SOAP logout URL, with no setting: botd sends a signed LogoutRequest for each still-live session the IdP vouched for, once per IdP session, in the background, so the admin never waits and a stolen browser can't sign straight back in through the IdP. Answers are audited as `auth.slo_response` with `revokeReason`, and `session.revoked`, `session.revoked_all`, `user.disabled` and `scim.user_deleted` list the requests in `idpLogouts` ([ADR 0258](docs/adr/0258-saml-back-channel-logout-on-revoke-and-deprovisioning.md), [guide](docs/sso/saml-native.md#when-an-admin-or-scim-ends-sessions), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML responses over the HTTP-Artifact binding. With `SSO_<ID>_RESPONSE_BINDING=artifact` (default `post`), AuthnRequests and SP metadata ask for HTTP-Artifact, the IdP sends the browser back to the ACS with only an artifact (by redirect or post), and botd fetches the response from the IdP's SOAP ArtifactResolutionService with a signed ArtifactResolve, so the assertion never passes through the browser. Only the IdP's own artifacts for an endpoint its metadata lists are sent, each once; the ArtifactResponse must answer that request and be fresh, and the Response inside is held to every check a posted one is. A provider takes only its one binding (`wrong_binding`), and metadata without an ArtifactResolutionService is refused for it. `auth.login` records `responseBinding`, and `botctl sso saml <id>` shows the binding and the IdP's artifact resolution URLs ([ADR 0268](docs/adr/0268-saml-artifact-binding.md), [guide](docs/sso/saml-native.md#responses-over-http-artifact), [#52](https://github.com/CG-Labs/superbot/issues/52)).
- Native SAML metadata from a federation's signed aggregate ([ADR 0301](docs/adr/0301-saml-federation-aggregates.md), [guide](docs/sso/saml-native.md#a-federations-aggregate), [#52](https://github.com/CG-Labs/superbot/issues/52)). `SSO_<ID>_IDP_AGGREGATE_URL` reads the aggregate a federation without an MDQ server publishes (InCommon's is 60 MB, eduGAIN's about 100 MB) for one IdP or every IdP in `IDP_ENTITY_IDS`, as it downloads and in a few MB of memory: gzipped, asked with its `ETag`, its root signature checked against `METADATA_SIGNING_CERT_FILE` (required) over a streaming canonical form, and only the listed IdPs kept, each read a second time and used only if both readings agree. Once a day for all of a provider's IdPs, in the background; an IdP the federation drops loses its copy, and a refused aggregate keeps the last good copies and is audited as `sso.saml_metadata_refused`.
- Every SAML IdP of a federation, without a list ([ADR 0308](docs/adr/0308-saml-every-idp-of-a-federation.md), [guide](docs/sso/saml-native.md#every-idp-of-a-federation), [#52](https://github.com/CG-Labs/superbot/issues/52)). `SSO_<ID>_IDP_ENTITY_IDS=all` with `IDP_AGGREGATE_URL` takes every SAML 2.0 IdP in the federation's signed aggregate, up to 10,000, following joins and leaves at each daily read; `IDP_ENTITY_CATEGORIES` keeps only IdPs with given entity categories (REFEDS R&S, Sirtfi). The chooser becomes a script-free search by name, entity ID or email domain that leaves out `hide-from-discovery` IdPs, and `botctl sso saml` counts the IdPs instead of listing them.
- A federation's discovery service picks the native SAML IdP ([ADR 0314](docs/adr/0314-saml-discovery-service.md), [guide](docs/sso/saml-native.md#a-federations-discovery-service), [#52](https://github.com/CG-Labs/superbot/issues/52)). With several IdPs, `SSO_<ID>_DISCOVERY_URL` (like SeamlessAccess's `https://service.seamlessaccess.org/ds/`) sends the browser there instead of SuperBot's chooser, as the Identity Provider Discovery Service Protocol says, to come back to `/api/auth/sso/<id>/discovery` with the sign-in's own parameters; the IdP picked is checked as the chooser's is (`unknown_idp`), a service that sends people back with no pick gets SuperBot's chooser, and SP metadata with several IdPs names that URL as its `idpdisc:DiscoveryResponse`, which `botctl sso saml` and its API show.
- SAML people named by subject-id or pairwise-id ([ADR 0319](docs/adr/0319-saml-subject-identifier-attributes.md), [guide](docs/sso/saml-native.md#subject-identifiers-subject-id-and-pairwise-id), [#52](https://github.com/CG-Labs/superbot/issues/52)). `SSO_<ID>_SUBJECT=subject-id` or `pairwise-id` takes the OASIS Subject Identifier attribute as the person instead of the NameID, so federation IdPs that send only transient NameIDs can sign people in. It must be in the signed assertion once, with one value like `8f2a91c4@uni.example`, at one of the IdP's `shibmd:Scope`s; otherwise the sign-in fails as `no_subject_id`, `bad_subject_id` or `subject_id_scope`, never falling back to the NameID. The NameID is still required, kept only for single logout, which matches sessions by it exactly. SP metadata asks for the attribute (`urn:oasis:names:tc:SAML:profiles:subject-id:req`) with a transient NameIDFormat; links and SCIM `externalId`s must be in the attribute's syntax; `auth.login` carries `subjectFrom`, `auth.slo` the `nameId`; `botctl sso saml` shows what people are known by and the IdP's scopes.
- SAML SP metadata a federation can register ([ADR 0323](docs/adr/0323-saml-sp-metadata-for-federation-registration.md), [guide](docs/sso/saml-native.md#registering-superbot-with-a-federation), [#52](https://github.com/CG-Labs/superbot/issues/52)). `SSO_<ID>_SP_DISPLAY_NAME`, `SP_DESCRIPTION`, `SP_INFORMATION_URL` and `SP_PRIVACY_URL` publish `mdui:UIInfo`; `SP_ORGANIZATION` and `SP_ORGANIZATION_URL` an `md:Organization`; `SP_CONTACT_TECHNICAL`, `_SUPPORT`, `_ADMINISTRATIVE` and `_SECURITY` the contacts, the last as the REFEDS security contact; `SP_SIRTFI=v1|v2` the Sirtfi assertion, with a security contact. With a display name, an `AttributeConsumingService` lists the attributes botd reads, required when sign-in needs them. Entity categories stay the federation's to add: the admin API's `about` and `botctl sso saml` show what Research and Scholarship and the Code of Conduct v2 still need. Unset, the metadata is unchanged.
- Native SAML can require identity assurance from the IdP ([ADR 0328](docs/adr/0328-saml-required-identity-assurance.md), [guide](docs/sso/saml-native.md#require-identity-assurance-refeds-raf), [#52](https://github.com/CG-Labs/superbot/issues/52)). `SSO_<ID>_ASSURANCE` lists values the signed assertion's `eduPersonAssurance` (or `ASSURANCE_ATTRIBUTE`) must all hold, like REFEDS RAF's `IAP/medium` and `ID/unique`, with RAF's own `https://refeds.org/assurance` added to RAF values; exact, no levels inferred. Checked on every sign-in after MFA and before just-in-time sign-up, refused as `assurance` with what the IdP sent and lacked (`sso_assurance_required` for the person); `auth.login` records `assurance`; the SP metadata asks for the attribute, required; `botctl sso saml <id>` shows it.
- Chromium's sandbox on inside the container ([ADR 0107](docs/adr/0107-chromium-sandbox-in-the-container.md)).
- Per-user machines hardened at first boot, on by default (`MACHINE_HARDENING=off` to opt out): SSH only for root with a key and no forwarding, kernel hardening sysctls, unattended security updates that never reboot by themselves, and egress rules that keep every Bot's and teammate's OS user (even one made later) off private, shared, link-local and cloud metadata addresses and `MACHINE_EGRESS_DENY`, while root and the OS's network daemons pass. Each agent reports every step in its heartbeat; botd audits `machine.hardened`, `machine.hardening_failed` and `machine.reboot_required`, and CI checks the rules as root and on a real Incus host ([ADR 0126](docs/adr/0126-per-user-machine-hardening.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Each Bot run on a user's machine is held to its tier's run limits in a cgroup of its own, on by default (`MACHINE_RUN_LIMITS=off` to opt out): a share of the machine's CPUs and memory, a process cap and an IO weight (`runLimits` in `MACHINE_TIERS`, with safe defaults), so one runaway run can't starve the machine, the agent or other runs. A run killed for memory, refused forks or held back on CPU is audited as `machine.run_limited`. Admins can also set an outbound allow-list for every machine, or for one user's, with `botctl machine egress`, `botctl user egress` or the console: Bots then reach only the listed hosts and networks, on top of the deny rules; runs wait until a machine has it loaded, and every change and load is audited ([ADR 0135](docs/adr/0135-run-limits-and-egress-allow-lists.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Bots on users' machines run as their own unprivileged user by default (`MACHINE_BOT_USER=off` opts out, with a warning at every start), one per person, owner or teammate. Every process run as such a user can't gain privileges again (no sudo, su, setuid programs or file capabilities), keeps its files to itself (umask 077, its own `TMPDIR`), and is killed before the agent when memory runs out; the agent refuses a run user in a privileged group or with a sudo rule; new and rebuilt machines hide other users' processes from runs; and runs through `superbot-run` on one server can't gain privileges either. Upgrading switches each machine over (its agent must be botd's build), and the installer says so. A red-team suite runs as root in CI and checks that cross-person file reads, reading the agent's key and records, privilege escalation, getting past or changing the outbound allow-list, and exhausting the machine are all stopped ([ADR 0145](docs/adr/0145-locked-down-run-users-and-red-team.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- A seccomp filter on every Bot run, login and screen on users' machines, and every run through `superbot-run` on one server: keyrings, eBPF, perf events, userfaultfd, io_uring (ENOSYS, so Node falls back), file handles, the kernel log, and administrators' calls (modules, kexec, reboot, swap, the clock) are refused, and calls through another ABI (i386, x32) kill the process; user namespaces stay open for harness sandboxes. Heartbeats say whether an agent filters runs (`botUser.seccomp` in the machine view), and a new red-team scenario checks each refused call ([ADR 0156](docs/adr/0156-seccomp-filter-per-run.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Incus hosts can be dedicated to one team (`botctl machine host dedicate <host> <team-id> [--reason <text>]`, server admins only): only that team's machines go there, and its machines go only on its hosts, for new machines, retries, restores onto another host and a lost host's recovery. When its hosts are full the team's next machine waits or is refused, never placed on a shared host, so a kernel escape stays within one customer. Dedicating is refused while anyone else's machine is on the host; `botctl machine host share <host> --reason <text>` ends it; both are audited. Machines a team change leaves on the wrong host are listed in `botctl machine hosts`, warned about at startup, counted on `/metrics` (`superbot_incus_machines_misplaced`) and alerted ([ADR 0166](docs/adr/0166-incus-hosts-dedicated-to-a-team.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Linode machines' Cloud Firewall now also drops outbound TCP and UDP from the whole machine, root included, to the same deny list as the rules inside it (private, shared and link-local ranges and `MACHINE_EGRESS_DENY`), letting botd's machine port through first when botd is on one of those addresses. On by default with `MACHINE_FIREWALL=on`; `MACHINE_FIREWALL_EGRESS=off` keeps outbound open at the provider (refused with Incus, whose network ACL always does this). Existing firewalls get the rules on the reconciler's next pass, with no rebuild, audited as `machine.firewall_updated` with `outbound`; startup and the substrate view say which ([ADR 0179](docs/adr/0179-outbound-rules-at-the-provider.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Teams can have a network of their own on Linode (`MACHINE_TEAM_NETWORK=vpc`, off by default, needs `MACHINE_FIREWALL=on`): each team gets a VPC per region, and its members' new machines join its subnet (`MACHINE_TEAM_NETWORK_SUBNET`, default `10.248.0.0/22`) from their first boot. The firewall's and the machines' own outbound rules let that subnet through for every user, and inbound stays dropped, so a team's machines reach the services the operator puts on its VPC, but not each other or any other team's network. A machine whose owner leaves the team is suspended, taken off the VPC and resumed by the reconciler. Audited as `machine.team_network_created`, `machine.team_network_leaving` and `machine.team_network_left` ([ADR 0189](docs/adr/0189-a-network-of-its-own-per-team.md)).
- Existing Linode machines now join their team's network without a rebuild, when team networks are turned on or their owner joins a team. The machine's agent first lets the team's subnet through its own egress rules (`PUT /v1/team-network`), then the reconciler gives the machine a VPC interface for its next boot. `MACHINE_TEAM_NETWORK_JOIN` waits for that boot (`next-boot`, the default), powers the machine off and on once it runs nothing (`when-idle`), or leaves joining to rebuilds (`off`). Audited as `machine.team_network_joining`, `machine.team_network_restarting`, `machine.team_network_joined`, `machine.team_network_rules_loaded` and `machine.team_network_rules_failed` ([ADR 0202](docs/adr/0202-existing-machines-join-their-teams-network.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- Teams can have a network of their own on Incus too (`MACHINE_TEAM_NETWORK=ovn`, off by default): each team gets an isolated OVN network per region on each host, with no uplink, no NAT and no gateway, named in the restricted project's network access list. Incus plugs the NIC into running containers and unplugs it, so existing containers join at once and a leaver is unplugged without a restart. Containers made before this release can't bring the NIC up and are refused until rebuilt; `botctl machine rebuild` now takes them even when their agent upgrades itself. botd refuses a subnet meeting its own address, `INCUS_EGRESS_ALLOW`, `INCUS_EGRESS_DENY` or an Incus host, and the admin check needs `network_ovn_isolated`, `backup_override_config` (Incus 6.17) and a bridge on another range.
