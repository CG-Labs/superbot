# Changelog

All notable changes to SuperBot are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The version is `server/Cargo.toml`'s; tagging `v<version>` publishes the images ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)) and a GitHub release with that version's section below as its notes ([ADR 0111](docs/adr/0111-changelog-and-github-releases.md)).

Add each user-facing change to the newest section in the PR that makes it. Once that version is tagged, start a `## [Unreleased]` section above it, and rename it to the next version, with `server/Cargo.toml` bumped to match, before tagging that one. CI checks the format, that the newest version is `server/Cargo.toml`'s, and that every tag has a dated section (`deploy/release-notes.sh`).

## [0.1.0] - Unreleased

The first release: everything merged to `main` up to the M4 public-launch work ([roadmap](docs/ROADMAP.md)).

### Added

- `botd`, a harness-agnostic Bot server in Rust, with adapters for Claude Code, Codex, Pi and Hermes Agent ([ADR 0011](docs/adr/0011-hermes-agent-backend.md)); Hermes Agent is the default harness on managed tiers ([ADR 0079](docs/adr/0079-hermes-default-for-managed-tiers.md)).
- A computer per Bot: a screen with a browser and desktop apps, shown live ([ADR 0003](docs/adr/0003-computer.md)).
- Bot-to-Bot messaging (`botctl ask`), routines, per-Bot model and reasoning effort, and suggested prompts.
- An Expo client for web, iOS and Android as the single interface, with a minimal admin-only console ([ADR 0027](docs/adr/0027-expo-primary-hermes-default.md), [ADR 0032](docs/adr/0032-console-admin-only.md)), push notifications ([ADR 0080](docs/adr/0080-client-push-notifications.md)) and an optional biometric app lock ([ADR 0078](docs/adr/0078-client-biometric-app-lock.md)).
- Installs: a VPS installer and Docker Compose ([ADR 0006](docs/adr/0006-docker-compose.md)), published multi-arch images on GHCR with computer use ([ADR 0084](docs/adr/0084-published-image-with-computer-use.md)), an onboarding wizard ([ADR 0034](docs/adr/0034-onboarding-wizard.md)) and a backup and restore tool with a CI drill ([ADR 0030](docs/adr/0030-backup-restore-drill.md)).
- Multi-user: users, server-side sessions and RBAC ([ADR 0012](docs/adr/0012-users-sessions-rbac.md)); sign-in with Microsoft Entra ID, Google, generic OIDC, GitHub, Apple and SAML through a broker; SCIM 2.0 provisioning, with SCIM groups as teams ([ADR 0095](docs/adr/0095-scim-groups-as-teams.md)); shared and private Bots.
- Approvals and a harness permission policy, with an editor, notifications and end-to-end hook tests against the real harness CLIs ([ADR 0007](docs/adr/0007-approvals.md)).
- Per-user isolation: a Unix account per user on one server ([ADR 0037](docs/adr/0037-per-user-unix-accounts.md)), teammates' own accounts and logins, and a token per run ([ADR 0083](docs/adr/0083-per-run-tokens.md)).
- A managed control plane: one machine per user on Linode or as an Incus container ([ADR 0025](docs/adr/0025-control-plane-linode.md), [ADR 0065](docs/adr/0065-incus-container-machines.md)), enrolled over mutual TLS ([ADR 0031](docs/adr/0031-machine-enrollment-mtls.md)), with harness CLIs, logins, screens, off-host backups, restores onto another host and placement by host load.
- Teams with a machine per teammate ([ADR 0087](docs/adr/0087-team-accounts-and-machines.md)).
- UK/EU data regions: a server admin sets a region, such as London (`gb-lon`) or Frankfurt (`de-fra-2`), for a user or a team; their machines are made only there (a Linode in that region, or an Incus host tagged with it) and their off-host backups go to that region's store, with requests, restores and region changes that would put data elsewhere refused and audited; `botctl regions`, `botctl user region`, `botctl team region`, and the console and app show it ([ADR 0117](docs/adr/0117-uk-eu-data-regions.md)).
- Contractual data residency: a server admin pins a user or a team to a data region under an agreement reference (`botctl user|team residency`, the console, or the admin API). The pin is refused while the region has no host or backup store, or any of their data is elsewhere. While it holds, their region can't change, a pinned team takes no member with data elsewhere and can't be deleted, backups go only to a store in the region even with `MACHINE_BACKUP_RESIDENCY=warn`, and restores, moves and lost-host recoveries outside it are refused; every pin, unpin (with a reason) and refusal is audited, and pins that can't be kept are warned about at startup and in `GET /api/regions` ([ADR 0129](docs/adr/0129-contractual-data-residency.md)). The DPA template gains a data residency annex that says plainly what a pin doesn't cover (botd's own data and model calls, with the regions model providers offer), and the security pack a DPIA template for customers.
- `MACHINE_OWN_KERNEL_TIERS`: the tiers whose machines must have a kernel of their own, or `all`; botd won't start with Incus containers for them, and refuses runs on a machine of those tiers that isn't one of its VMs (such as a container left from before a move to Linode), and the substrate view and `botctl machine substrate` show each tier's kernel. A machine's first `machine.enrolled` audit event records its provider, tier and seconds since it was requested. Both come with a proposed evaluation of the managed substrate: Linode VMs, Incus containers, an orchestrator, or a mix by tier, awaiting the owner's decision ([ADR 0120](docs/adr/0120-managed-substrate.md), [#43](https://github.com/CG-Labs/superbot/issues/43)).
- Air-gapped installs: `deploy/offline-bundle.sh` packs the release binaries, the web client, the landing page, the installer's templates, the Compose files and, optionally, the images (each signature-checked before it is saved, with its SBOM) into one bundle with a `SHA256SUMS`; `install.sh --offline <bundle>` installs or upgrades from it with no network (no apt, git, curl, cargo, npm or Let's Encrypt), after checking its SHA-256 or cosign signature and every file in it, refuses an older bundle than the one installed, and serves `--domain` with the operator's certificate (`--tls-cert`, `--tls-key`, also usable online). `offline-bundle.sh load` loads a bundle's images for Compose. A CI job installs and upgrades from real bundles as root with networking off. The license already verifies offline, now guarded by a test ([ADR 0128](docs/adr/0128-air-gapped-self-host.md), [guide](docs/ops/air-gapped.md), [#59](https://github.com/CG-Labs/superbot/issues/59)).
- Plans: tiers with model routing behind them ([ADR 0033](docs/adr/0033-tiers-model-routing.md)) and fallback across providers ([ADR 0077](docs/adr/0077-two-providers-through-tier-routing.md)); Stripe billing with checkout, the customer portal, token metering, storage limits, resizing on a plan change, billing emails and team plans ([ADR 0093](docs/adr/0093-team-billing.md)); a self-host license key ([ADR 0038](docs/adr/0038-self-host-license-key.md)) and no free tier ([ADR 0068](docs/adr/0068-no-free-tier.md)).
- Operations: Prometheus metrics and structured logs ([ADR 0089](docs/adr/0089-metrics-and-structured-logs.md)), host capacity metrics and a dashboard ([ADR 0106](docs/adr/0106-host-capacity-metrics.md)), a requests-and-runs dashboard, error alert rules and opt-in error reporting to a Sentry-compatible tracker, scrubbed of prompts, chats and secrets ([ADR 0113](docs/adr/0113-service-dashboards-and-error-reporting.md)), recovery objectives and backup alerts for Linode machines ([ADR 0110](docs/adr/0110-linode-machine-recovery-objectives.md)), and a status page with an uptime SLO ([ADR 0090](docs/adr/0090-status-page-and-uptime-slo.md)).
- Compliance: audit events with CSV export, chat history retention with legal holds ([ADR 0098](docs/adr/0098-chat-retention.md)), retention for harness session files and teammates' archived work, on the server and on machines ([ADR 0112](docs/adr/0112-harness-session-and-teammate-files-retention.md)), an access-review report ([ADR 0099](docs/adr/0099-access-review-report.md)), erasing a user's data ([ADR 0102](docs/adr/0102-erasing-a-users-data.md)), deleting a destroyed machine's backups ([ADR 0108](docs/adr/0108-deleting-a-destroyed-machines-backups.md)), and server backups copied off the host to S3-compatible storage, encrypted, with retention, an RPO, alerts and `botctl backups` ([ADR 0109](docs/adr/0109-server-backups-off-the-host.md)).
- Backups encrypted by default: new installs (installer and Compose) make an age key and encrypt server archives and their off-host copies to it, upgrades opt in with `--backup-age-generate`, and plain backups are a startup warning, a setup checklist item, a metric with an alert and an audit event; `SUPERBOT_BACKUP_ENCRYPTION=required` refuses them and `off` keeps them plain by choice ([ADR 0114](docs/adr/0114-backups-encrypted-by-default.md)).
- Opt-in OpenTelemetry traces over OTLP/HTTP (`TRACES_OTLP_ENDPOINT`, off by default): a span per request and per Bot run, with each harness attempt, tool call, approval check and machine call as a child and a Bot's own calls during a run joined to it; trace ids in structured logs and audit events; never a message, prompt, path or secret in a span. Requests and runs also counted by tier in `/metrics`, with no per-user labels ([ADR 0118](docs/adr/0118-harness-run-traces-and-per-tier-metrics.md), [guide](docs/ops/tracing.md)).
- Custom roles: an admin builds a role on member or read-only from six fixed permissions (`users.manage`, `bots.manage`, `audit.view`, `billing.manage`, `signups.approve`, `machines.manage`) and gives it across the server or within a team, through `/api/roles`; the built-in roles are presets of the same permissions and behave as before, unknown permissions grant nothing, holders can never change admins or make them, and every change is audited ([ADR 0123](docs/adr/0123-custom-roles.md), [#53](https://github.com/CG-Labs/superbot/issues/53)).
- Published plans: a public `/pricing` page and `/api/plans` JSON built from the tiers file, listing each sold tier's label, the prices the operator writes in `publishedPrices` (none shipped; "Contact us" without one), its limits, machine size where known, whether its machines have their own kernel where `MACHINE_OWN_KERNEL_TIERS` holds them to it, and feature lines, and an Enterprise contact link from `PLANS_CONTACT_URL`, never Stripe price ids, models or routes; `PLANS_PAGE=auto` (default) publishes only while billing is on ([ADR 0121](docs/adr/0121-published-plans.md), [#42](https://github.com/CG-Labs/superbot/issues/42)).
- GDPR documents for a managed provider, as drafts for legal review and not legal advice: a privacy policy template, a terms of service outline and a DPA template with a breach notification clause, a subprocessor annex and technical and organisational measures taken from the code; and a GDPR guide for self-hosters on roles, retention and answering access and erasure requests ([pack](docs/security/README.md), [#48](https://github.com/CG-Labs/superbot/issues/48)).
- A public site and docs portal, built as static files by `superbot-site`: a landing page with the plans (names and limits from the shipped tiers file, prices to be published, Enterprise by contact) and every doc in `docs/`, plus the install guide, security policy and changelog. It has navigation, search, and a CI build that fails on any broken internal link and keeps the site as an artifact. Publishing it is an operator step ([ADR 0119](docs/adr/0119-public-site-and-docs-portal.md)).
- A security pack for buyers and a SOC 2 readiness checklist ([pack](docs/security/README.md)), a security policy ([SECURITY.md](SECURITY.md)), and this changelog with a GitHub release per tag ([ADR 0111](docs/adr/0111-changelog-and-github-releases.md)).
- The start of a SOC 2 Type II programme, as drafts a managed provider adopts, not a certification: eight security policies (information security, access control, change management, an incident response plan with severity levels, a runbook and communication rules, vendor management, business continuity and disaster recovery, data classification and retention, and acceptable use), each owned by a role with a review cadence and the readiness checklist items it covers, and a Type II evidence plan mapping every criterion to the evidence SuperBot already produces and what is still manual; CI checks their structure and references ([policies](docs/security/policies/README.md), [evidence plan](docs/security/soc2-evidence-plan.md), [ADR 0130](docs/adr/0130-policy-set-and-type-ii-evidence.md), [#57](https://github.com/CG-Labs/superbot/issues/57)).

### Security

- Secrets sealed under a master key and redacted from output ([ADR 0010](docs/adr/0010-secrets.md)), with safe master key rotation ([ADR 0096](docs/adr/0096-master-key-rotation.md)).
- TOTP second factor with recovery codes ([ADR 0094](docs/adr/0094-totp-second-factor.md)), JIT SSO accounts only from an allow-list ([ADR 0103](docs/adr/0103-sso-jit-needs-an-allow-list.md)), and alerts on suspicious sign-ins ([ADR 0104](docs/adr/0104-suspicious-sign-in-alerts.md)).
- Model providers only over HTTPS ([ADR 0097](docs/adr/0097-model-providers-over-https.md)) and harness sandboxes on by default.
- Supply chain: dependency vulnerability scanning ([ADR 0092](docs/adr/0092-dependency-vulnerability-scanning.md)), GitHub Actions pinned by commit ([ADR 0100](docs/adr/0100-github-actions-pinned-by-commit.md)), and image scanning, signing and provenance ([ADR 0101](docs/adr/0101-image-scanning-and-signing.md)).
- Deprovisioning stops a person's work at once: deactivating or deleting them over SCIM, or an admin disabling them, stops every run and queued message on their Bots and the runs on others' Bots that are for them, a run's Bot token acts for no one who is disabled, and their own machine is suspended and held off until they're enabled again (`MACHINE_ON_DISABLE=suspend`, the default, or `keep`), each audited as `user.deprovisioned` ([ADR 0124](docs/adr/0124-deprovisioning-stops-bots-and-machines.md), [#51](https://github.com/CG-Labs/superbot/issues/51)).
- Chromium's sandbox on inside the container ([ADR 0107](docs/adr/0107-chromium-sandbox-in-the-container.md)).
- Per-user machines hardened at first boot, on by default (`MACHINE_HARDENING=off` to opt out): SSH only for root with a key and no forwarding, kernel hardening sysctls, unattended security updates that never reboot by themselves, and egress rules that keep every Bot's and teammate's OS user (even one made later) off private, shared, link-local and cloud metadata addresses and `MACHINE_EGRESS_DENY`, while root and the OS's network daemons pass. Each agent reports every step in its heartbeat; botd audits `machine.hardened`, `machine.hardening_failed` and `machine.reboot_required`, and CI checks the rules as root and on a real Incus host ([ADR 0126](docs/adr/0126-per-user-machine-hardening.md), [#54](https://github.com/CG-Labs/superbot/issues/54)).
- The client renders chat Markdown with `marked` and its own renderer instead of `react-native-markdown-display`, whose `markdown-it` had High advisories: raw HTML shows as text, only http(s) and mailto links open, images show as links instead of loading, and the npm audit gate fails on High ([ADR 0115](docs/adr/0115-client-markdown-renderer-and-npm-audit-at-high.md)).
- botd's whole database encrypted at rest with SQLCipher under a key derived from the master key: required on new installs (installer and Compose), an opt-in for existing ones that encrypts the database at start and keeps a plain copy, re-encrypted on master key rotation and kept encrypted in backups; shown at startup, in the setup checklist, `botctl database`, `/metrics` and the audit log; `SUPERBOT_DATABASE_ENCRYPTION=auto|required|off` ([ADR 0116](docs/adr/0116-database-encrypted-at-rest.md), [guide](docs/ops/database-encryption.md)).
