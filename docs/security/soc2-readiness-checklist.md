# SOC 2 readiness checklist

What has to be true before a SOC 2 audit of the managed SuperBot service can start, built from every gap in the [SOC 2 control mapping](soc2-control-mapping.md#gaps-for-the-soc-2-readiness-checklist-m4). Part of the [security pack](README.md), [#50](https://github.com/CG-Labs/superbot/issues/50) and the M4 exit criteria on the [roadmap](../ROADMAP.md#m4--public-launch).

**SuperBot is not SOC 2 certified, and no SOC 2 audit has started.** This is a readiness path, not a claim of compliance. A status of **Done** means the repository shows the control exists; only an auditor can say whether it is designed and operating well enough.

## How to read it

Each row is one thing to close. Its ID is the criterion it serves (AICPA 2017 Trust Services Criteria, revised points of focus 2022) and a number.

| Column | Meaning |
|--------|---------|
| Kind | **Product**: SuperBot's code must do it, and the evidence is code, an ADR or a CI job. **Process**: people must do it, and the evidence is a written policy, a record or a setting outside this repository. |
| Owner | The role that closes it, from the table below. |
| Evidence to collect | What an auditor will ask to see. For a Type II audit, collect it for the whole observation period. |
| Status | **Done**: the repository shows it, with a link. **Partial**: some of it exists, linked; the rest is named. **Gap**: nothing in the product or this repository does it yet. |

Statuses are checked against the code on `main`, not plans. When a change closes or opens a row, the same PR updates it ([pack rules](README.md#keeping-it-accurate)). CI checks that every link and every ADR and file reference here resolves, that every row has a known kind, owner and status, that every **Done** or **Partial** row links its evidence, that every criterion in the mapping's gap list has a row, that the summary counts match the rows, that every item a [policy](policies/README.md) says it covers is a row here, and that the [evidence plan](soc2-evidence-plan.md) lists every row under its criterion (`server/tests/security_docs_links.rs`).

| Owner | Who |
|-------|-----|
| Management | Whoever runs the managed provider: sets direction, approves policies and accepts risk. |
| Security owner | The named person accountable for the security programme and this checklist. |
| Engineering lead | Owns the code, CI and release process. |
| Operator | Runs the managed servers, hosts and backups. For a self-hoster's own audit, the customer. |
| People lead | Hiring, onboarding, training and leaving. |
| Privacy lead | Privacy policy, DPA, subprocessors and data-subject requests. |

Scope: the managed service. A self-hosting customer is its own service organisation: the product rows below are what SuperBot gives them, and the process rows are theirs to do. Physical security and data-centre controls are inherited from the hosting provider (Linode/Akamai, or wherever the Incus hosts run), whose own report the managed provider must review (CC6.4-1).

The policy set is written but not adopted, so rows it answers are **Partial** at most: a policy is evidence only once management approves it and people follow it ([ADR 0130](../adr/0130-policy-set-and-type-ii-evidence.md)). Rows whose evidence is a record of something done (training, reviews, assessments, tabletops) stay **Gap** until it is done. botd's monthly [evidence bundle](soc2-evidence-plan.md#the-evidence-bundle), and the [change-management bundle](soc2-evidence-plan.md#the-change-management-bundle) exported from GitHub ([ADR 0148](../adr/0148-change-management-evidence-from-github.md)), collect evidence for many rows, but move none: it shows controls operating only once an observation period has started and the bundles are kept ([ADR 0142](../adr/0142-type-ii-evidence-bundles.md)).

## Before engaging an auditor

1. **Name the security owner and the scope.** The system is the managed service; the criteria are Security, plus Availability and Confidentiality if customers' contracts rely on them. Write the system description from the [architecture](architecture.md) and [data flows](data-flows.md) pages, and name the hosting and storage providers as carved-out subservice organisations. The security owner and every other role are named in the provider's private policy register, not here ([adopting the policies](policies/README.md#adopting-them)).
2. **Adopt the policy set** (CC5.3-1) and the incident response plan (CC7.4-1), approved by management. Both are written as drafts in [`policies/`](policies/README.md); adopting them means filling in the placeholders and approving each at a commit. Most CC1 to CC5 rows close with them, once their records exist.
3. **Close or accept every product gap.** Each row above is either closed with code and tests, or accepted in the risk register (CC3.2-1) with a compensating control. Auditors expect at least MFA for staff (CC6.1-1 or CC6.1-2), access reviews (CC6.3-1, CC6.3-2), vulnerability management (CC7.1) and branch protection evidence (CC8.1-1).
4. **List the complementary user entity controls**: what customers must do for the controls to work, such as enforcing MFA at their IdP and reviewing who has access. The **Customer** rows of the [control mapping](soc2-control-mapping.md) are the start.
5. **Run a readiness assessment** with the chosen CPA firm or a consultant, and the external penetration test (CC3.2-2), and fix what they find.
6. **Start collecting evidence** from the day policies are adopted, in the "Evidence to collect" column: a Type II report can only cover the time evidence exists for. The [Type II evidence plan](soc2-evidence-plan.md) maps each criterion to the evidence SuperBot already produces and what is still manual, with a monthly, quarterly and yearly calendar; turn on botd's monthly [evidence bundle](soc2-evidence-plan.md#the-evidence-bundle) (`EVIDENCE_BUNDLES=monthly`) on each managed server the same day.

## Type I and Type II

A **Type I** report says whether controls are suitably designed at one date. A **Type II** report says whether they also operated effectively over an observation period, commonly 3 to 12 months, and is what most enterprise buyers ask for. The [roadmap](../ROADMAP.md#compliance-path-not-promises) puts this readiness checklist in M4 and the Type II programme in M5. A Type I can come first once the process rows are done; a Type II needs those controls running, with evidence, for the whole period, so evidence collection should start as soon as each control is in place, not when the auditor arrives. The Type II programme ([#57](https://github.com/CG-Labs/superbot/issues/57)) started with the draft [policy set](policies/README.md) and the [evidence plan](soc2-evidence-plan.md), and botd now writes the plan's monthly [evidence bundle](soc2-evidence-plan.md#the-evidence-bundle) ([ADR 0142](../adr/0142-type-ii-evidence-bundles.md)).
