# SOC 2 control mapping

How SuperBot, as the code works on `main` today, lines up with the AICPA 2017 Trust Services Criteria (revised points of focus, 2022): the Security common criteria (CC1 to CC9), Availability (A1) and Confidentiality (C1). Part of the [security pack](README.md) and [#41](https://github.com/CG-Labs/superbot/issues/41).

**SuperBot is not SOC 2 certified, and no SOC 2 audit has started.** This page is a self-assessment, not an auditor's opinion. It is the starting point for the [SOC 2 readiness checklist](soc2-readiness-checklist.md) (M4) and Type II (M5) on the [roadmap](../ROADMAP.md#compliance-path-not-promises). Every **Gap** below is open work, tracked there with an owner and the evidence to collect.

## How to read it

Each criterion gets one or more of these statuses:

| Status | Meaning |
|--------|---------|
| **Product** | SuperBot's code does it, and the linked code, ADR or CI job shows how. Some product controls are off until the operator turns them on; the row says so. |
| **Operator** | Whoever runs the SuperBot server must do it. When a customer self-hosts, that is the customer. On the managed service, it is the managed provider. |
| **Customer** | The customer organisation must do it, however SuperBot is run (for example, deciding who gets access, or enforcing MFA at its IdP). |
| **Gap** | Nothing in the product or in this repository does it today. It must be built or written before an audit. |

Where self-host and managed differ, the row names each. For self-host, every **Operator** duty is the customer's. For managed, organisation-level controls (policies, people, vendors, incident response) belong to the managed provider; this public repository holds no evidence of them, so they are listed as **Gap** until they are documented.

Links go to the ADR (design record), code or CI workflow that is the evidence. The other pages of the pack give more detail: [architecture](architecture.md), [data flows](data-flows.md), [access control and isolation](access-control.md), [subprocessors](subprocessors.md), [machine recovery objectives](machine-recovery-objectives.md).

## CC6: Logical and physical access

| Criterion | Status | What is in place | Gaps |
|-----------|--------|------------------|------|
| CC6.1 Logical access security | Product; Operator; Customer; Gap | Sessions are random 256-bit tokens stored only as SHA-256 hashes, in `__Host-` HttpOnly, Secure, SameSite=Strict cookies ([ADR 0012](../adr/0012-users-sessions-rbac.md), [`server/src/users.rs`](../../server/src/users.rs)). Every route is classified by role ([`server/src/rbac.rs`](../../server/src/rbac.rs)); Bots are private or shared by grant ([ADR 0017](../adr/0017-bot-acls.md)); sharing stops at a team ([ADR 0087](../adr/0087-team-accounts-and-machines.md)). Each Bot run gets its own token, revoked when the run ends ([ADR 0083](../adr/0083-per-run-tokens.md)). Secrets are sealed with XChaCha20-Poly1305 under a master key kept outside the data folder ([ADR 0010](../adr/0010-secrets.md), [`server/src/secrets/sealed.rs`](../../server/src/secrets/sealed.rs), [`server/src/secrets/key.rs`](../../server/src/secrets/key.rs)), and the key can be rotated, with an audit event ([ADR 0096](../adr/0096-master-key-rotation.md), [master key rotation](../ops/master-key-rotation.md)). Machines use mutual TLS with botd's own CA ([ADR 0031](../adr/0031-machine-enrollment-mtls.md), [`server/src/machines/pki.rs`](../../server/src/machines/pki.rs)). Sign-in codes and the owner's password can require a TOTP second factor with recovery codes, for admins or everyone ([ADR 0094](../adr/0094-totp-second-factor.md), [`server/src/mfa.rs`](../../server/src/mfa.rs)). The operator protects the master key and the host, and turns the MFA policy on. The customer requires MFA at its IdP for SSO sign-ins ([IdP guides](../sso/)). | No external secret vault (M5). No written rule yet for MFA at the IdP. |
| CC6.2 Registration and authorization before access | Product; Customer | Accounts come only from an admin (direct, or approving a signup request, which issues a one-time sign-in code), SCIM provisioning, a team invite that expires after 7 days, or SSO just-in-time accounts. Just-in-time accounts are off unless `SSO_<name>_JIT_ROLE` is set, and botd refuses to start when a provider has it without an allow-list: allowed email domains (generic OIDC, SAML, Apple), Workspace domains (Google), organizations (GitHub), or tenants (Entra, which is always pinned to one tenant id or an `ALLOWED_TENANTS` list) ([ADR 0103](../adr/0103-sso-jit-needs-an-allow-list.md), [ADR 0022](../adr/0022-landing-and-signups.md), [ADR 0023](../adr/0023-scim.md), [ADR 0087](../adr/0087-team-accounts-and-machines.md), [`server/src/sso/mod.rs`](../../server/src/sso/mod.rs)). The customer decides who is given access, and runs its IdP. | None in the product. |
| CC6.3 Role-based access, least privilege, removal | Product; Customer; Gap | Roles and Bot grants (`viewer`, `operator`); a Bot can do no more than its owner ([ADR 0029](../adr/0029-per-user-isolation.md)); team admins manage members' machines but not their data ([ADR 0087](../adr/0087-team-accounts-and-machines.md)). Disabling a user or SCIM deprovisioning ends their sessions at once ([ADR 0023](../adr/0023-scim.md)); admins can end any user's sessions. A teammate who loses access loses their OS user and files on the owner's machine or server ([ADR 0052](../adr/0052-teammate-offboarding-on-machines.md), [ADR 0066](../adr/0066-removing-teammate-accounts-on-one-server.md)). An access-review report lists everyone's role, status, team, SCIM tenant, second factor, last sign-in, Bot access, sessions and API tokens, and machine, exports as dated CSV, and records an admin's sign-off as an audit event ([ADR 0099](../adr/0099-access-review-report.md)). The customer assigns roles and reviews access. | No custom roles or service accounts (M5). |
| CC6.4 Physical access | Operator; Gap | Not a product control. Self-host: the customer's data centre or host. Managed: inherited from the hosting provider (Linode/Akamai, or wherever the operator runs Incus hosts) ([subprocessors](subprocessors.md)). | Managed: no documented review of the hosting provider's own assurance reports. |
| CC6.5 Disposal of assets | Product; Operator; Gap | Destroying a machine revokes its certificates ([ADR 0031](../adr/0031-machine-enrollment-mtls.md)); a machine a team gave a leaver is destroyed after `TEAM_MACHINE_DAYS` ([ADR 0087](../adr/0087-team-accounts-and-machines.md)); machine backups are deleted after their retention ([ADR 0071](../adr/0071-off-host-machine-backups.md)), and admins delete a destroyed machine's backups at once on request, audited ([ADR 0108](../adr/0108-deleting-a-destroyed-machines-backups.md)); teammates' work is archived for the owner by default, or deleted after a grace period with `MACHINE_TEAMMATE_FILES=delete` or `ISOLATION_TEAMMATE_FILES=delete` ([ADR 0052](../adr/0052-teammate-offboarding-on-machines.md)). Admins erase a user's personal data on request: Bots, chats, sign-ins and secrets go, the user row stays as a tombstone, and the audit log names them by a pseudonym; refused under a legal hold, as a team's last owner, or with a machine ([ADR 0102](../adr/0102-erasing-a-users-data.md)); their machines' backups go with them when asked ([ADR 0108](../adr/0108-deleting-a-destroyed-machines-backups.md)). Wiping disks is the hosting provider's. | Erasure leaves the per-user isolation folder to the operator and data in server backups until their retention ends. |
| CC6.6 Protection against threats from outside the boundary | Product; Operator | Only Caddy is public; botd is on loopback or an unpublished container network ([architecture](architecture.md#components)). Caddy sends a Content-Security-Policy ([`deploy/docker/Caddyfile`](../../deploy/docker/Caddyfile)). Sign-in failures are limited to 10 per 10 minutes per IP; writes without a bearer token must come from botd's own origin ([auth review](auth-review-2026-11.md)). Incus containers can't reach each other, the host or private ranges ([ADR 0065](../adr/0065-incus-container-machines.md)). The Linode firewall needs `MACHINE_FIREWALL=on`, off by default; without it a new Linode is open to the internet and only mutual TLS guards the agent port ([ADR 0035](../adr/0035-machine-firewall-auto-enroll.md)). The operator runs the host firewall and OS patching. | No intrusion detection or WAF in the product. |
| CC6.7 Data in transit | Product; Operator; Gap | HTTPS to the server; mutual TLS 1.3 to machines; Incus host certificate pinned; webhook and S3 URLs must be HTTPS; model providers SuperBot configures (the tiers file, `SUPERBOT_HERMES_BASE_URL`) must be HTTPS or loopback ([ADR 0097](../adr/0097-model-providers-over-https.md)); SMTP uses STARTTLS or TLS ([encryption in transit](data-flows.md#in-transit)). Backups are encrypted with age when the operator sets recipients ([ADR 0030](../adr/0030-backup-restore-drill.md), [ADR 0071](../adr/0071-off-host-machine-backups.md)). | Backups are plain unless the operator sets age recipients. |
| CC6.8 Unauthorized or malicious software | Product; Gap | Risky tool calls wait for a person, scripts are read like the command line that runs them, and a canary checks every hooked tool ([ADR 0007](../adr/0007-approvals.md), [ADR 0053](../adr/0053-smarter-command-analysis.md), [ADR 0063](../adr/0063-canary-covers-every-hooked-tool.md)). Runs are confined to their user's Unix account or machine ([access control](access-control.md#isolation-between-users)). Harness CLIs and the agent are checked against pinned hashes (CC5.2). Pages the Bots open run in Chromium's sandbox inside the published image too, checked at start and by the smoke test, with an explicit, logged opt-out ([ADR 0107](../adr/0107-chromium-sandbox-in-the-container.md)). | No malware scanning or endpoint detection on the server or machines. No egress allowlists for runs (M5). |
