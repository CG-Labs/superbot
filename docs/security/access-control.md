# Access control and isolation

How people and Bots sign in, what each may do, how one user is kept from another, and what is recorded. Part of the [security pack](README.md).

## Authentication

| Method | How it works |
|--------|--------------|
| **Sessions** | An opaque 256-bit token, stored only as a SHA-256 hash. Sent as a cookie (`__Host-superbot_session`: HttpOnly, Secure, SameSite=Strict) or a bearer token from the apps. Ends after 7 days idle or 30 days at most, and on sign-out, "sign out everywhere", or the user being disabled ([ADR 0012](../adr/0012-users-sessions-rbac.md), [ADR 0024](../adr/0024-auth-review-hardening.md)). |
| **SSO (OpenID Connect)** | Microsoft Entra ID, Google, any OIDC provider (Okta, Auth0, Keycloak, ...), Sign in with Apple, and GitHub. Several at once; optional allowed email domains; just-in-time accounts, only with an allow-list for the provider (domains, GitHub organizations or Entra tenants, [ADR 0103](../adr/0103-sso-jit-needs-an-allow-list.md)) ([ADR 0014](../adr/0014-oidc-sso-entra.md), [ADR 0016](../adr/0016-sso-multi-provider.md), [ADR 0018](../adr/0018-sso-github-apple.md)). Entra emails count only when the tenant verified the domain ([auth review, AUTH-03](auth-review-2026-11.md)). |
| **SAML** | Natively: botd is the SAML 2.0 service provider ([ADR 0127](../adr/0127-native-saml-service-provider.md), [guide](../sso/saml-native.md)). The assertion must be signed by a certificate from the IdP's metadata (never from the message), with RSA-SHA256 or stronger, or ECDSA on P-256 or P-384 (SHA-1 refused), and match the audience, ACS URL, request ID, IdP and validity window; each assertion is used once; signature wrapping, DTDs and comments are refused, each refusal audited with its reason ([ADR 0151](../adr/0151-saml-encrypted-nameids-ecdsa-and-signed-metadata.md)). Sign-in starts at SuperBot; a post from the IdP's app portal only restarts one, with `SSO_<ID>_IDP_INITIATED=restart`, and never signs anyone in itself ([ADR 0175](../adr/0175-saml-idp-initiated-sign-in-restarted.md)). Optional, each off by default: signed AuthnRequests ([ADR 0137](../adr/0137-saml-signed-requests-and-single-logout.md)), encrypted assertions and NameIDs (AES-GCM with RSA-OAEP; AES-CBC only inside a response the IdP signed, [ADR 0150](../adr/0150-saml-encrypted-assertions.md), [ADR 0218](../adr/0218-saml-aes-cbc-in-signed-responses.md)), signed IdP metadata ([ADR 0151](../adr/0151-saml-encrypted-nameids-ecdsa-and-signed-metadata.md)), responses over the HTTP-Artifact binding ([ADR 0268](../adr/0268-saml-artifact-binding.md)), and requiring the IdP's MFA (`SSO_<ID>_AUTHN_CONTEXT`, [ADR 0190](../adr/0190-saml-required-authn-context.md)), identity assurance such as REFEDS RAF ([ADR 0328](../adr/0328-saml-required-identity-assurance.md)), membership of given groups ([ADR 0160](../adr/0160-saml-groups-and-role-mapping.md)) or a recent sign-in at the IdP ([ADR 0225](../adr/0225-saml-session-lifetime-and-reauthentication.md)). A session ends when the IdP's does (`SessionNotOnOrAfter`), on by default (ADR 0225). Single logout both ways, in the browser and server to server (SOAP), only with signed, fresh, unreplayed messages; revoking someone's sessions, disabling them or SCIM deprovisioning also ends their IdP sessions where the IdP takes SOAP logout ([ADR 0208](../adr/0208-saml-back-channel-soap-logout.md), [ADR 0258](../adr/0258-saml-back-channel-logout-on-revoke-and-deprovisioning.md)). Federations: several IdPs, or every IdP of a federation's signed aggregate, under one provider, with a chooser or the federation's discovery service ([ADR 0282](../adr/0282-saml-several-idps-of-a-federation.md), [ADR 0308](../adr/0308-saml-every-idp-of-a-federation.md), [ADR 0314](../adr/0314-saml-discovery-service.md)). SuperBot's own keys roll over with no failed sign-in, and expiring certificates are audited 30 days ahead ([ADR 0181](../adr/0181-saml-sp-key-rollover.md), [ADR 0198](../adr/0198-saml-certificate-expiry-warnings.md)). Or through an OIDC broker (Keycloak) that checks the IdP's signed assertion, accepting only logins brokered by the named IdP ([ADR 0020](../adr/0020-saml-bridge.md)). Both follow the same linking, just-in-time allow-list and disabled-user rules as OIDC. |
| **One-time sign-in codes** | An admin issues a code for a person; it expires (default 60 minutes). |
| **Break-glass password** | `AUTH_PASSWORD`, for the owner account, for setup and recovery. Constant-time compare and rate-limited. |
| **Two-factor authentication** | TOTP from any authenticator app, with ten one-time recovery codes, for sign-in codes and the password. An admin (or `AUTH_MFA`) requires it for admins, which includes the owner, or for everyone; anyone can turn on their own. Secrets are sealed under the master key; wrong codes are limited per IP and per user and audited. Once the owner needs it, the password works only at sign-in, not over HTTP Basic ([ADR 0094](../adr/0094-totp-second-factor.md)). |
| **SCIM 2.0 provisioning** | Off by default (`SCIM=on`). Its own hashed bearer token, valid only on `/scim/v2`, expiring, and limited to its scopes: users or groups, read or write ([ADR 0196](../adr/0196-scim-token-expiry-and-rotation.md), [ADR 0224](../adr/0224-scim-token-scopes.md)). Deprovisioning disables the user, ends their sessions, stops their runs and suspends their machine ([ADR 0023](../adr/0023-scim.md), [ADR 0026](../adr/0026-scim-review-hardening.md), [ADR 0124](../adr/0124-deprovisioning-stops-bots-and-machines.md)). Bulk requests and the Enterprise User extension are supported; Google Workspace, which pushes SCIM only to its catalog apps, is read by botd from its Directory API instead (`GOOGLE_DIRECTORY_SYNC`, off by default) ([ADR 0274](../adr/0274-scim-provisioning-delivered.md)). SCIM never sets a built-in role; group-to-role mappings are below. |
| **Service account tokens** | For scripts and integrations: `sbsa_` plus 256 random bits, shown once and stored only as a SHA-256 hash. Each is scoped to permissions its account holds, expires (1 to 365 days, default 90), and can be rotated (with an overlap of at most a day) or revoked. A service account has no password, code, identity or session, so it can't sign in, and is never an admin ([ADR 0143](../adr/0143-service-accounts.md)). |
| **App lock** | Optional biometric unlock in the iOS and Android apps ([ADR 0078](../adr/0078-client-biometric-app-lock.md)). |

Sign-in failures (password, codes, second factors, SSO) are limited to 10 per 10 minutes per IP address, and wrong second factors to 5 per 15 minutes per person. Writes without a bearer token must come from botd's own origin, which blocks cross-site requests ([auth review](auth-review-2026-11.md)).

SSO sign-ins don't get SuperBot's second factor: they rely on the IdP's MFA, which the customer must require there (each [IdP guide](../sso/) says where). With native SAML, botd can also refuse a sign-in whose signed assertion doesn't say the IdP used MFA (`SSO_<ID>_AUTHN_CONTEXT`, [ADR 0190](../adr/0190-saml-required-authn-context.md)); the IdP's word is what it checks.

On an air-gapped server, sign-in works with the password, sign-in codes, TOTP, and an IdP inside the network; cloud IdPs only if the server can reach them ([air-gapped guide](../ops/air-gapped.md#what-needs-the-internet-and-what-to-do-instead)).

**Not built:** WebAuthn or passkeys, and long-lived personal API tokens.

## Authorization

- **Roles.** `admin`, `member` and `readonly`. Every API route is classified; an unclassified route needs admin ([ADR 0012](../adr/0012-users-sessions-rbac.md)).
- **Custom roles.** An admin builds a role from `member` or `readonly` plus any of six fixed permissions (`users.manage`, `bots.manage`, `audit.view`, `billing.manage`, `signups.approve`, `machines.manage`) and gives it across the server or within a team. Each opens a named list of routes; unknown permission names are refused or grant nothing. Holders never reach admins, the owner, or other custom-role holders, and never make admins. Every change and refusal is audited ([ADR 0123](../adr/0123-custom-roles.md)). Admins build, change, give and delete roles under **Roles** in the app and the console, or with `botctl role`, from the same fixed permissions; each person's effective permissions are shown in Users, and the apps ask first before giving a role to an admin (they stop being one) or changing a held role's base ([ADR 0132](../adr/0132-custom-roles-in-the-apps.md)). A role can be given until an end, with a reason for the audit log; it grants nothing once the end passes, and is taken away within a minute, audited as `role.expired`. A role with a time limit is time-bound: given only by hand, with an end within the limit, and never to a SCIM or SAML group or a service account, so elevated access can't become standing access ([ADR 0197](../adr/0197-time-bound-custom-roles.md)). An admin can make a time-bound role requestable: people ask for it for a few hours, with a reason, and another admin approves (never their own), for as long or shorter, or denies; approval rechecks everything and the role ends by itself. A request never changes someone's built-in role or replaces their custom role, and every step is audited ([ADR 0209](../adr/0209-requests-for-time-bound-roles.md)). A team's owners and admins give the team's plain members a custom role within the team, and take it away, without a server admin: only roles with a team permission, only their team permissions apply, never to themselves, and never over a role the IdP gives; it is never more than they could give by making someone a team admin ([ADR 0254](../adr/0254-team-owners-give-custom-roles-in-their-team.md)). They also decide their team's requests for roles within it, beside server admins, with the same rechecks in one transaction, only for its plain members and never over a role the IdP gives; requests across the server stay with server admins, and their decisions are audited with `via: "team"` ([ADR 0263](../adr/0263-team-owners-decide-requests-for-team-roles.md)). They hear of new ones by email and push, never read-only people, and never for a request they couldn't approve ([ADR 0302](../adr/0302-team-owners-hear-of-requests-for-team-roles.md)). Someone holding `bots.manage` hands a disabled person's Bots and routines to someone else without a server admin, but never an admin's, the owner's or another custom-role holder's, never the primary Bot, and never to themselves; a service account can't, and each refusal is audited ([ADR 0315](../adr/0315-bot-handover-under-bots-manage.md)). An admin can make a requestable role need two approvers: two different people who may decide the request, the second for the first's hours or fewer; a first approval counts only while its approver could still approve, and the setting is refused with fewer than two active admins ([ADR 0320](../adr/0320-two-approvers-for-chosen-roles.md)). The person who asked hears when their request is approved, denied or lapses, by email and on their phone, and nobody else does: never the notification list or webhook, and the push names no role ([ADR 0329](../adr/0329-the-asker-hears-when-their-request-is-decided.md)).
- **Service accounts.** Hold member, read-only or a custom role, across the server or within a team, never admin (the database refuses it too). They can't be made to hold more than their owner, and every request gets at most the token's scopes, within the account's role, within what the owner holds then; a disabled owner lends nothing. They can't use a person's routes (sign-in, own account, machine, billing, screens, approvals, a Bot's access and grants) or manage service accounts. Admins manage all, in the app and the console too, where a new token is shown once; delegates with `users.manage` only their own, in the app, with `botctl` or the API, and only in the team they're on. Any other owner sees their own, revokes their tokens and disables them, nothing more; others' are not found for them ([ADR 0239](../adr/0239-owners-see-and-stop-their-service-accounts.md)). A team's service account acts in that team only while its owner is an admin or on it ([ADR 0182](../adr/0182-delegates-own-service-accounts.md)). Audited as themselves ([ADR 0143](../adr/0143-service-accounts.md), [ADR 0152](../adr/0152-service-accounts-in-the-apps.md)). A Bot's owner or an admin can grant one viewer or operator on a Bot; on every request it reaches no Bot, and does no more with one, than its owner can then, and never decides approvals. Each one's refusals in the last 30 days are counted by reason in its views ([ADR 0170](../adr/0170-service-accounts-granted-bots.md)). With `write` it can make private Bots that its owner owns (their machine, plan and keys) and manage the ones it keeps, at most 20, never sharing or granting them; triggers release them to the owner when the Bot or the account changes owner or the account is deleted, and under isolated shared Bots their runs reach only what the account may; only the Bot's owner or an admin hands it an existing Bot or takes one back, never the account itself ([ADR 0229](../adr/0229-handing-bots-to-service-accounts.md), [ADR 0222](../adr/0222-service-accounts-keep-their-owners-bots.md)), several at once only all or none, each checked as one is and within the limit together ([ADR 0324](../adr/0324-handing-several-bots-to-a-service-account.md)).
- **SCIM group roles.** Off unless `SCIM_GROUP_ROLES=on`. An admin can map a SCIM group to a custom role, within its team or across the server, so the group's members hold it while the IdP keeps them in the group. The IdP never names a role. A mapping is never to `admin`, a built-in role, or a role whose permissions act on admins (`bots.manage` or `machines.manage` across the server, `machines.manage` in a team), and such a role can't gain them later. It never changes an admin, the owner account, or anyone with a custom role already; it takes away only what it gave and nobody has changed by hand since, and taking away runs even with the setting off. Grants, removals, skips and refusals are audited ([ADR 0138](../adr/0138-scim-group-role-mapping.md), [guide](../sso/scim.md#groups-to-roles)). An admin can also declare a SCIM group a role group: no team, so it overlaps teams, and its members hold its custom role across the server, under the same limits; a person holds one custom role, from the oldest role group that can give it ([ADR 0180](../adr/0180-scim-role-groups.md), [guide](../sso/scim.md#role-groups)).
- **SAML group roles.** An admin can map a group named in a native SAML provider's signed assertions to a custom role across the server, with the same limits as SCIM's: never admin, a built-in role or a role whose permissions reach admins. Each sign-in gives the role to people in the group and takes it back from those no longer in it; only what a mapping gave is taken away, and a change by hand stands. With several IdPs of a federation, each mapping names its IdP and only that IdP's sign-ins apply it, and group values scoped to another IdP's domain are dropped. Every grant, removal and refusal is audited ([ADR 0160](../adr/0160-saml-groups-and-role-mapping.md), [ADR 0287](../adr/0287-saml-groups-per-idp-of-a-federation.md), [guide](../sso/saml-native.md#groups)).
- **Delivered scope.** What advanced RBAC ([#53](https://github.com/CG-Labs/superbot/issues/53)) and SCIM provisioning ([#51](https://github.com/CG-Labs/superbot/issues/51)) cover, with their tests and the follow-ups not started, is mapped in [ADR 0272](../adr/0272-advanced-rbac-delivered.md) and [ADR 0274](../adr/0274-scim-provisioning-delivered.md).
- **Bot permissions.** A Bot is private to its owner or shared. Sharing grants `viewer` or `operator`; owners and admins manage. Read-only users can only view ([ADR 0017](../adr/0017-bot-acls.md)).
- **Shared Bots.** A shared Bot runs as its owner's Bot. With `SHARED_BOTS=isolated` it reaches for a teammate only what that teammate could, without the owner's keys or facts. That is the default, and the only choice, when Bots run on users' machines (`MACHINE_ROUTING` on or assigned). On one server (`MACHINE_ROUTING=off`) the default is `SHARED_BOTS=open`: a shared Bot acts with its owner's access, keys and facts for everyone who uses it ([ADR 0046](../adr/0046-shared-bots-under-isolation.md)).
- **Admin console.** `/console/` is for admins only ([ADR 0032](../adr/0032-console-admin-only.md)).
- **Approvals.** Risky actions wait for a person: destructive shell commands, file deletes, outbound messages, network installs and `git push`. Each harness checks with botd before each tool call through its own hook (Claude Code, Codex, Pi and Hermes Agent); if botd can't be reached, the call is refused. Bots can't approve. Scripts are read and classified like the command line that runs them ([ADR 0007](../adr/0007-approvals.md), [ADR 0051](../adr/0051-approve-once-per-run.md), [ADR 0053](../adr/0053-smarter-command-analysis.md), [ADR 0063](../adr/0063-canary-covers-every-hooked-tool.md)). Admins edit the policy in the apps ([ADR 0049](../adr/0049-policy-editor-in-the-apps.md)).
- **Harness sandboxes.** New installs turn on the harness's own sandbox for Claude Code and Codex ([ADR 0055](../adr/0055-harness-sandbox-defaults.md)).

## Bots: a token for each run

Each run of a Bot gets its own token (`sbb_<bot>.<id>.<HMAC-SHA256>`) ([ADR 0083](../adr/0083-per-run-tokens.md)):

- It is valid for that run only, for at most the run timeout plus 60 seconds, and is revoked as soon as the run ends, however it ends.
- botd holds what it may do in memory; nothing survives a restart.
- A Bot can do no more than its owner. A disabled owner's Bot can do nothing. A Bot can't act as another Bot.
- On machines, the agent's relay checks the token too, so nothing left on a machine reaches botd after the run.
- Issue and revoke are both audited (`bot.token_issued`, `bot.token_revoked`).

## Secrets in an external store

With `SECRETS_BACKEND` set to `vault`, `azure-keyvault`, `gcp-secret-manager` or `aws` (off by default), the operator's own secrets manager decides who may read or change each secret, under its own policies and audit trail ([ADR 0125](../adr/0125-external-secrets-backend-vault.md), [ADR 0136](../adr/0136-cloud-secret-managers.md), [ADR 0146](../adr/0146-aws-secrets-manager.md), guides for [Vault](../ops/vault.md) and [the clouds](../ops/cloud-secrets.md)).

- **botd only reads.** It never writes to the store, so its policy there needs only read access, and a botd given only that can't change the organisation's secrets. Secrets people save in the app still go to botd's sealed store.
- **Folders keep scopes apart.** botd's own secrets are read only from `server/`, the server-wide secrets Bots get only from `bots/`, and, with `SECRETS_USER_FOLDERS=1`, each user's only from `users/<user id>/`, given only to Bots that user owns ([ADR 0174](../adr/0174-users-secrets-in-the-external-store.md)). A name in the wrong folder is ignored. Names botd reserves, such as the master key and the store's own credentials, are never read from it.
- **Nothing for Bots to take.** botd's credentials for the store, and its cloud identity's keys, are kept from every run and redacted. Values read are redacted from chats, events and the audit log like any other secret.
- **Short-lived credentials per run**, each off by default: a Vault lease, an AWS STS session, a GCP access token or an Entra app token made as the run starts, optionally one per user (`{owner}`) or narrowed by a session policy or credential access boundary. Vault leases are revoked when the run ends; the others can't be revoked and are audited with their expiry ([ADR 0185](../adr/0185-short-lived-credentials-per-run.md), [ADR 0194](../adr/0194-sts-sessions-for-each-run.md), [ADR 0203](../adr/0203-gcp-service-account-tokens-for-each-run.md), [ADR 0213](../adr/0213-entra-app-tokens-for-each-run.md), [ADR 0230](../adr/0230-session-policies-and-tags-for-each-run.md), [ADR 0240](../adr/0240-downscoped-gcp-tokens-for-each-run.md)).
- **Audited and fail closed.** Every read that reaches the store (`secret.read`), each sign-in to it and each lease is audited, never a value. A store that can't answer refuses the runs that need it (`secrets_unavailable`) rather than handing out an old or a different value. Rotations reach new runs after the cache time, at once with `botctl secrets refresh`, or within seconds from Vault's or GCP Secret Manager's change events ([ADR 0291](../adr/0291-refreshing-the-external-secrets-cache.md), [ADR 0306](../adr/0306-following-vaults-change-events.md), [ADR 0325](../adr/0325-following-gcp-secret-managers-change-events.md)).

## Residency pins

- **Who pins.** Only a server admin pins a user or a team to a data region, under an agreement reference, and unpinning needs a reason. A pin is refused while its region has no host or backup store, or any of their data is elsewhere. Every pin, unpin and refusal is audited ([ADR 0129](../adr/0129-contractual-data-residency.md)).
- **What it holds.** While a pin holds, their region can't change, and backups, restores, moves, model routes and runs outside it are refused and audited ([ADR 0139](../adr/0139-in-region-model-routes.md), [ADR 0267](../adr/0267-runs-on-a-computer-in-the-pins-region.md)). With `RESIDENCY_STARTUP=refuse`, botd won't start while a pin can't be kept ([ADR 0171](../adr/0171-residency-startup-and-leavers.md)).
- **Who sees it.** Admins get a report on each pin, sealed with a SHA-256 digest the customer can check ([ADR 0155](../adr/0155-residency-reports.md)). People see their own pin in Settings and download the report on it; a team's owners and admins the one on the team's pin, at most 5 per person every 10 minutes ([ADR 0168](../adr/0168-residency-in-the-app.md)). Where the data is kept: [data flows](data-flows.md#in-a-regions-chat-store-residency-pins).

## Isolation between users

| Setup | What keeps users apart |
|-------|------------------------|
| **One server** | Each user's own working folder and facts ([ADR 0029](../adr/0029-per-user-isolation.md)). Each user's Bots run as that user's own Unix account (`sb-u-<id>`), which can't read botd's files, the database, the master key or other users' folders. On by default for new installs, for every harness ([ADR 0037](../adr/0037-per-user-unix-accounts.md), [ADR 0058](../adr/0058-harness-os-user-by-default.md)). A teammate's run of a shared Bot gets an account of its own for that owner's Bots only with `ISOLATION=users`, `SHARED_BOTS=isolated` and `ISOLATION_TEAMMATES` on (its default when both are set). `SHARED_BOTS` defaults to `open` here, so by default a teammate's run uses the owner's account, access and keys ([ADR 0064](../adr/0064-teammate-accounts-on-one-server.md), [ADR 0066](../adr/0066-removing-teammate-accounts-on-one-server.md)). |
| **Managed** | One machine per user (Linode VM or Incus container). A Linode VM has a kernel of its own. Incus containers on one host share its kernel, so a kernel escape would cross every user on that host; `MACHINE_OWN_KERNEL_TIERS` makes botd refuse to start with containers for the tiers it lists, and refuse runs on any machine of those tiers that isn't one of its VMs ([ADR 0065](../adr/0065-incus-container-machines.md), [ADR 0120](../adr/0120-managed-substrate.md)). An admin can dedicate Incus hosts to a team (**off by default**): only that team's machines go there and its machines go nowhere else, so such an escape stays within one customer ([ADR 0166](../adr/0166-incus-hosts-dedicated-to-a-team.md)). A Bot runs only on its owner's machine, never on the server or another user's machine ([ADR 0036](../adr/0036-bots-on-the-users-machine.md)). On the machine, Bots run as the unprivileged `superbot-bots` user, **on by default**, locked down so no run can gain privileges again (no sudo, setuid programs or file capabilities), keeps its files to itself and sees only its own user's processes; the agent refuses a run user in a privileged group or with a sudo rule. `MACHINE_BOT_USER=off` runs them as root, like the machine agent, so they can read the agent's key ([ADR 0043](../adr/0043-bots-own-os-user-on-machines.md), [ADR 0145](../adr/0145-locked-down-run-users-and-red-team.md)). `MACHINE_TEAMMATE_USERS=on` (**off by default**; needs the Bots' own user) runs teammates as their own OS users with their own harness logins and screens; without it, a teammate's run of a shared Bot shares the owner's Bots' user and home, so its tools can read the owner's folder and logins, though botd still withholds the owner's keys and facts ([ADR 0046](../adr/0046-shared-bots-under-isolation.md), [ADR 0048](../adr/0048-teammates-own-os-user-on-machines.md), [ADR 0062](../adr/0062-teammate-harness-logins.md)). Either way, no run reaches another user's machine. Machines are hardened at first boot, **on by default** (`MACHINE_HARDENING`): SSH only for root with a key, kernel hardening sysctls, unattended security updates, and egress rules that refuse every user but root and the OS's network daemons at private, shared, link-local and cloud metadata addresses, which bind Bots unless `MACHINE_BOT_USER=off` ([ADR 0126](../adr/0126-per-user-machine-hardening.md)). Each run is held to its tier's run limits in a cgroup of its own (**on by default**, `MACHINE_RUN_LIMITS`), and admins can restrict outbound traffic to an allow-list for every machine or one user's (**off by default**) ([ADR 0135](../adr/0135-run-limits-and-egress-allow-lists.md)). |
| **Machine network** | Linode: only with `MACHINE_FIREWALL=on` (off by default), a Cloud Firewall drops inbound except botd to the agent port; SSH closed unless the operator lists sources. Without it, the Linode is open to the internet and only mutual TLS guards the agent port ([ADR 0035](../adr/0035-machine-firewall-auto-enroll.md)). The same firewall drops outbound TCP and UDP to private, shared and link-local ranges and `MACHINE_EGRESS_DENY` from the whole machine, root included (**on by default** with the firewall, `MACHINE_FIREWALL_EGRESS`; [ADR 0179](../adr/0179-outbound-rules-at-the-provider.md)). With `MACHINE_TEAM_NETWORK=vpc` (off by default), a team's machines are also on a VPC of the team's own, where they reach only the team's services: the firewall still drops inbound there, and a machine whose owner leaves the team is taken off it ([ADR 0189](../adr/0189-a-network-of-its-own-per-team.md)). Machines made before their owner joined the team join it at their next boot, or when idle with `MACHINE_TEAM_NETWORK_JOIN=when-idle`; botd sends the agent only a validated private subnet to let through ([ADR 0202](../adr/0202-existing-machines-join-their-teams-network.md)). Every create names its kind of interface, so the account's default never leaves a machine outside the firewall; a machine with Linode interfaces counts as behind it only when each public and VPC interface is, and joins or leaves its team's VPC only while powered off ([ADR 0226](../adr/0226-linode-interfaces-behind-the-firewall-and-on-team-networks.md)). Incus: botd requires `MACHINE_FIREWALL=on`; unprivileged containers with AppArmor and seccomp, and a firewall that keeps them off each other, the host and private ranges ([ADR 0065](../adr/0065-incus-container-machines.md)). With `MACHINE_TEAM_NETWORK=ovn`, a team's containers also get a NIC on an isolated OVN network of the team's own, whose ACL lets nothing in and out only to the team's subnet; a container whose owner leaves is unplugged at once ([ADR 0212](../adr/0212-an-ovn-network-per-team-on-incus.md)). A deleted team's network is removed once nothing is on it (`MACHINE_TEAM_NETWORK_REMOVE`, [ADR 0236](../adr/0236-removing-the-networks-of-teams-that-are-gone.md)). |
| **Secrets** | Personal secrets reach only that person's own Bots. Each is sealed with its user and name. botd's own secrets never reach a run ([ADR 0029](../adr/0029-per-user-isolation.md), [ADR 0044](../adr/0044-client-personal-secrets.md)). |

Tested in CI on real hosts: no Bot reaches another user's folder or logins, or botd's files ([`deploy/test-isolation.sh`](../../deploy/test-isolation.sh), [`deploy/test-isolation-harness.sh`](../../deploy/test-isolation-harness.sh)), and Incus containers on a real host ([ADR 0069](../adr/0069-validating-incus-containers-on-a-real-host.md)), including that a user made inside a container can't reach botd's machine port or the metadata address while root can; and, as root, that a machine's egress rules hold every user but root and the OS's daemons, even one made after they loaded ([ADR 0126](../adr/0126-per-user-machine-hardening.md)); that an allow-list lets them reach only its entries, and that a run is held to its CPU, memory and process limits in a real cgroup ([ADR 0135](../adr/0135-run-limits-and-egress-allow-lists.md)).

**Planned:** dedicated or VPC hosts for enterprise tiers, and the M5 red-team exercise ([ADR 0135](../adr/0135-run-limits-and-egress-allow-lists.md)).

## Audit log

- Records sign-ins and failures, user and role changes, Bot and routine changes, policy and approval decisions, each harness run and its result, denied access, licence, SCIM and machine events ([ADR 0009](../adr/0009-audit-events.md)).
- Each event names its actor (user, Bot or system) with email, role, sign-in method, IdP, session, and who a Bot acted for ([ADR 0019](../adr/0019-audit-actors.md)).
- Append-only: database triggers refuse updates, and deletes except retention pruning. This guards against mistakes and API misuse, not someone with write access to the database file. Kept forever unless `AUDIT_RETENTION_DAYS` is set.
- Admins view and filter it in the apps and export CSV ([ADR 0028](../adr/0028-client-admin-console-link-and-audit.md), [ADR 0060](../adr/0060-client-audit-detail-and-filters.md)).
- **Access reviews**: admins see one report of everyone's role, status, team, SCIM tenant, second factor, last sign-in, Bot access, sessions and API tokens (never the tokens), and machine, and every service account's owner, roles, what it can use today, Bot access and live tokens (scopes, expiry and last use, never the token), with flags for an inactive owner, an owner off its team (so it acts in none), and unscoped or unused tokens; they export it as dated CSV and sign it off, and the sign-off is an `access_review.completed` event over a digest that covers both ([ADR 0099](../adr/0099-access-review-report.md), [ADR 0165](../adr/0165-service-accounts-in-access-reviews.md), [ADR 0188](../adr/0188-service-accounts-off-their-team-in-access-reviews.md)).
- **Tamper-evident**: every event is sealed onto a SHA-256 hash chain. `botctl audit verify` names the first changed, removed, added or reordered event, and checks hashes pinned from a copy kept elsewhere ([ADR 0122](../adr/0122-siem-export-and-tamper-evident-audit.md)). Hourly checkpoints of the chain's head are signed, and optionally timestamped by an RFC 3161 time-stamping authority ([ADR 0149](../adr/0149-signed-and-timestamped-audit-checkpoints.md)).
- **SIEM export and archive**: off by default. `AUDIT_EXPORT` sends every event, in order and with its hashes, to up to four SIEMs (JSON lines over HTTPS, syslog over TLS, Microsoft Sentinel, Google SecOps or Datadog) and an S3 archive, write-once under Object Lock unless `AUDIT_EXPORT_S3_LOCK=off`, each resuming from its own cursor; retention waits until every sink has an event ([ADR 0122](../adr/0122-siem-export-and-tamper-evident-audit.md), [ADR 0154](../adr/0154-write-once-s3-audit-archive.md), [ADR 0173](../adr/0173-an-archive-alongside-a-siem.md), [ADR 0191](../adr/0191-several-siems-with-their-own-headers.md), [guide](../ops/audit-export.md)). botd checks the archive against its own log daily, and anyone can check an exported copy without botd with `botctl audit verify-lines` ([ADR 0163](../adr/0163-checking-the-audit-archive.md), [ADR 0183](../adr/0183-daily-check-of-new-archive-objects.md), [ADR 0199](../adr/0199-self-checking-audit-lines.md)). Failing and stopped sinks are audited, shown in the app's audit log and on `/metrics`, with alert rules ([ADR 0273](../adr/0273-stopped-audit-sinks-in-the-app-and-56-delivered.md)). Each month's evidence bundle records the chain checks, checkpoints and whether each sink took every event ([ADR 0261](../adr/0261-audit-integrity-evidence.md)).
- **Pinned people's events**: the details of a pinned person's events (who, IP address, browser, what changed) are kept in their region's chat store, and a sink the operator states is outside that region (`AUDIT_EXPORT_DATA_REGION`) gets those events as sealed rows without the details, which still verify on the chain. A sink with no stated region gets every event whole, and the pin's report says so ([ADR 0316](../adr/0316-audit-details-in-the-regional-store.md), [ADR 0330](../adr/0330-audit-export-held-to-a-pins-region.md)).
- **Not built:** erasing data already exported. An erasure removes the person's details from botd's log, but copies in a SIEM or the archive stay until that store's own retention ends ([ADR 0122](../adr/0122-siem-export-and-tamper-evident-audit.md)).

## Licence key (self-host)

- A signed JWT (EdDSA, Ed25519) checked offline against public keys built into botd. It never calls home ([ADR 0038](../adr/0038-self-host-license-key.md)).
- It sets the number of seats and the edition, with a 14-day grace period after expiry.
- Without a valid licence, no Bot runs, unless `TESTING_MODE=on`. Admins can still sign in to install one ([ADR 0068](../adr/0068-no-free-tier.md)).
- It works the same on an air-gapped server: a test guards that the licence code opens no connection, and `botd license check` says, before an offline upgrade or rollback, whether Bots would still run under the new release ([ADR 0128](../adr/0128-air-gapped-self-host.md), [ADR 0305](../adr/0305-the-license-through-offline-upgrades.md)).
