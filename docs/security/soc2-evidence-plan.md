# SOC 2 Type II evidence plan

What evidence shows each control operating over a Type II observation period, which of it SuperBot already produces, how and how often to collect it, and what is still manual. Part of the [security pack](README.md) and the SOC 2 Type II programme ([#57](https://github.com/CG-Labs/superbot/issues/57)). It builds on the [control mapping](soc2-control-mapping.md), the [readiness checklist](soc2-readiness-checklist.md) and the [policy set](policies/README.md). Design: [ADR 0130](../adr/0130-policy-set-and-type-ii-evidence.md).

**SuperBot is not SOC 2 certified, no SOC 2 audit has started, and no observation period has begun.** This is a plan for collecting evidence once one does. The auditor decides what evidence is enough.

## Why collect continuously

A Type II report covers an observation period, commonly 3 to 12 months, and the auditor tests samples drawn from the whole of it: a few access reviews, a sample of changes, a sample of days' backups. Evidence that wasn't kept at the time can't be made later. Three things in the product make this urgent:

- **GitHub keeps workflow logs and artifacts for a limited time** (90 days by default, and some of this repository's artifacts for 14), so CI evidence must be exported at least monthly.
- **Audit retention can delete events.** If `AUDIT_RETENTION_DAYS` is set, it must cover the period plus a year ([retention](policies/data-classification-and-retention.md#retention)); monthly exports keep a copy either way.
- **Point-in-time state isn't history.** `botctl backups` or the setup checklist show today's settings only, so they are captured on a schedule.

## Where evidence is kept

Outside this public repository, in an access-controlled store the security owner runs, readable by the people who collect and the auditor. One folder per criterion and month (`CC6.3/2027-03/`), each file named for what it is and when it was taken. Exports are kept as produced, with a SHA-256 digest recorded beside each, and nothing is edited after collection. Evidence is kept for the observation period plus at least a year, or longer if the auditor asks. Evidence holding customer data (audit exports carry emails and IP addresses) is Confidential under the [data classification policy](policies/data-classification-and-retention.md#classes).

## The evidence bundle

botd makes one dated bundle per period from what it already records ([ADR 0142](../adr/0142-type-ii-evidence-bundles.md)): `botctl evidence bundle` (`GET /api/evidence/bundle`, admins) on request, and each month by itself with `EVIDENCE_BUNDLES=monthly`, into `EVIDENCE_DIR` (default `DATA_DIR/evidence`, so the server backups carry it off the host), deleted `EVIDENCE_RETENTION_DAYS` after its month (default 760). Every bundle is audited as `evidence.bundle_created` with its manifest's SHA-256, and `SHA256SUMS` in it checks every file. It holds no secret values, chats, prompts, files, names, emails, IP addresses or free-text notes and reasons: people, Bots and machines are named by their ids, which the quarterly access-review CSV maps to people. Snapshots are as of when it was made, the 1st for scheduled ones; events are those of the period.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `access-review.json` | Everyone who can sign in: role and custom role's permissions, status, admin, second factor, last sign-in, Bot access, sessions and API tokens, machine; the report's digest; the MFA policy; the period's account, role, SCIM, team and access-review sign-off events | CC1.3, CC6.1, CC6.2, CC6.3 | CC6.1-1, CC6.2-1, CC6.3-1, CC6.3-2 |
| `changes.json` | Each botd start in the period with its version, and each change of version; policy, encryption, egress, license and tier changes; machine agent upgrades | CC5.1, CC5.2, CC8.1 | CC5.1-1, CC8.1-2 |
| `backups.json` | Server backup, backup encryption and database encryption settings now; every server copy, machine backup, RPO breach and restore in the period, by day | A1.2, A1.3, CC6.7, CC7.5, CC9.1 | A1.2-1, A1.2-2, CC6.7-2 |
| `retention.json` | Retention settings, last passes and legal holds now, and whether audit retention keeps the period plus a year; every pruning pass, hold, erasure and deletion in the period | C1.2, CC6.5 | C1.2-1, CC6.5-1, CC6.5-2 |
| `sign-ins-and-alerts.json` | Sign-ins, failures, second factors, suspicious sign-ins, alerts sent and failed, status incidents and host events, by day | CC6.1, CC6.6, CC7.2 | CC6.1-1, CC7.2-1 |
| `audit-summary.json` | Every audit event in the period counted by action and outcome, with a digest reproducible from the log | CC2.1, CC4.1, CC7.2 | None |

A unit test in [`server/src/evidence.rs`](../../server/src/evidence.rs) checks this table against the code. What the bundle can't hold stays on the calendar: the change-management bundle below, drill artifacts, Alertmanager's history, and every record people keep.

## The change-management bundle

botd can't see GitHub, so code changes have a bundle of their own, made by `superbot-evidence github` from the GitHub API with a read-only token the operator supplies ([ADR 0148](../adr/0148-change-management-evidence-from-github.md)). [`change-evidence.yml`](../../.github/workflows/change-evidence.yml) makes last month's on the 1st with the workflow's own read-only token and keeps it as an artifact for 90 days; anyone can make one for any period with `superbot-evidence github --repo <owner>/<repo> [--from <date> --to <date>]` and `GITHUB_TOKEN` set (a fine-grained token with read access to contents, pull requests, actions, checks and commit statuses). It has the same shape as the evidence bundle: one folder, `superbot-changes-<from>_<to>-<UTC time>/`, with a manifest and `SHA256SUMS`, and the period is whole UTC days, `from` included and `to` not.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `pull-requests.json` | Every pull request merged into `main` in the period: author, merge commit and who merged it, each review's state and commit, approvers other than the author (never a Bot) and whether they approved the last commit, changes still requested at merge, every check on its last commit and which were required, each required check's result at the merge (from the app it must come from) and whether it passed only later, and the CI runs on its merge commit, even ones that started after the period; every update of `main` in the period from GitHub's activity record (merge, push or force push, who and when), and every commit dated in the period with the pull request it came from, or none; and the exceptions: merged without an independent approval, without required checks passing at the merge, with failing checks, or pushed straight to `main` | CC3.4, CC8.1 | CC3.4-1, CC8.1-1, CC8.1-2 |
| `branch-protection.json` | `main`'s rulesets and classic protection as of the export: pull requests required, approvals, required checks, force pushes and deletions blocked, admins included; what the token couldn't read says so | CC8.1 | CC8.1-1 |
| `workflow-runs.json` | Every GitHub Actions run on `main` in the period, counted by workflow and conclusion and by day, the failed ones, and each with its commit, event and url | CC4.1, CC5.2, CC7.1, CC8.1 | CC5.2-2, CC7.1-1, CC7.1-3 |

It holds no token, pull request or review text, comments, commit messages, emails, logs or artifacts; people are named by their GitHub logins, and titles can be left out with `--no-titles`. A unit test in [`server/src/bin/superbot-evidence/changes.rs`](../../server/src/bin/superbot-evidence/changes.rs) checks this table against the code. Logs and artifacts of the runs kept as evidence are still downloaded by hand before GitHub deletes them.

## The vulnerability bundle

The [information security policy](policies/information-security.md#vulnerability-management) has every vulnerability fixed or accepted with a reason within 30 days for Critical and High and 90 for Medium and Low. GitHub keeps the alerts the scans raise, Dependabot's for dependencies and code scanning's for the Grype image scans, so `superbot-evidence vulnerabilities` exports them for a period with each one judged against its window ([ADR 0154](../adr/0154-vulnerability-remediation-evidence.md)). The same workflow makes last month's on the 1st, with read access to code scanning and Dependabot alerts only; anyone can make one for any period with `superbot-evidence vulnerabilities --repo <owner>/<repo> [--from <date> --to <date>]` and a token with read access to Metadata, Contents, Dependabot alerts and Code scanning alerts. A source the token can't read is recorded as unavailable, with GitHub's answer, not left out silently. It has the change-management bundle's shape, in a folder `superbot-vulns-<from>_<to>-<UTC time>/`.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `vulnerability-alerts.json` | Every Dependabot and code scanning alert open at any time in the period: its advisory or rule, package or location, severity, when it was opened and closed, how (fixed, dismissed or dismissed automatically, with the reason's code and who), its due date (opened plus its severity's window; an alert without a severity gets the strictest), and whether it was closed in time, or still open and overdue at the period's end; counted by severity with the median days to close; and the exceptions: closed late, overdue at the end, dismissed without a reason, without a severity | CC4.2, CC7.1 | CC4.2-1, CC7.1-2, CC7.1-3 |
| `accepted-findings.json` | The findings [`.cargo/audit.toml`](../../.cargo/audit.toml) and [`.grype.yaml`](../../.grype.yaml) accept, as of the export, each with its reason, and the file's blob | CC7.1 | CC7.1-2 |

The windows are the policy's unless `--windows` gives others, and the manifest records the ones used. It holds no token, dismissal comments, advisory descriptions, code snippets or alert messages. GitHub keeps only each alert's latest state, so an alert dismissed and reopened shows only its latest closing. Vulnerabilities found outside the scans (reports under [`SECURITY.md`](../../SECURITY.md), penetration tests, vendors) are still tracked by hand. A unit test in [`server/src/bin/superbot-evidence/vulns.rs`](../../server/src/bin/superbot-evidence/vulns.rs) checks this table against the code.

## What is still manual

Most of the remaining work is records people keep, not code: the register (role holders, approvals, acknowledgements, exceptions), training and background checks, the risk register, management review minutes, vendor reviews, incident and change records, and reviews of access outside SuperBot. Product evidence from the server is collected by the monthly [evidence bundle](#the-evidence-bundle), code changes and CI runs by the monthly [change-management bundle](#the-change-management-bundle), and scan findings against their deadlines by the monthly [vulnerability bundle](#the-vulnerability-bundle); copying both to the store, downloading the logs and artifacts of runs kept as evidence, and an admin's quarterly export of branch protection are still tasks for the operator and security owner.

## Before the observation period starts

1. Adopt the [policy set](policies/README.md#adopting-them) and name the role holders.
2. Close or carve out the checklist's **Gap** rows that have no evidence ([readiness checklist](soc2-readiness-checklist.md#before-engaging-an-auditor)).
3. Set up the evidence store, turn on `EVIDENCE_BUNDLES=monthly` on each managed server, and run one full month of the calendar as a dry run, then fix what was hard to collect.
4. Agree the period, the criteria and the sample sizes with the auditor.
