# SOC 2 Type II evidence plan

What evidence shows each control operating over a Type II observation period, which of it SuperBot already produces, how and how often to collect it, and what is still manual. Part of the [security pack](README.md) and the SOC 2 Type II programme ([#57](https://github.com/CG-Labs/superbot/issues/57)). It builds on the [control mapping](soc2-control-mapping.md), the [readiness checklist](soc2-readiness-checklist.md) and the [policy set](policies/README.md). Design: [ADR 0130](../adr/0130-policy-set-and-type-ii-evidence.md).

**SuperBot is not SOC 2 certified, no SOC 2 audit has started, and no observation period has begun.** This is a plan for collecting evidence once one does. The auditor decides what evidence is enough.

## Why collect continuously

A Type II report covers an observation period, commonly 3 to 12 months, and the auditor tests samples drawn from the whole of it: a few access reviews, a sample of changes, a sample of days' backups. Evidence that wasn't kept at the time can't be made later. Three things in the product make this urgent:

- **GitHub keeps workflow logs and artifacts for a limited time** (90 days by default, and some of this repository's artifacts for 14), so CI evidence must be exported at least monthly.
- **Audit retention can delete events.** If `AUDIT_RETENTION_DAYS` is set, it must cover the period plus a year ([retention](policies/data-classification-and-retention.md#retention)); monthly exports keep a copy either way.
- **Point-in-time state isn't history.** `botctl backups` or the setup checklist show today's settings only, so they are captured on a schedule.

## Where evidence is kept

Outside this public repository, in an access-controlled store the security owner runs, readable by the people who collect and the auditor. One folder per criterion and month (`CC6.3/2027-03/`), each file named for what it is and when it was taken. Exports are kept as produced, with a SHA-256 digest recorded beside each, and nothing is edited after collection. Evidence is kept for the observation period plus at least a year, or longer if the auditor asks. Evidence holding customer data (audit exports carry emails and IP addresses) is Confidential under the [data classification policy](policies/data-classification-and-retention.md#classes).

## The evidence bundle

botd makes one dated bundle per period from what it already records ([ADR 0142](../adr/0142-type-ii-evidence-bundles.md)): `botctl evidence bundle` (`GET /api/evidence/bundle`, admins) on request, and each month by itself with `EVIDENCE_BUNDLES=monthly`, into `EVIDENCE_DIR` (default `DATA_DIR/evidence`, so the server backups carry it off the host), deleted `EVIDENCE_RETENTION_DAYS` after its month (default 760). Every bundle is audited as `evidence.bundle_created` with its manifest's SHA-256, and `SHA256SUMS` in it checks every file. It holds no secret values, chats, prompts, files, names, emails, IP addresses or free-text notes and reasons: people, Bots and machines are named by their ids, which the quarterly access-review CSV maps to people. Snapshots are as of when it was made, the 1st for scheduled ones; events are those of the period.

|------|---------------|----------|----------------|

The manifest names `audit-integrity.json`'s rows only while they held for the whole period: CC2.1-2 while every export sink has delivered the period's last event and none started past an event of the period or came back with its events deleted, even if that was recorded after it, and CC7.2-2 while, as well, no check or checkpoint gap was found, the last whole check by the period's end and the latest one when the bundle is made both passed, and checkpoints are on; neither is named if the bundle couldn't read the whole period. So a month the log wasn't guarded or shipped is a gap in the coverage report. A stretch counts only while botd was writing events, so a server that was down isn't a gap here (the uptime bundle shows that). A check is taken against the checkpoint interval set when the bundle is made.

`egress.json` and `secrets.json` name their rows the same way. CC6.8-2 is named only while machines are on, at least one is running, the server's policy was an allow-list all period, no user with a machine was let out on their own during it, no running machine is open now, and the period's policy changes were read whole; a machine that hasn't loaded its list yet doesn't stop it, since botd runs nothing there until it has. CC6.1-4 is named only while every botd start in force used an external manager and the period's starts were read whole; a start recorded before botd wrote its backend counts as unknown, so the first month after an upgrade doesn't name it, and so does the time before the period's first start when no earlier one is on record (a new server, or one whose earlier start retention pruned).

A unit test in [`server/src/evidence.rs`](../../server/src/evidence.rs) checks this table against the code. What the bundle can't hold stays on the calendar: the change-management, vulnerability, drill, uptime and alerts bundles below, drill artifacts, and every record people keep.

## The change-management bundle

botd can't see GitHub, so code changes have a bundle of their own, made by `superbot-evidence github` from the GitHub API with a read-only token the operator supplies ([ADR 0148](../adr/0148-change-management-evidence-from-github.md)). [`change-evidence.yml`](../../.github/workflows/change-evidence.yml) makes last month's on the 1st with the workflow's own read-only token and keeps it as an artifact for 90 days; anyone can make one for any period with `superbot-evidence github --repo <owner>/<repo> [--from <date> --to <date>]` and `GITHUB_TOKEN` set (a fine-grained token with read access to contents, pull requests, actions, checks and commit statuses). It has the same shape as the evidence bundle: one folder, `superbot-changes-<from>_<to>-<UTC time>/`, with a manifest and `SHA256SUMS`, and the period is whole UTC days, `from` included and `to` not.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `pull-requests.json` | Every pull request merged into `main` in the period: author, merge commit and who merged it, each review's state and commit, approvers other than the author (never a Bot) and whether they approved the last commit, changes still requested at merge, every check on its last commit and which were required, each required check's result at the merge (from the app it must come from) and whether it passed only later, and the CI runs on its merge commit, even ones that started after the period; every update of `main` in the period from GitHub's activity record (merge, push or force push, who and when), and every commit dated in the period with the pull request it came from, or none; and the exceptions: merged without an independent approval, without required checks passing at the merge, with failing checks, or pushed straight to `main` | CC3.4, CC8.1 | CC3.4-1, CC8.1-1, CC8.1-2 |
| `branch-protection.json` | `main`'s rulesets and classic protection as of the export: pull requests required, approvals, required checks, force pushes and deletions blocked, admins included; what the token couldn't read says so. Judged against the [change management policy](policies/change-management.md#reviews-and-segregation-of-duties) ([ADR 0303](../adr/0303-branch-protection-judged-against-the-policy.md)): each of its settings (an approval required, status checks required, force pushes blocked, deletion blocked, administrators included) met, not met or unknown, where it is enforced (each ruleset, classic protection, or the required checks the branch shows), and every ruleset the rules come from with who can bypass it; and the exceptions: settings not met, settings the token couldn't see, and who can bypass them (each ruleset's bypass actors by type, id and mode; classic protection not including administrators, or allowing some to bypass its pull request rules) | CC8.1 | CC8.1-1 |
| `workflow-runs.json` | Every GitHub Actions run on `main` in the period, counted by workflow and conclusion and by day, the failed ones, and each with its commit, event and url | CC4.1, CC5.2, CC7.1, CC8.1 | CC5.2-2, CC7.1-1, CC7.1-3 |

The manifest names CC8.1-1, for both `pull-requests.json` and `branch-protection.json`, only while the protection meets the policy as the token saw it at the export; otherwise `pull-requests.json` still names CC3.4-1 and CC8.1-2 (the changes are there to sample) and `branch-protection.json` names nothing, so a month whose protection fell short, or couldn't be seen, is a gap in the coverage report rather than covered. A setting is met when a ruleset or classic protection enforces it with nobody able to bypass it there; it is unknown, not met, while something that might enforce it is hidden from the token. GitHub shows classic protection only to tokens with Administration read, and a ruleset's bypass list only to tokens that can edit the ruleset, so the workflow's own token can't judge administrators included: give the workflow a `CHANGE_EVIDENCE_TOKEN` secret (a fine-grained token with read-only Administration, Contents, Pull requests, Actions, Checks and Commit statuses) for classic protection with administrators included, or have an admin make the month's bundle where rulesets protect `main`. Protection is judged as it stood at the export, not through the month: the month's exceptions (merged without an approval or checks, pushed straight to `main`) show a lapse during it. It holds no token, pull request or review text, comments, commit messages, emails, logs or artifacts; people are named by their GitHub logins, and titles can be left out with `--no-titles`. A unit test in [`server/src/bin/superbot-evidence/changes.rs`](../../server/src/bin/superbot-evidence/changes.rs) checks this table against the code. Logs and artifacts of the runs kept as evidence are still downloaded by hand before GitHub deletes them.

## The vulnerability bundle

The [information security policy](policies/information-security.md#vulnerability-management) has every vulnerability fixed or accepted with a reason within 30 days for Critical and High and 90 for Medium and Low. GitHub keeps the alerts the scans raise, Dependabot's for dependencies and code scanning's for the Grype image scans, so `superbot-evidence vulnerabilities` exports them for a period with each one judged against its window ([ADR 0086](../adr/0086-vulnerability-remediation-evidence.md)). The same workflow makes last month's on the 1st, with read access to code scanning and Dependabot alerts only; anyone can make one for any period with `superbot-evidence vulnerabilities --repo <owner>/<repo> [--from <date> --to <date>]` and a token with read access to Metadata, Contents, Dependabot alerts and Code scanning alerts. A source the token can't read is recorded as unavailable, with GitHub's answer, not left out silently. It has the change-management bundle's shape, in a folder `superbot-vulns-<from>_<to>-<UTC time>/`.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `vulnerability-alerts.json` | Every Dependabot and code scanning alert open at any time in the period: its advisory or rule, package or location, severity, when it was opened and closed, how (fixed, dismissed or dismissed automatically, with the reason's code and who), its due date (opened plus its severity's window; an alert without a severity gets the strictest), and whether it was closed in time, or still open and overdue at the period's end; counted by severity with the median days to close; and the exceptions: closed late, overdue at the end, dismissed without a reason, without a severity | CC4.2, CC7.1 | CC4.2-1, CC7.1-2, CC7.1-3 |

## The drill bundle

A1.3 asks for recovery tested, and the evidence was scattered: CI's drill runs in `workflow-runs.json` with no word on the drill step itself, their timing in artifacts GitHub deletes, and the operator's drills in saved terminal output. `superbot-evidence drills` puts a period's drills in one bundle ([ADR 0177](../adr/0177-restore-drill-evidence.md)). The same workflow makes last month's on the 1st from CI alone; anyone can make one for any period with `superbot-evidence drills --repo <owner>/<repo> [--record <saved drill output>]... [--from <date> --to <date>]` and a token with read access to Metadata and Actions, or with `--no-ci` and records only, with no token or network. A workflow the token can't read is recorded as unavailable, with GitHub's answer. It has the change-management bundle's shape, in a folder `superbot-drills-<from>_<to>-<UTC time>/`.

The drills CI runs, each on the workflow's runs on the branch: `server-restore`, the installer's server backup restored onto a fresh host within its RTO and RPO budgets (`backup-drill` in `server.yml`); `compose-restore`, every Compose volume deleted and restored within its budget (`compose-smoke` in `docker.yml`); `machine-restore`, an Incus container restored from its off-host backup within its tier's RTO, with its `restore-drill-*` artifact; and `host-loss`, a lost host's container restored onto another host, with its `host-drill-*` artifact (both in `incus-e2e.yml`, one per Incus version). The operator's drills are `server-restore` ([`deploy/backup-drill.sh`](../../deploy/backup-drill.sh)) and `machine-restore` ([`deploy/machine-restore-drill.sh`](../../deploy/machine-restore-drill.sh)): each prints a record line when it finishes, passed or not, and `--record` reads the last one from the saved output.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `ci-drills.json` | Every run of each CI drill on the branch in the period, by matrix job (jobs that skip the drill, such as Incus versions botd refuses, are only counted): the drill step's result (passed, failed, cancelled, not reached), when it started and how long it took, the run's commit, event and url, and the job's own drill artifacts (name, size, GitHub's digest, expiry); counted by drill with the median and longest passing time; and the exceptions: not run in the period, run but never passed, failing at the period's end in any matrix variant, failed, drill step not found, passed without its artifact, artifacts already expired | A1.2, A1.3 | A1.3-1 |
| `operator-drills.json` | Every drill record given, which must have finished in the period: the drill, when it finished, whether it passed, how long the restore took against its objective (botd's recorded restore time and the tier's RTO, or the server drill's timed restore and its budget, with the next backup against the RPO), the restore and backup ids, and the saved output's name, size and SHA-256; and the exceptions: failed, over the objective | A1.3, CC9.1 | A1.3-1, CC9.1-2 |

The manifest maps a file to its criteria and rows only when it holds at least one drill, so a month without any shows as a gap in the coverage report rather than as covered. It holds no token, logs, artifacts' contents, or any of a drill's output but its record line's known fields: keep each saved output beside the bundle, where its SHA-256 identifies it, and download the artifacts kept as evidence before GitHub deletes them. A passing CI step is the drill's verdict: each drill fails its step when the restore takes longer than its objective, so the step's duration, which includes setting up, is an upper bound on the restore. ## The register bundle

## The uptime bundle

A1.1-3 asks for uptime measured against the [SLO](../slo.md), and the SLO makes the outside probe of `/status.json` the measure of record: botd can't count its own downtime. The probe's results sat in Prometheus or a hosted checker, kept for as long as they keep them, with no monthly report. `superbot-evidence uptime` turns a period of the probe's checks into a bundle ([ADR 0249](../adr/0249-uptime-evidence-from-the-outside-probe.md)). With `--prometheus <url>` it reads the blackbox exporter's raw samples of `--query` (default `probe_success{job="superbot-status"}`, the probe [deploy/README.md](../../deploy/README.md#status-page-and-slo-alerts) sets up) a day at a time, with a token from `PROMETHEUS_TOKEN` if Prometheus needs one; with `--checks <file>...` it reads any other probe's export instead, one check a line (`<time>,<result>[,<location>]`), with no network. `--objective` is the server's objective (default 99.9%, the strictest plan on a shared server, as the burn-rate rules), and each `--maintenance <from>/<to>` a window of maintenance announced on the status page. It has the change-management bundle's shape, in a folder `superbot-uptime-<from>_<to>-<UTC time>/`, and its manifest records where the checks came from (the query, or each file's SHA-256).

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `uptime.json` | Each calendar month in the period and the whole period: its minutes, down minutes (a minute with checks that all failed, from any location), unmeasured minutes (no check), maintenance minutes excused (those starting in an announced window, up to 4 hours a month) and down minutes inside them, the availability (the share of minutes that weren't down) and measured share, and against the objective and each plan's (Starter 99.5%, Pro and Max 99.9%, Enterprise 99.95%) whether it was met, the error budget in minutes and how much was spent; every outage (a run of down minutes), with its share of the 30-day error budget and whether it spent more than a quarter of it and so needs a written review; each day's down, unmeasured and maintenance minutes; each probe series (by job and location, never its target) with its checks and failures; the gaps of 5 minutes or more in the probe's record; and the exceptions: the objective missed, half the error budget or more spent, outages needing a written review, down at the period's end, probe gaps, probe gaps longer than the error budget, maintenance past 4 hours | A1.1 | A1.1-3 |

A minute is down only when every check in it failed: one check that answered means users could reach the service. Unmeasured minutes aren't down, as the SLO counts them, so the manifest maps the file to its criteria and row only while the period's unmeasured minutes fit in the objective's error budget: a month the probe didn't watch well enough to show the objective was met or missed is a gap in the coverage report, not evidence. The bundle can't tell that a maintenance window was announced 48 hours ahead, outside business hours: check each against its status page note. Outages that need a written review are reviewed under the [incident response plan](policies/incident-response.md#post-incident-review) and recorded in the [policy register](policy-register.md#incidents) as error-budget outages, which the register bundle's `incidents.json` checks. It holds no token, Prometheus address or probe target, and no label but the job and location: keep the probe's own export (or the checks files, by SHA-256) beside it. A unit test in [`server/src/bin/superbot-evidence/uptime.rs`](../../server/src/bin/superbot-evidence/uptime.rs) checks this table against the code, and the objectives against the SLO.

## The alerts bundle

CC2.1-1, CC7.2-1 and A1.1-1 ask for alert history beside the rules: what the shipped [alert rules](../../deploy/prometheus/) fired on a running server, and that they were running at all. That history lived only in the operator's Prometheus, kept 15 days by default, and Alertmanager keeps only what is active now. `superbot-evidence alerts` turns a period of it into a bundle ([ADR 0288](../adr/0288-alert-history-evidence-from-prometheus.md)). With `--prometheus <url>` (a token, if needed, from `PROMETHEUS_TOKEN`, as for the uptime bundle) it reads, a day at a time, the raw samples of `ALERTS{alertstate="firing"}`, Prometheus' own record of every alert while it fires, and of `--watch` (default `up{job="superbot"}`, botd's scrape, which every shipped rule reads); the alerting rules loaded as the bundle is made; and, where Prometheus scrapes Alertmanager, its notification counters each day. The rules expected are those `deploy/prometheus/` ships, or with `--rules <file>...` the files the operator loads, recorded by SHA-256. It has the change-management bundle's shape, in a folder `superbot-alerts-<from>_<to>-<UTC time>/`.

| File | What it shows | Criteria | Checklist rows |
|------|---------------|----------|----------------|
| `alerts.json` | Every SuperBot alert that fired in the period, as episodes (samples of one series no more than 5 minutes apart): the alert, its severity, a digest of its labels, when it started and was last seen, its minutes, and whether it was firing at the period's start or end; each expected rule with its file, severity, whether it is loaded, in which group, healthy and evaluated in the last 10 minutes when the bundle is made, the severity it is loaded with, and its episodes and firing minutes in the period; the stretches of more than 5 minutes Prometheus had no sample of botd's scrape, when no alert could fire, by month (against the 99.9% error budget) and day; Alertmanager's notifications sent and failed by integration each day, or none recorded; and the exceptions: every page, episodes firing more than a day, alerts still firing at the end, watch gaps and months whose gaps exceed the budget, rules unreadable, not loaded, failing, not evaluated or loaded with another severity, notifications failed, and days with no notifications recorded | CC2.1, CC7.2, A1.1 | CC2.1-1, CC7.2-1, A1.1-1 |

The manifest maps the file to its criteria and rows only while the unwatched minutes fit in the 99.9% error budget and every expected rule is loaded, healthy and evaluated, so a month Prometheus wasn't watching botd, or wasn't running the rules, is a gap in the coverage report rather than a quiet month. The rules are judged as of the bundle's making, not through the period: make it in the first days of the next month. Each page needs its response on record, a ticket or an incident in the [policy register](policy-register.md#incidents): the bundle is the list to sample from, not the response. It holds no token, Prometheus address, rule file paths, rule expressions or errors, and no alert label but its name, severity, job and the ones the shipped rules group by that never name a host (`harness`, `route_class`, `provider`, `tier`); others, such as `instance` and `host`, go only into the series' digest. ## Checking the store's coverage

Seven tools make the bundles above on their own schedules, and a month lost from any of them can't be made later. `superbot-evidence coverage` reads every bundle in the store, as a `.tar` or unpacked, at any depth, and reports on a period ([ADR 0169](../adr/0169-evidence-coverage-report.md)). It needs no token or network and never writes into the store.

- **Each bundle is checked** against its `SHA256SUMS` and manifest: every listed file exists with its digest, no file was added, the manifest's kind and period match the bundle's name, and every file its kind always has is there. A file changed after the bundle was made fails it, even with `SHA256SUMS` rewritten to match. The report lists each manifest's SHA-256 to compare with what was recorded when it was made.
- **Coverage is by day**: for each kind of bundle month by month (complete, partial or missing), and for each checklist row and criterion a bundle names, the days of the period a bundle that checks covers and the gaps. With `--checklist`, also the rows no bundle collects evidence for: their evidence is records people keep.
- It warns about bundles made more than 7 days after their period (their snapshots are of then) or before it ended, and counts the exceptions in each change-management, vulnerability, drill, register, uptime and alerts bundle, and in each evidence bundle's `baseline.json` and `audit-integrity.json`.

It exits 0 when every bundle checks and every kind covers every day, and 2 when not, so it can run on a schedule beside the store. A complete report says evidence was kept for each day, not that the controls worked.

## Testing samples

A Type II auditor doesn't read every record: they take each control's population for the period, draw a sample, and test each item drawn. The bundles above already hold most of those populations, so `superbot-evidence sample` draws the samples the same way, for a readiness assessment, a dry run or the operator's own quarterly testing ([ADR 0296](../adr/0296-control-testing-samples-from-the-evidence-store.md)). It is not the audit: the auditor chooses their own populations, sizes and samples, and may use these or not.

`superbot-evidence sample <store> --from <period start> --to <period end>` reads every bundle in the store as [coverage](#checking-the-stores-coverage) does and gathers each test's population from the bundles that check: every item dated in the period, an item listed in more than one bundle taken from the newest. A store may hold several repositories' and servers' bundles: pull requests and alerts are named with their repository (`<owner>/<name>#<number>`), and a day of backups with its bundle's name and manifest digest, so none is mistaken for another, and each repository's days are checked on their own (a gap names its `repository`). Evidence bundles don't name their server, so one server's month can't be told missing beside another's: run `sample` on each server's evidence separately. Register bundles of later periods are read too, since each carries a change or a finding still open at its start with its later state. A population is incomplete when a bundle of its kind failed its digests (a tar too damaged to tell its kind counts against every population), lacks the file, or couldn't read one of its sources (a vulnerability bundle whose token GitHub refused Dependabot or code scanning alerts), or the period has days no bundle of that kind covers; the samples say which, so a sample from an incomplete population isn't mistaken for one from the whole.

| Test | Population | What the tester checks on each item | Checklist rows |
|------|------------|-------------------------------------|----------------|
| `merged-pull-requests` | Pull requests merged into the main branch, from each change-management bundle's `pull-requests.json` | On GitHub: approved by someone other than its author before the merge, on its last commit; its required checks passed; a change to a control carries its ADR and the pack's update | CC3.4-1, CC8.1-1, CC8.1-2 |
| `production-changes` | Production and emergency changes made, from each register bundle's `production-changes.json` | The change record: approved beforehand by someone else (an emergency change by the incident's commander, then reviewed and followed by a pull request); announced if it could interrupt the service; checked afterwards | CC8.1-2 |
| `access-grants` | Grants of production access, from each register bundle's `access.json` | The written request and approval, by the right roles and not the grantee, on or before the grant; the level on the system is the level approved; a leaver's access removed in time | CC6.2-2 |
| `access-reviews` | Reviews of production access, from each register bundle's `access.json` | The user list and sign-off: every account judged, MFA recorded, findings fixed by their due dates; a managed server's review matched to its `access_review.completed` event | CC6.1-2, CC6.3-2 |
| `security-events` | Security events detected, from each register bundle's `incidents.json` | The ticket: triaged in time by the commander recorded, handled as the [incident response plan](policies/incident-response.md) says; a possible breach's notice sent within the DPA's hours; the written review, with its actions done | CC7.3-1, CC7.4-1, CC7.4-2, CC7.5-1 |

Each sample's size follows how often the control runs, as auditors commonly size them: 1 from a population of 1 (yearly), 2 of up to 12 (quarterly or monthly), 5 of up to 52 (weekly), and 25 of more (daily or per event), never more than the population; `--size <test>=<n>` sets the size the auditor agrees instead. The selection can be re-performed by anyone with the store: every item is ranked by the SHA-256 of the seed, the test and its id, and the lowest ranks are the sample. The seed is the SHA-256 of the period and every population's own SHA-256, so the same store always gives the same samples and nobody can pick items without changing the evidence; `--seed <text>` uses the auditor's instead, and the bundle records which. A unit test in [`server/src/bin/superbot-evidence/sample.rs`](../../server/src/bin/superbot-evidence/sample.rs) checks this table against the code.

It writes a bundle `superbot-samples-<from>_<to>-<UTC time>/` with the change-management bundle's shape: `samples.json` (each test's population size, SHA-256, bundles and missing days, the seed and sizes, and every item drawn with its rank and the fields to test it by, copied from the bundle it came from) and `worksheet.csv`, one line for each item drawn. It copies no notes, titles or names, only what the bundles already hold, and writes nothing into the store: keep the samples and results bundles beside it.

The tester fills in each line's `result` (`pass`, `fail` or `n/a`), `tester` (their register id), `tested_on`, and `reference` (the ticket, record or SHA-256 they looked at), with any `notes`. `superbot-evidence results <samples bundle> <worksheet.csv>` checks the worksheet against the samples bundle (refusing items it didn't draw, an item twice, a column twice, a result or tester it can't read, and days in the future) and writes a bundle `superbot-results-<from>_<to>-<UTC time>/` with `results.json`: each test's results and conclusion, and the exceptions: deviations, deviations with no reference, items not tested, items marked not applicable, items tested before the samples were drawn, and populations that were incomplete. The worksheet's notes stay out; its SHA-256 is recorded, so keep the filled-in worksheet beside the bundle. It exits 0 when every item was tested, none deviated and every population was complete, and 2 when not. Each deviation is a deficiency to evaluate under CC4.2 and record in the [policy register](policy-register.md) with an owner and a due date: as a risk, or as an `internal` finding where it is a vulnerability; results that pass say the samples drawn passed, not that the control is designed well or that an auditor would conclude the same.

## What is still manual

Most of the remaining work is records people keep, not code: the [policy register](policy-register.md) (role holders, approvals, acknowledgements and training, the risk register, management reviews, vendor reviews, exceptions, conduct concerns, incidents and tabletops, production access and its reviews, vulnerabilities outside the scans and penetration tests, production and emergency changes), which the monthly [register bundle](#the-register-bundle) checks against the policies' cadences but people must keep true, background checks, management review minutes, the incident tickets, notices and reviews the register points to, change records, and the user lists exported for reviews of access outside SuperBot. Product evidence from the server is collected by the monthly [evidence bundle](#the-evidence-bundle), code changes and CI runs by the monthly [change-management bundle](#the-change-management-bundle), scan findings against their deadlines by the monthly [vulnerability bundle](#the-vulnerability-bundle), restore drills by the monthly [drill bundle](#the-drill-bundle), uptime against the SLO by the monthly [uptime bundle](#the-uptime-bundle), alert history by the monthly [alerts bundle](#the-alerts-bundle), and the register by the monthly [register bundle](#the-register-bundle); running the operator's drills and saving their output, copying them to the store and checking its [coverage](#checking-the-stores-coverage) each month, downloading the logs and artifacts of runs kept as evidence, and an admin's quarterly export of branch protection are still tasks for the operator and security owner. [Testing samples](#testing-samples) draws what to test and checks the worksheet, but testing each item is a person's work, and so is finding someone independent of the controls to do it.

## Before the observation period starts

1. Adopt the [policy set](policies/README.md#adopting-them), name the role holders and start the [policy register](policy-register.md) from its template.
2. Close or carve out the checklist's **Gap** rows that have no evidence ([readiness checklist](soc2-readiness-checklist.md#before-engaging-an-auditor)).
3. Set up the evidence store, turn on `EVIDENCE_BUNDLES=monthly` on each managed server, and run one full month of the calendar as a dry run, then fix what was hard to collect, until `superbot-evidence coverage` reports the month complete.
4. Test the dry run's samples ([testing samples](#testing-samples)) and fix what deviated, then agree the period, the criteria and the sample sizes with the auditor.
