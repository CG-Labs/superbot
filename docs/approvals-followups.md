# Approvals follow-ups

Work left after the approvals MVP ([ADR 0007](adr/0007-approvals.md)). Each item is meant to become one GitHub issue.

1. **End-to-end hook tests against real CLIs.** Done: the real Claude Code, Codex, Pi, and Hermes Agent CLIs, at the versions machines install (`server/src/adapters/install.rs`), run through `botd`'s approvals with a fake model each reaches through its own custom-endpoint setting. An allowed call runs, a call a deny rule matches is blocked, and a `git push` waits, then runs once approved or fails once denied. The `harness-e2e` workflow runs them on changes to the hook path, weekly, and by hand; `deploy/harness-e2e.sh` runs the same checks against real models on a logged-in server. The oldest Codex that runs hooks in `codex exec` is 0.141.0, and CI tests it too ([ADR 0057](adr/0057-harness-hook-e2e-tests.md)). A guarded run on an older Codex, or one whose version can't be read, is refused before it starts, on the server and on users' machines, with the fix in chat and `bot.run_refused` in the audit log; the canary stays as a backstop ([ADR 0059](adr/0059-refusing-guarded-runs-on-old-codex.md)).
2. **Run harnesses as a separate OS user.** Done: each user's Bots run as their own Unix account on every harness (Claude Code, Codex, Pi, Hermes Agent), which can't read `.env`, the database, the master key or `DATA_DIR`. On for new installs with `deploy/install.sh` and Docker Compose; installs from before keep it off until an admin opts in. Machines already run Bots as their own user ([ADR 0058](adr/0058-harness-os-user-by-default.md), [ADR 0037](adr/0037-per-user-unix-accounts.md), [ADR 0043](adr/0043-bots-own-os-user-on-machines.md)).
3. **Per-Bot tokens.** Done: each Bot run gets its own `BOT_TOKEN`, and `from` must be the Bot itself ([ADR 0029](adr/0029-per-user-isolation.md)).
4. **Policy editor in the apps.** Done: the client edits the mode, class actions, the timeout, and the rules (view, add, delete), globally and per Bot, with a Bot's fields put back to the default one at a time; the console's Settings does the same for all Bots; admins change, everyone else reads ([ADR 0049](adr/0049-policy-editor-in-the-apps.md)).
5. **Audit export.** Done: CSV export, filters, and a viewer in the web app ([ADR 0009](adr/0009-audit-events.md)). The Expo client has no viewer yet.
6. **Notifications.** Done: a pending approval reaches people by email (through the admin's SMTP server) and an outgoing webhook (Slack-compatible, or signed JSON), set for all Bots and per Bot, with a Bot's own webhook URL; email goes to listed addresses and the Bot's owner and operators. Each notice links to the approval in the client and to its audit trail in the console, shows only what the approval card shows (or less), waits 30 seconds so answered approvals send nothing, goes once per approval, and folds bursts into a digest; every send and failure is audited. Off until an admin turns it on, in the app's policy editor or the console ([ADR 0060](adr/0060-approval-notifications.md)). Left: mobile push, M3 ([#36](https://github.com/CG-Labs/superbot/issues/36)), which plugs into the same notifier.
7. **Smarter command analysis.** Done: scripts the Bot runs from its workspace (`./x.sh`, `bash x.sh`, `source`, `python x.py`, `node x.js`, Ruby, Perl, PHP) and inline code (`-c`, `-e`, here-documents, text piped into an interpreter) are read and classified like the command line; scripts that can't be read ask; decoded or piped code (`base64 -d | sh`, `eval "$(…)"`, `make | sh`) asks one call at a time ([ADR 0053](adr/0053-smarter-command-analysis.md)). Left: reading scripts on a user's machine (they ask), and a real parser for languages other than shell (they're scanned).
8. **Approve once per run.** Done: "Approve for this run" approves the call and, until that run ends, later calls of the same kind from the same Bot in the same run; it saves no rule, deny rules and deny classes still win, and some calls (destructive shell commands, downloaded scripts, typed input) can only be approved one at a time ([ADR 0051](adr/0051-approve-once-per-run.md)).
9. **Sandbox defaults.** Done: a `sandbox` policy setting, global and per Bot, turns on the harness's own sandbox on top of approvals. Codex runs in `workspace-write` with the network on; Claude Code gets its Bash sandbox. Pi and Hermes Agent have none to turn on. On for new installs; installs from before keep it off until an admin turns it on ([ADR 0055](adr/0055-harness-sandbox-defaults.md)).
10. **Pi canary coverage.** The unguarded-run canary keys off shell tool names (`bash`, `shell`, and Hermes's `terminal`). Extend it to every tool once each harness reports hook calls reliably.
