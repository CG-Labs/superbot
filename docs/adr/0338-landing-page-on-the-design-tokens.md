# 0338: The landing page on the design tokens

## Status

Accepted (26 Nov 2026). The landing page slice of the UI overhaul workstream ([roadmap](../ROADMAP.md#ui-overhaul-grok-bot-aligned)), on the design system of [ADR 0335](0335-design-system-for-the-app-and-the-console.md).

## Context

SuperBot has two landing pages. `site/index.html` is the one every server shows at `/`, next to the "Get started" form ([ADR 0022](0022-landing-and-signups.md)); botd embeds it and the installer serves it from disk. The public site's landing page is generated by `superbot-site` ([ADR 0119](0119-public-site-and-docs-portal.md)), with the docs portal around it. Both used `site/assets/site.css`, which had its own dark-first, cool grey colours, and the two pages carried separate copies of the same marketing copy. Since ADR 0335 the app and the console use one set of tokens; the site was the last surface on its own palette.

## Decision

- **The same tokens.** `npm run tokens` (in `apps/client`) writes the token block into `site/assets/site.css` as well as `web/styles.css`, and `npm run tokens:check` fails CI when either disagrees with `tokens.json`; the client workflow now also runs when `site.css` changes. Every colour, spacing step, radius, type size and motion duration in `site.css` and the docs portal's `docs.css` comes from the block. Only the display headings are larger than the app's type scale. Light and dark follow the browser's setting, like the console, with no switch and no script.
- **One copy of the shared sections.** The product picture, the value rows (an AI computer per person, single sign-on and security, self-hosting and air-gapped installs), the feature grid and the security strip are written once, in `site/index.html`, between `<!-- shared:NAME:start -->` and `<!-- shared:NAME:end -->` markers. `superbot-site` takes those blocks into the public landing page and points their `/site/` asset paths at `assets/`; a missing marker fails the build. Each page keeps its own hero call to action (Get started on a server, the install guide on the public site), and only the public site has plans, documentation links and "Contact sales".
- **No invented facts.** No customer logos, quotes, metrics or prices. Every claim is something SuperBot does today, with the plans' prices still "to be published" (the test that checks for currency signs still runs). The product picture is drawn in HTML and CSS (no screenshots to go stale, nothing to download) and hidden from screen readers.
- **Accessible and light.** Landmarks, a skip link, real headings, visible focus, and text that meets WCAG AA in both schemes, checked with axe-core on both landing pages, the form and a docs page, at desktop and phone widths. The server's landing page still runs no scripts, and the pages meet the server's content security policy (no inline styles or scripts). Docs tables, which scroll sideways on phones, can now be reached by keyboard.

## Alternatives considered

- **Generating the server's landing page from Rust too**: one generator for both, but botd embeds `site/` at compile time and the installer serves it from a checkout or an offline bundle, so the page would need a build step in each of those paths. Markers in a hand-written page keep it a plain file.
- **A theme switch**: one more script and stored setting for a choice the browser already makes; the app and the console follow the system too.
- **Customer logos or a metrics strip**: we have none we can publish, so the trust strip lists security facts instead.

## Consequences

- A palette or spacing change to `tokens.json` plus `npm run tokens` now reaches the app, the console, both landing pages and the docs portal.
- Marketing copy in the shared sections is edited in `site/index.html`; the public site picks it up on its next build.
