# 0137: Signed SAML AuthnRequests and single logout

## Status

Accepted. The second M5 slice of full SAML ([#52](https://github.com/CG-Labs/superbot/issues/52), [roadmap](../ROADMAP.md#m5--enterprise)). Builds on [ADR 0127](0127-native-saml-service-provider.md) and keeps its narrow XML-DSig verifier. Setup guide: [native SAML](../sso/saml-native.md#single-logout).

## Context

ADR 0127 shipped a native SAML service provider and left out signed AuthnRequests and single logout (SLO), among other things. Some IdPs (often ADFS and PingFederate setups, and Okta or Entra ID apps an admin locked down) want signed AuthnRequests and refused us. Without SLO, signing out of the IdP left SuperBot sessions open for up to their idle or maximum age, and signing out of SuperBot left the IdP session open, so the next sign-in went through without a password. Security reviews ask for both.

Signing needs a private key we hold. The redirect binding signs the URL query, not the XML ([SAML Bindings](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf) 3.4.4.1), so its signature is detached and checked differently from the enveloped signatures in ADR 0127. Logout messages are attacker-reachable URLs that end sessions, so they need the same care as the ACS: signatures, issuer, destination, freshness, and replay.

## Decision

**An SP key per native provider.** Each native SAML provider has an RSA-3072 key and a self-signed certificate. botd makes one the first time it's needed and keeps it in its settings, the key sealed with the master key ([ADR 0116](0116-database-encrypted-at-rest.md)) and the certificate valid for 20 years, so it never expires under a running deployment (IdPs keep the copy they imported, and SAML does not use the certificate's dates for trust). Making it is audited as `sso.saml_sp_key_created` with the certificate's SHA-256. Master-key rotation seals it again like every other sealed value, so the certificate stays the same; `SUPERBOT_FORGET_SEALED` drops one the key can't open together with its certificate, and the next one is made afresh. Operators who need their own key set `SSO_<ID>_SP_CERT_FILE` (PEM, read and checked at startup) and the key as the provider's secret, `SSO_<ID>_PRIVATE_KEY` (PKCS #8 PEM, env, `_FILE`, or `botctl secret set`); the provider isn't offered until the key is there and matches the certificate. SP metadata publishes the certificate as a signing `KeyDescriptor` and our SLO URL for both bindings. Without a database, metadata has neither and SLO is off.

**Signed AuthnRequests, per provider.** `SSO_<ID>_SIGN_REQUESTS=true` signs each AuthnRequest over HTTP-Redirect with RSA-SHA256: the signature covers `SAMLRequest=…&RelayState=…&SigAlg=…` exactly as sent, and the metadata says `AuthnRequestsSigned="true"`. Off by default, since most IdPs don't check it. IdP metadata with `WantAuthnRequestsSigned="true"` is still refused when it is off, now with the setting to turn on.

**Single logout at `/api/auth/sso/{id}/slo`,** for IdPs whose metadata has an HTTP-Redirect `SingleLogoutService` on https:

- **At sign-in** botd keeps, with each session it makes from a native SAML assertion, the NameID as sent (with its format and qualifiers) and the `AuthnStatement`'s `SessionIndex` (`saml_sessions`, removed with the session). App sign-ins keep them through the one-time code handoff.
- **Signing out of SuperBot** (`POST /api/auth/logout`) revokes the session first, as before. For a browser session from such an IdP, the answer also has `logoutUrl`: a signed LogoutRequest naming that NameID and SessionIndex, over the redirect binding. The web app and the client app's web build go there; the IdP ends its session and sends the browser back. Its LogoutResponse must answer a request botd sent in the last 10 minutes; it is audited as `auth.slo_response` with the IdP's status. Bearer sessions (the phone app, `botctl`) end only here.
- **Signing out at the IdP** sends a LogoutRequest, over HTTP-Redirect or HTTP-POST. It must be signed by a certificate in the IdP's metadata: over the query (redirect, with `SigAlg` and `Signature`) or enveloped (either binding), checked with the same rules as ADR 0127 (RSA-SHA256 or SHA-512, SHA-1 refused, the key from metadata only, a signature only as a direct child of the message, unique IDs). Then it must have our entity's IdP as `Issuer`, our SLO URL as `Destination` (required here, unlike the ACS), an `IssueInstant` within five minutes (with the usual two minutes of skew), any `NotOnOrAfter` in the future, a plain `NameID` (`EncryptedID` is refused), and an ID not seen before. botd then revokes every live session that IdP's NameID signed in with before the request's `IssueInstant` (plus the skew), limited to the named SessionIndexes when there are any (sessions made before this change have none and are revoked too), drops their unredeemed app codes, and answers with a signed LogoutResponse to the IdP's response URL, echoing `RelayState`. It leaves the browser's own session cookie alone, since that session may not be one the message named. Metadata from a URL is loaded here if nothing has since a restart, so a logout never waits for a sign-in. It answers success even when nothing matched: the person is signed out either way. Audited as `auth.slo` with the subject, request ID, SessionIndexes and revoked sessions.
- **Refused messages** answer 400 and are audited as `auth.slo_failed` with a reason (`unsigned`, `bad_signature`, `wrapped`, `wrong_issuer`, `wrong_destination`, `expired`, `replayed`, `unknown_request`, …). Those before the signature check, including a provider not ready or without an SLO URL, are throttled like unauthenticated sign-in failures.

The XML-DSig verifier gains one function, `verify_raw`, that checks a detached signature with the same algorithm and key rules as the enveloped one; its wrapping and canonicalization tests are unchanged.

## Consequences

- IdPs that require signed AuthnRequests work natively, and SuperBot sessions end when the IdP ends the person's session, not hours later. Admins who enable SLO must re-import SuperBot's SP metadata at the IdP (or add the certificate and SLO URL by hand), since older imports have neither.
- Revoking by SLO is only as good as the IdP's signature and the NameID: the same trust ADR 0127 gives sign-in. A stolen IdP signing key could sign people out, which is far less than it could already do.
- Used logout IDs are kept in memory, like used assertion IDs (ADR 0127), so a restart forgets them. A LogoutRequest replayed after one is still signed and fresh, but it only reaches sessions made before it was issued, which it already revoked; with the skew, a session made in the two minutes after it could also end.
- SLO is front-channel only (the browser carries the messages). SOAP back-channel logout, which some IdPs use when the browser is gone, isn't supported; IdPs that only offer it are treated as having no SLO URL.
- Still not supported, each still refused with a clear reason: encrypted assertions and NameIDs, IdP-initiated sign-in, and ECDSA keys. Encrypted assertions came next, in [ADR 0150](0150-saml-encrypted-assertions.md), with a separate key of their own; IdP-initiated sign-in stays off because an unsolicited assertion has no request to bind to the browser.
- A new table (`saml_sessions`) and two settings per native provider (`sso_saml_sp_key_<id>`, `sso_saml_sp_cert_<id>`). Deleting those settings makes botd generate a new key, which the IdP must then import.
