# 0023: SCIM provisioning (stub)

## Status

Accepted. A stub for M2 ([roadmap](../ROADMAP.md), issue #24). Full SCIM (groups, group-to-role mapping, bulk) is M5. It builds on [ADR 0012](0012-users-sessions-rbac.md) (users, roles, disabling ends sessions), [ADR 0014](0014-oidc-sso-entra.md) and [ADR 0016](0016-sso-multi-provider.md) (identities are `(issuer, subject)`, never email), [ADR 0019](0019-audit-actors.md) (audit actors) and [ADR 0022](0022-landing-and-signups.md) (approved sign-ups).

## Context

Enterprises manage people in their IdP. When someone joins, they want them in SuperBot. When someone leaves, they want them out within minutes, everywhere, without an admin remembering to run `botctl user disable`. Entra ID, Okta and others do this with SCIM 2.0 ([RFC 7643](https://www.rfc-editor.org/rfc/rfc7643), [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644)). Google Workspace has no generic SCIM client; a connector (or Entra/Okta in front of Google) does it.

Until now an admin made each user by hand, approved a sign-up, or let just-in-time SSO sign-up make one. None of these removes people.

## Decision

### Scope: Users only, core schema

- `/scim/v2/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`: discovery. Only the User resource type.
- `/scim/v2/Users`: `GET` (list, `filter`, `startIndex`, `count`), `POST`. `/scim/v2/Users/{id}`: `GET`, `PUT`, `PATCH`, `DELETE`.
- Attributes kept: `userName`, `externalId`, `name.givenName`, `name.familyName`, `displayName`, one email, `active`. The name SuperBot shows is rebuilt only when a name attribute changes, so an admin's rename lasts until the IdP sends a new name. Everything else (phone numbers, title, the enterprise extension, `roles`, `groups`, Okta's placeholder `password`) is accepted and ignored. Nothing ignored is stored or logged.
- Filters: only `userName eq "…"` (any case) and `externalId eq "…"` (exact). That is what Entra and Okta send to find a user. Anything else is a 400 `invalidFilter`.
- `PATCH`: `add`, `replace` and `remove`, in any case (Entra sends `Replace`). Paths: the kept attributes, `name.*`, `emails`, and `emails[type eq "work"].value`. No path means an object of attributes (Okta's deactivation). `active` as `"True"`/`"False"` strings is accepted, as Entra has sent it.
- Bulk, sorting, ETags and password changes: not supported, and `ServiceProviderConfig` says so.
- Responses are `application/scim+json`. Errors use the SCIM error schema with `scimType` where RFC 7644 defines one.

**Groups are deferred.** SuperBot has no groups to map them to: roles are per user, and Bot access is per user grant ([ADR 0017](0017-bot-acls.md)). Mapping IdP groups to roles is exactly where admin escalation hides, so it gets its own design in M5. `GET /scim/v2/Groups` returns an empty list, so the IdP's connection test passes; other group requests get 501 with a message to turn group provisioning off.

### Auth: per-tenant bearer tokens

- A **tenant** is one IdP connection, named by an admin (`entra`, `okta-prod`). Tokens belong to a tenant. Each tenant sees and changes only users it provisioned.
- A token is `sbp_` plus 256 random bits. Only its SHA-256 is stored (like sessions). It is shown once, by `botctl scim token create <tenant>`. `botctl scim tokens` lists them (never values), `botctl scim token revoke <id>` ends one. A tenant can have several tokens, so rotation has no gap.
- `sbp_…` is redacted by shape everywhere botd redacts ([ADR 0010](0010-secrets.md)), and never logged.
- `/scim/v2` has its own guard, not the session middleware. Session tokens, break-glass Basic auth and the Bots' token don't work there; a SCIM token doesn't work on `/api`.
- **Off by default**: `SCIM=on` turns it on. Off, `/scim/v2` answers 404. Tokens can be made while it's off.

### One user per person: `externalId` and SSO identities

`externalId` is the IdP's id for the person. SuperBot's `id` is the SCIM resource id.

- A tenant can **link an SSO provider** (`--sso <provider>`, set by its first token, for good). Then `externalId` must be the person's subject at that provider (Entra: the object id, mapped from `objectId`; Okta: the user id, which is Okta's default `externalId` and its OIDC `sub`). It is required and checked like `botctl user link`. Provisioning creates the SSO identity with the user, so the person can sign in at once and is the same user everywhere.
- If that identity is already linked to a user (an admin linked it, or just-in-time sign-up made the user), `POST` takes that user on (`scim.user_linked`) instead of making a second one. Never the owner account, and never a user another tenant manages, even one it deleted: only that tenant can bring them back (409).
- **Email never matches.** An existing user with the same email is a 409 `uniqueness`, with a hint to link the SSO identity first. Same rule as SSO ([ADR 0014](0014-oidc-sso-entra.md)) and sign-ups.
- `externalId` can be set once, then never changes (400 `mutability`). Attribute names are read in any case, as RFC 7643 requires; the same name twice in one object, in different cases, is a 400. `POST` with a known `externalId` is a 409 while the user exists. That makes retries safe.
- Without a linked provider, SCIM manages users who sign in with codes or are linked later.

### Deprovisioning

- `active: false` disables the user. Every session ends at once (`revoke_user_sessions`), and open screens are closed, as when an admin disables someone. Disabled users still appear in `GET` and filters: Entra and Okta must find them to reactivate them.
- The IdP owns `active` for the users it manages. An admin can still disable one in SuperBot, but the IdP's next update with `active: true` enables them again. Remove people in the IdP.
- Updates check, in the same transaction as the write, that the user is still the tenant's and not deleted, so a racing update can't undo a `DELETE`. Only `POST` restores.
- `DELETE` is soft. The user is disabled, its sessions end, and the tenant can no longer see it (404). The user row, its identities, its Bots and the audit history stay; users are never deleted ([ADR 0012](0012-users-sessions-rbac.md)). The `externalId` stays reserved: provisioning the same person again brings back the same user (`scim.user_restored`), not a stranger with their history.

### Roles

SCIM never sets a role. New users get `SCIM_DEFAULT_ROLE`: `member` (default) or `readonly`. botd refuses to start with `admin`. `roles` in requests is ignored. Admins change roles as before, and SCIM updates leave them alone. Granting admin is never an IdP attribute away.

### Sign-ups

Separate paths that don't collide. A SCIM user who asks for access on the get-started page shows as `existingUser` and can't be approved again (409), like any user. A sign-up approved first is an unmanaged user; SCIM takes it on only through its linked SSO identity, never by email.

### Audit

Every change is recorded with a system actor for the token ([ADR 0019](0019-audit-actors.md)): `actorKind: system`, `actorId: scim:<token id>`, `actorName: SCIM <tenant>`, `authMethod: scim_token`, and the linked provider in `idp`/`idpProvider`. Events: `user.created` (`reason: scim`), `user.updated` (with `userName`/`externalId`/name changes), `user.disabled` (`sessionsRevoked`), `user.enabled`, `user.identity_linked`, `scim.user_linked`, `scim.user_deleted`, `scim.user_restored`. Admins' token changes: `scim.token_created`, `scim.token_revoked`. Bad tokens: `scim.auth_failed`, throttled per IP like failed logins. Filter with `botctl audit --actor system:scim:<token id>` or `--method scim_token`.

### Rate limits

- 600 requests a minute per tenant. More gets 429 with `Retry-After`; Entra and Okta back off on it.
- 20 requests with a bad or missing token per IP in 10 minutes, then 429 for that IP.
- Bodies over 64 KiB are refused.

## Consequences

- Leavers lose access as soon as the IdP sends the update: Entra's provisioning cycle (about 40 minutes, or on demand) or Okta's push (seconds).
- Two new tables (`scim_tokens`, `scim_users`) in migration 9. `users` is unchanged: SCIM is a layer on it, not a second user store.
- A tenant is a trust boundary inside one server. M3 tenancy can map SCIM tenants to SuperBot tenants.
- Without a linked SSO provider, SCIM users still need a sign-in code or a manual link. The setup guide recommends linking.

## Alternatives considered

- **Session middleware with a new role**: SCIM errors and auth differ from `/api`, and a provisioning token must never reach Bots or approvals. A separate guard keeps the blast radius to users.
- **Match existing users by email**: easy, and how account takeover happens ("nOAuth"). Rejected, as for SSO.
- **Hard delete on `DELETE`**: destroys audit history and Bot ownership. Rejected.
- **One global token**: can't scope users per IdP or rotate without a gap. Rejected.

## Not in this slice

Groups and group-to-role mapping, Bulk, sorting, ETags, the enterprise extension, `meta.version`, a web UI for tokens, and per-token scopes (M5).
